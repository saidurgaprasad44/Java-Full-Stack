Client or Integrated Application mainly uses the below mechanisms for authentication:
- API Keys
- HMAC
- OAuth2 Client Credentials - Client Secret or JWT Assertion
- TLS
- mTLS

=======================================================================================================================================================================
API Keys
=======================================================================================================================================================================

- An API key is a credential used to identify and authenticate an application, client, or integration when accessing an API.
- An API key is usually generated by the API provider and associated with a specific client.
- The provider can use the key to identify the caller, apply permissions, rate limits, quotas, or other policies.
- API keys are generally application credentials rather than human-user credentials.

------------------------------------------------------------
Client/Application/Integration Identity
------------------------------------------------------------

- An API key commonly identifies the application or integration that possesses it.
- The provider can therefore associate API activity with that client.

Example:

  API key A → My Travel App
  API key B → Weather Dashboard
  API key C → Mobile Application

- If multiple users operate the same application using the same API key, the API provider may only know the application identity unless an additional user-authentication mechanism is supplied.

- Possessing an API key does not automatically prove which human user is making the request.
- It generally proves possession of a credential associated with an application or client.

=======================================================================================================================================================================
Fundamentals
=======================================================================================================================================================================

- API keys are commonly used when an application needs to access an API without requiring a human user to log in for every request.
- An API key is typically a long-lived credential compared with a short-lived access token.
- The key itself is usually a random value with no meaningful information encoded inside it.

Example:

  Developer registers:
    My Travel App

  API Provider creates:
    API key → abc123...

  Travel App:
    API request + API key
        ↓
    API Provider
        ↓
    Identify "My Travel App"
        ↓
    Apply permissions / limits
        ↓
    Return response

- An API key is not necessarily a token in the OAuth2 sense.
- API key and access token are both credentials, but they have different security models and purposes.

=======================================================================================================================================================================
Architecture
=======================================================================================================================================================================

- The main participants are:
  - API Client
  - API Provider
  - API Key
  - Protected API

- The API Provider maintains an association between the API key and the client it represents.

Flow:

  API Client
      │
      │ API Key
      ↓
  API Provider
      │
      ├── Identify client
      ├── Check key status
      ├── Check permissions
      ├── Check limits
      ↓
  Protected API

- The API provider may store metadata associated with the key, such as:
  - Client/application
  - Status
  - Permissions
  - Expiration
  - Creation time
  - Rate limits
  - Usage information

=======================================================================================================================================================================
Authentication Flow
=======================================================================================================================================================================

- A typical API-key flow is:

  Client registration
        ↓
  API key generated
        ↓
  Key provided to client
        ↓
  Client sends API request
        ↓
  API provider extracts key
        ↓
  Key validated
        ↓
  Client identified
        ↓
  Authorization / policy checks
        ↓
  API request processed

------------------------------------------------------------
API Key Generation
------------------------------------------------------------

- API keys should be generated using a cryptographically secure random mechanism.
- Predictable values such as usernames, timestamps, sequential IDs, or simple hashes should not be used as keys.
- The generated value should have sufficient entropy to make guessing impractical.

Example:

  Client registration
       ↓
  Secure random generation
       ↓
  API key
       ↓
  Associate key with client

- A provider may display the full key only once and require the client to store it securely.

------------------------------------------------------------
API Key Transmission
------------------------------------------------------------

- An API key must be transmitted securely.
- HTTPS should be used so that the key is protected during network transmission.
- Common transmission approaches include request headers.

Example:

Authorization: ApiKey <api-key>

- Some APIs use a custom header:

X-API-Key: <api-key>

- Query parameters can also technically carry API keys, but they are generally undesirable because URLs can appear in logs, browser history, monitoring systems, proxies, and other places.

- The header name itself does not make an API key secure.
- The security comes from protecting the credential, using HTTPS, and properly controlling how the credential is handled.

------------------------------------------------------------
API Key Validation
------------------------------------------------------------

- The server typically performs several checks after receiving an API key.

  Request
      ↓
  Extract API key
      ↓
  Locate associated key
      ↓
  Verify key
      ↓
  Check active/expired status
      ↓
  Identify client
      ↓
  Check permissions/policies
      ↓
  Process request

- The provider may compare the supplied key against a stored representation.
- A provider does not necessarily need to store the raw API key; it can store a secure hash of the key and compare hashes during validation.
- The exact storage strategy depends on the API provider.

------------------------------------------------------------
Authorization and Permissions
------------------------------------------------------------

- API keys can be associated with permissions or restrictions.
- Examples:
  - Read-only access
  - Write access
  - Specific API products
  - Specific resources
  - Specific environments
- The API provider can check these permissions after identifying the client.

Example:

  API key → Reporting App

  Allowed:
    reports.read

  Not allowed:
    reports.delete

- Permissions should follow the principle of least privilege.

=======================================================================================================================================================================
Key Management
=======================================================================================================================================================================

- API keys should be treated as secrets and managed throughout their lifecycle.

  Generation
      ↓
  Distribution
      ↓
  Storage
      ↓
  Usage
      ↓
  Rotation
      ↓
  Expiration / Revocation

- Key management should include mechanisms for identifying which application owns each key.

------------------------------------------------------------
Key Storage
------------------------------------------------------------

- API keys should not be stored directly in source code.
- They should not be committed to source-control repositories.
- Production applications should use appropriate secret-management mechanisms.

Common approaches:

- Environment configuration
- Secret managers
- Vault systems
- Cloud secret-management services

- The API provider should also protect stored API-key information.
- Hashing can reduce the impact of a database compromise when the provider does not need to recover the original key.

------------------------------------------------------------
Key Rotation
------------------------------------------------------------

- Key rotation means replacing an existing key with a new key.
- Rotation limits the lifetime of a particular credential and allows compromised or aging keys to be replaced.

Example:

  Existing key
      ↓
  Generate new key
      ↓
  Deploy new key
      ↓
  Verify new key
      ↓
  Revoke old key

- A controlled overlap period can allow applications to migrate without service interruption.

------------------------------------------------------------
Key Expiration and Revocation
------------------------------------------------------------

- Expiration automatically makes a key invalid after a configured time.
- Revocation explicitly disables a key before or at any time during its normal lifetime.
- Revocation is useful when:
  - A key is leaked
  - An application is decommissioned
  - Access is withdrawn
  - A developer leaves an organization
  - A security incident occurs

- Rotation and revocation are different operations.
- Rotation replaces an existing credential.
- Revocation disables a credential.

------------------------------------------------------------
Multiple API Keys
------------------------------------------------------------

- A client can have multiple API keys when the provider supports it.
- Multiple keys can make rotation and environment separation easier.

Example:

  Production → key A
  Staging    → key B
  Development → key C

- Separate keys can also make it easier to revoke one environment without affecting others.

=======================================================================================================================================================================
Security Risks
=======================================================================================================================================================================

- An API key is often a bearer-style credential: whoever possesses the valid key may be able to use it.
- Common exposure points include:
  - Source code
  - Git repositories
  - Application logs
  - URLs
  - Browser history
  - Configuration files
  - Error messages
  - Screenshots
  - Client-side applications

- If a key is exposed, it should be treated as compromised.

------------------------------------------------------------
API Key Leakage
------------------------------------------------------------

- A leaked API key can allow unauthorized access using the privileges associated with that key.
- The impact depends on the permissions, resources, and limits associated with the key.

Example:

  Read-only key leaked
      ↓
  Attacker may read permitted data

  Administrative key leaked
      ↓
  Attacker may perform privileged operations

- Least privilege reduces the impact of a compromised key.

Important measures:

- HTTPS
- Secure storage
- Secret management
- Key rotation
- Key revocation
- Least privilege
- Avoiding sensitive logging
- Monitoring API-key usage

------------------------------------------------------------
Replay Considerations
------------------------------------------------------------

- A normal API key does not inherently prove that a particular request was created by the legitimate client.
- If an attacker obtains a valid key, they may be able to reuse it for additional requests.
- API keys therefore do not provide the per-request integrity and replay protection that request-signing mechanisms such as HMAC can provide.

=======================================================================================================================================================================
API Keys in Microservices
=======================================================================================================================================================================

- API keys can be used for service-to-service authentication when the environment is simple and the requirements are limited.
- Example:

  Quiz Service
      │
      │ API key
      ↓
  Question Service
      │
      ↓
  Validate key
      ↓
  Identify Quiz Service
      ↓
  Process request

- The Question Service can associate the key with `quiz-service` and apply permissions or rate limits.
- For larger microservice environments, more sophisticated mechanisms such as OAuth2 client credentials or mTLS may provide stronger service identity and lifecycle management.

------------------------------------------------------------
API Key Limitations
------------------------------------------------------------

- API keys provide relatively simple client authentication but limited security semantics compared with more advanced authentication systems.
- Common limitations include:
  - Often long-lived credentials
  - Possession-based authentication
  - Limited user identity
  - Limited per-request integrity
  - Credential leakage can allow direct reuse
  - Authorization capabilities depend heavily on provider implementation
  - Rotation and revocation must be properly managed
  - Less suitable for complex delegated authorization

- API keys are therefore most appropriate when the API primarily needs to identify and control access for an application or integration and does not require the richer authorization model provided by OAuth2 or request-level signing provided by HMAC.












=======================================================================================================================================================================
HMAC
=======================================================================================================================================================================

- HMAC (Hash-based Message Authentication Code) is a mechanism for authenticating messages using a shared secret and a cryptographic hash function.
- HMAC is commonly used when a client and server share a secret and the server needs to verify that a request was created by someone possessing that secret.
- HMAC can provide:
  - Authentication of the caller possessing the shared secret
  - Integrity of the signed request data
- HMAC does not encrypt the request or the secret.

------------------------------------------------------------
Fundamentals
------------------------------------------------------------

- HMAC is calculated from:
  - A shared secret
  - Message/request data
  - A cryptographic hash function
- The shared secret is known by both the sender and receiver.
- The secret itself is never sent as part of the request.

Conceptually:

  HMAC = HMAC(secret, request-data)

- Common hash functions used with HMAC include SHA-256 and SHA-512.
- HMAC-SHA256 is a common practical choice.

------------------------------------------------------------
Shared Secret
------------------------------------------------------------

- The shared secret is the credential used by both parties to generate and verify the HMAC.
- The client stores the secret and uses it to sign requests.
- The server stores the corresponding secret and uses it to verify requests.
- The secret must remain confidential.

Example:

  Client
    secret = S123...

  Server
    secret = S123...

- An attacker who obtains the secret can generate valid HMAC signatures.
- Therefore, the shared secret should be protected like any other sensitive credential.

------------------------------------------------------------
HMAC as Request Signing
------------------------------------------------------------

- HMAC is commonly used to sign request data.
- The request itself does not become an HMAC.
- The client calculates an HMAC value from selected request data and the shared secret.
- That HMAC value is sent along with the request as the request signature.

Example:

  Request data
       +
  Shared secret
       ↓
  HMAC-SHA256
       ↓
  Signature

- The server independently calculates the expected signature and compares it with the received signature.

------------------------------------------------------------
Authentication and Integrity
------------------------------------------------------------

- If the server successfully verifies the HMAC, it establishes that the caller possessed the shared secret.
- If the HMAC covers the relevant request data, modification of that data causes the calculated signature to differ.
- Therefore, HMAC can provide both:
  - Proof of possession of the shared secret
  - Integrity protection for the signed request data

- HMAC does not identify a human user unless the shared secret itself is associated with a specific user identity.
- It is commonly used for application, service, or integration identity.

------------------------------------------------------------
Request Signing Data
------------------------------------------------------------

- The client and server must agree exactly on which request information is included in the HMAC calculation.
- Common signing inputs include:
  - HTTP method
  - Request path
  - Query parameters
  - Request body
  - Timestamp
  - Nonce

Example:

  POST
  /payments
  amount=100
  timestamp=...
  nonce=...

       +
  shared secret

       ↓

  HMAC-SHA256
       ↓
  signature

- The exact representation of the signing data must be agreed between both parties.

------------------------------------------------------------
Canonicalization
------------------------------------------------------------

- Canonicalization means converting request data into a deterministic representation before calculating the signature.
- Both client and server must produce exactly the same signing input.
- Differences in whitespace, parameter ordering, encoding, casing, or body representation can produce different HMAC values.

Example:

  Client signing data:
  amount=100&currency=INR

  Server signing data:
  currency=INR&amount=100

- If parameter ordering is significant and no canonicalization rule exists, the signatures can differ even though the logical request is equivalent.
- A defined canonical representation prevents this problem.

------------------------------------------------------------
Request Signing Flow
------------------------------------------------------------

- The complete request-signing flow is:

  Client
     ↓
  Prepare request
     ↓
  Create canonical signing data
     ↓
  Add timestamp / nonce
     ↓
  Calculate HMAC using shared secret
     ↓
  Add signature to request
     ↓
  Send request
     ↓
  Server receives request
     ↓
  Validate timestamp / nonce
     ↓
  Recreate canonical signing data
     ↓
  Calculate expected HMAC
     ↓
  Compare signatures
     ↓
  Accept / reject request

- The request data used by the server must match the data used by the client when generating the signature.

------------------------------------------------------------
Signature Transmission
------------------------------------------------------------

- The generated HMAC value is commonly transmitted using an HTTP header.

Example:

Authorization: HMAC keyId="client-123", signature="abc..."

- Another API may use custom headers:

X-Client-Id: client-123
X-Timestamp: 1789837655
X-Signature: abc...

- The exact header format is application-specific.
- The shared secret itself must not be included in the request.

------------------------------------------------------------
Signature Verification
------------------------------------------------------------

- The server receives the request and signature.
- It identifies the client or key associated with the request.
- It retrieves the corresponding shared secret.
- It reconstructs the signing data.
- It calculates the expected HMAC.
- It compares the expected signature with the supplied signature.

Flow:

  Received request
        ↓
  Identify client/key
        ↓
  Retrieve secret
        ↓
  Recreate signing data
        ↓
  Calculate expected HMAC
        ↓
  Compare
      /     \
   Match   Different
     ↓         ↓
  Accept     Reject

- Signature comparison should use a constant-time comparison mechanism where appropriate to reduce timing-based side channels.

------------------------------------------------------------
Request Integrity
------------------------------------------------------------

- HMAC protects the integrity of the data included in the signature.
- If an attacker changes signed data, the server's calculated HMAC will no longer match the received signature.

Example:

  Original:

  amount=100
  signature=HMAC(secret, amount=100)

  Attacker changes:

  amount=1000

  Server calculates:

  HMAC(secret, amount=1000)

  Result:
  Signature mismatch → request rejected

- Only data included in the signing input receives this integrity protection.

------------------------------------------------------------
Replay Attacks
------------------------------------------------------------

- A replay attack occurs when an attacker captures a valid signed request and sends the same request again.
- A basic HMAC signature does not automatically prevent replay.
- The attacker does not need to know the secret to replay an already valid signed request.

Example:

  Legitimate request
      ↓
  HMAC signature
      ↓
  Attacker captures request
      ↓
  Sends identical request again
      ↓
  Server may accept it

- Replay protection requires additional request-specific information.

------------------------------------------------------------
Timestamp
------------------------------------------------------------

- A timestamp can be included in the signed request.
- The server can reject requests outside an allowed time window.

Example:

  Request timestamp = 10:00

  Allowed window = ±5 minutes

  Request at 10:02 → accepted
  Request at 10:20 → rejected

- The timestamp must itself be included in the signed data so that an attacker cannot simply modify it.

------------------------------------------------------------
Nonce
------------------------------------------------------------

- A nonce is a unique value intended to be used only once.
- The client includes the nonce in the signed request.
- The server can track recently used nonces and reject a duplicate.

Flow:

  Request 1:
    nonce = ABC123
    → accepted
    → ABC123 recorded

  Request 2:
    nonce = ABC123
    → already used
    → rejected

- A nonce provides stronger replay protection when combined with appropriate server-side tracking.

------------------------------------------------------------
Timestamp + Nonce
------------------------------------------------------------

- Timestamp and nonce can be used together.
- Timestamp limits how long a captured request remains usable.
- Nonce prevents the same request from being accepted repeatedly within that time window.

Example:

  timestamp = 1789837655
  nonce = 7f82a1...
  signature = HMAC(secret, request-data + timestamp + nonce)

- The server validates both the timestamp and nonce before accepting the request.

------------------------------------------------------------
Secret Management
------------------------------------------------------------

- HMAC security depends heavily on protecting the shared secret.

Lifecycle:

  Generate
     ↓
  Securely distribute
     ↓
  Securely store
     ↓
  Use for signing
     ↓
  Rotate
     ↓
  Revoke / replace

- Secrets should not be hard-coded in source code.
- Secrets should not be committed to source-control repositories.
- Production systems should use appropriate secret-management mechanisms.

------------------------------------------------------------
Secret Rotation
------------------------------------------------------------

- Secret rotation replaces an existing shared secret with a new one.
- Both client and server must coordinate the change.

Example:

  Old secret → S1
  New secret → S2

  Client updated → S2
  Server accepts → S1 + S2 temporarily
  Migration complete
  Server removes → S1

- Supporting a key identifier can make rotation easier when multiple active secrets exist.

------------------------------------------------------------
Secret Compromise
------------------------------------------------------------

- If an HMAC secret is compromised, an attacker can generate valid signatures.
- The server cannot distinguish an attacker using the stolen secret from the legitimate client using the same secret.
- The compromised secret should therefore be revoked and replaced.

- Least privilege should be applied to each client/service associated with a shared secret.

------------------------------------------------------------
HMAC in Webhooks
------------------------------------------------------------

- HMAC is commonly used to authenticate webhook requests.
- A webhook provider and receiving application share a secret.
- The provider signs the webhook payload.
- The receiving application recalculates the signature and verifies it before processing the event.

Flow:

  Webhook Provider
       ↓
  Payload
       +
  Shared secret
       ↓
  HMAC signature
       ↓
  HTTP request
       ↓
  Receiving Application
       ↓
  Recalculate HMAC
       ↓
  Verify signature
       ↓
  Process webhook

- Timestamp and replay protection can be added when the webhook protocol supports them.

------------------------------------------------------------
HMAC in Service-to-Service Communication
------------------------------------------------------------

- HMAC can authenticate requests between services that share a secret.

Example:

  Order Service
       ↓
  HMAC-signed request
       ↓
  Payment Service
       ↓
  Verify signature
       ↓
  Process request

- This can be useful for controlled internal integrations and external partner APIs.
- Each service or integration can have its own secret to limit the impact of compromise.

------------------------------------------------------------
Important Security Considerations
------------------------------------------------------------

- Always protect the shared secret.
- Use HTTPS even when HMAC is used.
- Sign every security-sensitive request component that must be protected.
- Define a deterministic canonicalization scheme.
- Include timestamps and/or nonces when replay protection is required.
- Validate timestamps within a reasonable window.
- Track nonces when one-time request protection is required.
- Use constant-time signature comparison where appropriate.
- Rotate compromised or aging secrets.
- Avoid logging shared secrets and complete sensitive signatures unnecessarily.
- Use least privilege for each client or service.
- Do not assume HMAC provides encryption; request confidentiality still requires TLS or another encryption mechanism.

------------------------------------------------------------
Limitations
------------------------------------------------------------

- Both parties must securely possess the shared secret.
- Secret distribution becomes more difficult as the number of clients increases.
- Compromise of the secret allows an attacker to generate valid signatures.
- Replay protection requires additional mechanisms such as timestamps and nonces.
- Client and server must agree precisely on the signing algorithm and canonical request representation.
- HMAC does not provide delegated authorization by itself.
- HMAC does not inherently provide human-user authentication.
- HMAC does not encrypt request data.
