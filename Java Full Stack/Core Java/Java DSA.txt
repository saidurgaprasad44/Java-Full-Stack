============================================================
String: 
============================================================

- Immutable, so its contents cannot be changed after creation, any change will create a completely new object in string pool, so automatically thread-safe.

- String Literal: 
	- Example: String str = "Java"; // Declared and initialized using a literal
	- The most common way. It uses the String Pool for memory efficiency.
	- If "Java" already exists in the pool, the new reference points to the existing object.

- Using the new Keyword: 
	- Example: String s = new String("Java"); // Explicit instantiation
	- This forces the creation of a new object in the standard heap memory, even if "Java" already exists in the pool.
	- Less efficient; creates redundant objects.

- Example: 
	String s1 = "Hello";
	String s2 = "Hello";
	String s3 = new String("Hello");
	System.out.println(s1 == s2); // true (same reference in pool)
	System.out.println(s1 == s3); // false (different objects in memory)
	System.out.println(sq.equals(s3) // true (== to compare the reference, while .equals() to compare the content)

============================================================
HashMap: 
============================================================

- Offers fast lookups but no specific order.


Internal data structure: 

- A HashMap internally uses an array of buckets. Each bucket can hold entries containing:
	- Hash value
	- Key
	- Value
	- Reference to the next entry (to connect entries that have the same bucket index called chaining collision-resolution technique)

- The bucket array is called the table in the OpenJDK implementation.
- Each entry is represented by a Node object, conceptually containing:

static class Node<K,V> {
    int hash;
    K key;
    V value;
    Node<K,V> next;
}

- Consider:

Map<Integer, String> employees = new HashMap<>();

employees.put(101, "John");
employees.put(102, "Alice");
employees.put(103, "David");

- Conceptually:

Index	Bucket
-------------------
0	Empty
1	101 → John
2	103 → David
3	Empty
4	102 → Alice
5	Empty
6	Empty
7	Empty


Mutability & Modifiability: 


How do operations work?:

put(): 
	
Step 1: Calculate the key's hash
- It obtains the key's hashCode() and applies an additional hash-spreading operation.

Step 2: Calculate the bucket index
- HashMap determines where the entry should be stored using: index = (capacity - 1) & hash;
- A single bucket can have multiple entries (hash collision)

Step 3: Check the bucket
- If the bucket is empty, insert a new node.
- If the bucket already contains an entry, compare (==) search hash with stored hash and search key with (equals()) stored key.
- If the same key exists, replace its value.
- Otherwise, handle the collision by adding another node to that bucket.

Step 4: Check whether resizing is required
- HashMap monitors its size against its threshold.
- With the default configuration:
	- Initial capacity: 16 (allocated lazily when first needed).
	- Load factor: 0.75.
	- Resize threshold: 16 × 0.75 = 12.
- When the number of entries exceeds the threshold, the table generally doubles in capacity (16, 32, 64, ....).
- For example if the current capacity is 16, then resize threshold = 12; At this moment, if a 13th element is added, it resizes itself to 32

get():

- Calculates the hash of key 101 using hashCode().
- Calculates the bucket index.
- Goes directly to that bucket.
- Checks the hash and key equality with equals().
- Returns the matching value.


Time complexity:

Operation	Average			Worst case
--------------------------------------------------

remove()	O(1)			O(n)

------------------------------------------------------------
equals() vs hashCode()
------------------------------------------------------------

- These two methods are particularly important when working with custom objects in hash-based collections.
- hashCode() helps locate the bucket; equals() distinguishes objects within that bucket.


equals():

- By default, the equals() method inherited from Object compares object references, just like ==
- The equals() method is overridden in String class to define content based equality
- Override equals() in custom Java classes to define business logic based equality.


Overriding equals():

class Employee{
	private String name;
	private int id;
	
	@Override
	public boolean equals(Object obj) {
		if (this == obj) return true;
		
		if (obj == null || !(obj instanceof Employee)) return false;
		
		Employee other = (Employee)obj;
		
		return Objects.equals(this.name,other.name) && this.id == other.id;
	}	

	//getters & setters.....

	//Overridden hashCode().....
}


hashCode():

- hashCode() returns an integer to determine where an object should be stored.
- If hashCode() isn't overridden in custom classes, the default implementation from Object guarantees a distinct integer for every single unique object instance created in memory, regardless of whether their internal fields hold identical data.
- Override hashCode() in custom classes to use hash based collections like HashMap, HashSet etc.,


Overriding hashCode():

class Employee{

	......

	@Override
	public int hashCode() {
    		return Objects.hash(name, id);
	}	

	......

}

- For custom objects as HashMap keys, make sure the equals-hashCode contract is followed

The equals-hashCode contract:

Rule				Meaning
--------------------------------------------
If a.equals(b) is true		a.hashCode() must equal b.hashCode()
If hash codes are equal		Objects are not necessarily equal
If equals() is overridden	You should also override hashCode()
If objects are unequal		They may still have the same hash code (collision)

- If mutable fields are used for HashMap key equality and hashing, the lookup may fail, if the field is changed after inserting the object 
- Why? The entry was stored using the original hash, but lookup now calculates a hash using the modified ID
- Use immutable fields for HashMap key equality and hashing wherever possible.



------------------------------------------------------------
Hash Collision:
------------------------------------------------------------

- A hash collision occurs when their hash values map to the same bucket index.
- The nodes from the same bucket maintain links to next node for node traversal (Single linked list)

How does HashMap retrieve an element from a collided bucket?

- Suppose John and Alice are in the same bucket.

HashMap:

- Calculates Alice's hash.
- Identifies bucket 5.
- Checks the first node (John).
- Compares the stored hash and key.
- John doesn't match.
- Follows next to the second node.
- Finds Alice and returns 200.



------------------------------------------------------------
Treeification:
------------------------------------------------------------

- If a bucket gets too crowded, the long linked list can make lookups expensive.
- To improve performance, modern Java HashMap implementations can convert a heavily collided bucket into a Red-Black Tree called treeification.
- In OpenJDK Java 17/21, the relevant thresholds are:

Constant		Value	Meaning
-------------------------------------------
TREEIFY_THRESHOLD	8	Collision-chain threshold that triggers treeification consideration
UNTREEIFY_THRESHOLD	6	Threshold used when splitting tree bins during resizing
MIN_TREEIFY_CAPACITY	64	Minimum table capacity for treeification

- Treeification improves lookup in heavily collided buckets from O(n) toward O(log n).



------------------------------------------------------------
Resizing:
------------------------------------------------------------

- Allocate a new bucket array with double the capacity.
- Redistribute existing entries into the new table.
- Update the table reference and threshold.

Note: Existing nodes already store their spread hash, so HashMap reuses it during resizing



============================================================
LinkedHashMap:
============================================================

Internal Data Structure:

- LinkedHashMap extends HashMap. 
- It retains the hash-based lookup mechanism but adds a doubly linked list connecting entries to maintain iteration order.
- The LinkedHashMap entry contains additional before and after references alongside the normal HashMap node fields (i.e., hash, key, value, next).

Conceptually:

static class Entry<K, V> extends HashMap.Node<K, V> {
    Entry<K, V> before;
    Entry<K, V> after;
}

static class Node<K, V> {
    final int hash;
    final K key;
    V value;
    Node<K, V> next;
}

- The trade-off is additional memory for the two linked-list references in every entry.



Mutability & Modifiability:

 

How do operations work?: 

Insertion:

- HashMap calculates the hash and identifies the bucket.
- The entry is inserted into the bucket.
- LinkedHashMap links the new entry after the current tail.
- The insertion order is maintained.

Retrieval:

- Retrieval uses the normal HashMap mechanism for finding the key in the bucket array
- And it uses next node to traverse through the nodes in the collided bucket

Removal:

- HashMap locates the entry.
- The entry is removed from its bucket.
- Its previous and next entries are linked together.
- The removed entry is unlinked from the ordering list.



Time and space complexity:

Operation	Average complexity
----------------------------------
put()		O(1)
get()		O(1)
remove()	O(1)
containsKey()	O(1)
Iteration	O(n)



Insertion order vs access order:

- By default, it preserves insertion order, but you can configure it to preserve access order instead.

Map<Integer, String> employees = new LinkedHashMap<>(16, 0.75f, true); //LinkedHashMap(int initialCapacity, float loadFactor, boolean accessOrder)

- When accessOrder is true, accessing an entry moves it to the end of the linked list.
- This behavior is the foundation of a classic LRU (Least Recently Used) cache.

Example: Suppose a cache can hold only three entries.

Operation	Cache order (oldest → newest)
Add A		A
Add B		A → B
Add C		A → B → C
Access A	B → C → A
Add D		C → A → D

- B is evicted because it is now the least recently used entry.



Null handling: 

- One null key.
- Multiple null values.



============================================================
TreeMap:
============================================================

- Keeps keys in a sorted order.



Binary Tree: - Each node has at most two children
Binary Search Tree(BST) - A Binary tree where all the left sub tree is less than the current node and the right sub tree is greater than the current node
Complete Binary Tree - A Binary tree with all the levels are completely filled except possibly for the last level filled from left to right.
Red-Black Tree - A self balancing BST using red/black color field
Binary Heap - A Complete Binary Tree with min/max heap ordering.


             Tree
              |
         Binary Tree 
        /           \
      BST        Complete Binary Tree
       |             |
Red-Black Tree   Binary Heap(min/max)




Internal data structure:

- Unlike HashMap and LinkedHashMap, which use bucket array and hashing to locate entries, TreeMap stores entries in a Binary Search Tree structure.
- Each node conceptually contains:

class Entry<K, V> {
    K key;
    V value;

    Entry<K, V> parent;
    Entry<K, V> left;
    Entry<K, V> right;

    boolean color;
}

- Every node's left subtree contains smaller keys.
- Every node's right subtree contains larger keys.
- The tree remains balanced using red/black color field to avoid becoming a long chain.



Ordering using Comparable / Comparator:

- TreeMap determines key ordering using either:

	- Natural ordering through Comparable.
	- A custom ordering through Comparator.

- TreeMap uses the comparison result to determine whether keys are equivalent.
- If compareTo() or compare() returns zero, TreeMap treats the keys as the same key, even if their equals() method returns false.



Mutability & Modifiability: 



Operations: 

Retrieval/get():

- TreeMap starts at the root and compares the requested key with each node
- If the requested key is greater, move right.
- If it is smaller, move left.
- If equal, return the value.

Insertion/put():

- The tree finds the correct position using comparisons.
- However, inserting many values in sorted order could make an ordinary binary search tree unbalanced.

For example: 10, 20, 30, 40

10
  \
   20
     \
      30
        \
         40

- Searching this structure would take O(n), defeating the purpose of a tree.
- TreeMap solves this using Red-Black Tree balancing.



Red-Black Tree Balancing:

- A Red-Black Tree assigns each node a color: red or black.
- It follows rules that prevent the tree from becoming excessively unbalanced.
- When insertion or deletion violates those rules, TreeMap restores balance using:

	- Recoloring nodes.
	- Left rotations.
	- Right rotations.




Time and space complexity:

Operation		Complexity
put()			O(log n)
get()			O(log n)
remove()		O(log n)
containsKey()		O(log n)
firstKey() / lastKey()	O(log n)
containsValue()		O(n)
Iteration		O(n)



Null handling:

- Null key is not allowed with natural ordering
- Null key with custom comparator is allowed if comparator supports null
- Null values are allowed


Important TreeMap APIs:

Method			Meaning
firstKey()		Smallest key	
lastKey()		Largest key	
lowerKey(30)		Greatest key strictly less than 30	
floorKey(30)		Greatest key less than or equal to 30	
ceilingKey(35)		Smallest key greater than or equal to 35	
higherKey(30)		Smallest key strictly greater than 30	
map.subMap(20, 50)	Returns entries with keys from 20 (inclusive) to 50 (exclusive)
map.headMap(30)		Returns keys strictly less than 30.
map.tailMap(30)		Returns keys greater than or equal to 30.
map.pollFirstEntry()	Retrieves and removes smallest entry
map.pollLastEntry()	Retrieves and removes largest entry
map.descendingMap();	Reverse-order view

============================================================
ArrayList:
============================================================


List<Integer> nums = List.of(1, 34, 32, 45); //creates an unmodifiable List, cannot perform operations like set(), remove(), add(), ...
List<String> names = new ArrayList<>(List.of("sai", "vaishu", "bhuvana", "Priya", "Akshay")); //creates a modifiable ArrayList backed by arrays
List<String> roles = Arrays.toList("hr", "developer"); //creates a modifiable ArrayList from an object array


Internal data structure: 

- An ArrayList internally uses a resizable array of Objects (Dynamic Array).
- It has spare capacity to accommodate future additions.
- If the internal array is full and you still append elements
- The ArrayList must:
	- Allocate a larger array.
	- Copy existing elements into it.
	- Insert the new element.
	- Replace the reference to the old array.

- In OpenJDK Java 17/21, the usual growth policy is approximately 1.5 times the previous capacity.
- Resizing involves allocating a new array and copying existing references, which takes O(n) time.
- However, resizing doesn't happen on every insertion. Therefore, repeated add() operations at the end have amortized O(1) time complexity.
- If you know the approximate number of elements beforehand, you can reduce resizing:

List<Employee> employees = new ArrayList<>(1000);

or

ArrayList<Employee> employees = new ArrayList<>();
employees.ensureCapacity(1000);


Mutability & Modifiability:

--------------------------------------------------------------------------------------------------

remove(object)			Search using equals(), then shift			O(n)

Null Safety: 

- ArrayList allows Multiple null elements, because the internal array can store null references.
- However, operations such as calling methods on retrieved elements can cause NullPointerException


Optimization considerations::

- You frequently retrieve elements by index.
- You append elements frequently.
- You iterate over collections frequently.
- You don't need frequent insertions/removals near the beginning or middle.
- You don't require built-in concurrent access.


============================================================
LinkedList: 
============================================================

- Better for frequent insertions and deletions at the beginning or end.
- Implements both List and Deque, so it can be used as a list, queue, or deque.


Internal data structure:

- LinkedList uses a doubly linked list.
- Each node contains:
	- The element.
	- A reference to the previous node.
	- A reference to the next node.

- Java's LinkedList maintains references to the first, last nodes and the size, allowing efficient insertion and removal at both ends.


Mutability & Modifiability: 


How do operations work?:

- Insertion/removal at a known node is O(1), but reaching that position from the beginning generally takes O(n).

Operation			Internal behavior		Complexity
--------------------------------------------------------------------------
get(index)			Traverse nodes from an end	O(n)
add(value)			Create node and link at tail	O(1)
addFirst()/addLast()		Link new node at head/tail	O(1)
removeFirst()/removeLast()	Unlink head/tail		O(1)
remove(index)			Traverse to node, then unlink	O(n)
contains()			Traverse and compare		O(n)


Memory Overhead: 

- Every element requires a separate node containing: The object reference, a previous-node reference, a next-node reference, object-header and alignment overhead.


Thread safety: 

- Not thread-safe; concurrent modifications require synchronization.

 
Null handling: 

- Allows multiple null elements.


Optimization considerations: 

- Use it when you genuinely need efficient insertions/removals at both ends or already have an iterator positioned at the required node.

- A Set is a collection that does not allow duplicate elements.

Size		size(), isEmpty()			Standard collection operations.
Convert		toArray()				Can convert the set into an array.
Iterate		iterator(), forEach()			HashSet iteration order is not guaranteed.




============================================================
HashSet:
============================================================

- Unordered and backed by a hash table for fast operations.


Internal data structure: 

- HashSet internally uses a HashMap.
- Every element you add becomes a key in the internal HashMap.
- The value is a shared dummy object called PRESENT.

For example:

HashSet elements:

John
Alice
David

Internal HashMap:

Key	Value
---------------
John	PRESENT
Alice	PRESENT
David	PRESENT

- This explains why HashSet has no duplicate elements: HashMap keys must be unique.



Mutability & Modifiability: 



Operations: 

add():

- HashMap calculates the hash of the key.
- It identifies the corresponding bucket.
- It checks whether an existing key is equal to insert key.
- If it finds an existing key.
- It replaces the existing value with the same PRESENT object and returns false, indicating no new element was added.
- If no equal key is present, it inserts new key with value PRESENT.



Time complexity:

Operation	Average			Worst case
--------------------------------------------------
add()		O(1)			O(n)
remove()	O(1)			O(n)
contains()	O(1)			O(n)
Iteration	O(size + capacity)	O(size + capacity)



Space complexity:

- HashSet maintains an underlying HashMap table, containing buckets and entries.
- O(n) space for stored elements.
- Additional capacity for unused buckets.
- Each entry has its own node/object overhead.
- Resizing may temporarily require old and new bucket arrays.



Null handling: 

- HashSet permits one null element and any number of non-null elements.



============================================================
LinkedHashSet:
============================================================

- Maintains the order in which elements were added.


Internal data structure:

- LinkedHashSet is essentially a HashSet backed by a LinkedHashMap.
- It maintains the hashing structure for fast lookup and a doubly linked list to preserve insertion order.



Mutability & Modifiability: 



Time Complexity: 

Operation	Average complexity
----------------------------------
add()		O(1)
remove()	O(1)
contains()	O(1)
Iteration	O(n)



Space Complexity:

- It has additional memory overhead compared with HashSet because each entry maintains linked-list references.



Null handling: 

- Allows one null element.



============================================================
TreeSet:
============================================================

- Automatically keeps elements in a sorted order.



Internal data structure: 

- It internally uses a TreeMap, which is implemented as a Red-Black Tree (a self-balancing binary search tree) in OpenJDK.



Mutability & Modifiability: 



Operations: 

add():

- Starts at the root.
- Compares the new value with the current node.
- Moves left if smaller, right if greater.
- Continues until it finds an empty position.
- Inserts the new node.
- If an equivalent element already exists, it isn't inserted.
- Rebalances the tree if necessary.



Time complexity:

Operation		Complexity
-----------------------------------
add()			O(log n)
remove()		O(log n)
contains()		O(log n)
First/last element	O(log n) in the general tree traversal
Iteration		O(n)
Range queries		O(log n + k), approximately



Null handling:

- With natural ordering, it does not permit null elements because they cannot be compared.
- A custom comparator can define a null ordering, although null handling must be explicitly designed.


Optimization considerations: when to choose.


Feature			HashSet			LinkedHashSet			TreeSet
---------------------------------------------------------------------------------------------
Ordering		No guaranteed order	Insertion order			Sorted order
Internal structure	Hash table		Hash table + linked ordering	Balanced tree
Add/search/remove	O(1) average		O(1) average			O(log n)
Null			One null allowed	One null allowed		Generally no null with natural ordering
Duplicates		Not allowed		Not allowed			Not allowed





============================================================
Queue (Order of Processing)
============================================================

- A Queue is designed for holding elements prior to processing, typically following the FIFO (First-In-First-Out) principle. 
- Queue: First In, First Out. Elements are added at the back and removed from the front.
- Deque: Allows insertion and removal at both ends.



Important Queue APIs:

Purpose		Methods			Behavior
----------------------------------------------------
Insert		add(), offer()		add() throws on capacity restriction; offer() returns false.
Remove head	remove(), poll()	remove() throws if empty; poll() returns null.
Inspect head	element(), peek()	element() throws if empty; peek() returns null.



Deque-specific APIs:

Purpose			Methods
-------------------------------------
Insert at front		addFirst(), offerFirst()
Insert at rear		addLast(), offerLast()
Remove from front	removeFirst(), pollFirst()
Remove from rear	removeLast(), pollLast()
Inspect front		getFirst(), peekFirst()
Inspect rear		getLast(), peekLast()



============================================================
PriorityQueue: 
============================================================

- Elements are ordered based on their natural priority or a custom comparator.
- Unlike a normal FIFO queue, the element with the highest priority (or lowest value by default) is retrieved first.



Internal data structure: 

- Java implements PriorityQueue using a Min-Heap, this means the smallest element always stays at the root.
- Java stores the heap in an array.
- For example:

Min-Heap:

      10
     /  \
    20   30
   /  \ 
  40  50

For the above example, one valid internal representation is:

Index:    0   1   2   3   4
          |   |   |   |   |
Array:   [10, 20, 30, 40, 50]

- The relationship between array indexes and tree positions is for a node at index i:

Position	Index
---------------------------
Parent		(i - 1) / 2
Left child	2 * i + 1
Right child	2 * i + 2

- This is why a binary heap doesn't need node objects or left/right references like a TreeMap.
- However, after every insertion/removal, the tree has to restore the min-heap property



Mutability & Modifiability: 



Operations:

Insertion:

- The new element is initially placed at the end to preserve the complete binary tree structure.
- Compare the new element with its parent using "(i-1)/2"
- If the new element is smaller than its parent, swap - Heapify upward (sift-up).
- Repeat this until the new element is greater than its parent
- The heap property is restored.

Removal/poll():

- Remove the root, which is the smallest element.
- Move the last element to the root
- Compare the root with its children using 2 * i + 1 (Left child) and 2 * i + 2 (Right child)
- If the greater than its children, swap with the smaller child - Heapify downward (sift-down)
- Continue until the heap property is restored.



Time and space complexity:

Operation		Complexity
----------------------------------
offer() / add()		O(log n)
poll()			O(log n)
peek()			O(1)
remove(Object)		O(n)
contains()		O(n)
Iteration		O(n)
Space			O(n)



Custom priority using Comparator:

- By default, PriorityQueue is a Min-Heap.
- To create a Max-Heap:

PriorityQueue<Integer> maxHeap = new PriorityQueue<>(Comparator.reverseOrder());

- To prioritize objects:

class Job {
    int priority;
    String name;
}

PriorityQueue<Job> jobs =
    new PriorityQueue<>(
        Comparator.comparingInt(job -> job.priority)
    );

- This retrieves jobs with the smallest priority value first.
- If you want larger priority numbers first:

PriorityQueue<Job> jobs =
    new PriorityQueue<>(
        Comparator.comparingInt((Job job) -> job.priority)
                  .reversed()
    );



Null handling:

- Null elements not allowed



Common backend use cases:

- Processing jobs based on priority.
- Scheduling the next task by execution time.
- Finding the top K elements from a large dataset.
- Merging multiple sorted streams.
- Implementing algorithms such as Dijkstra's shortest path.



============================================================
ArrayDeque: 
============================================================

- A double-ended queue that supports insertion and removal at both ends.
- ArrayDeque is generally preferred over the legacy Stack class for stack operations.
- It can function as:
	- A FIFO Queue.
	- A LIFO Stack.
	- A general-purpose Deque.



Internal data structure: 

- ArrayDeque is implemented using a resizable circular array.
- It maintains:
	- An internal array.
	- A head index pointing to the first element.
	- A tail index representing the next insertion position at the rear.



Mutability & Modifiability:

peekLast()	Read rear; returns null if empty

Complexity:

----------------------------------------------

Remove from front/rear		O(1)
Peek at front/rear		O(1)
Search (contains)		O(n)

- Duplicate elements are allowed


============================================================
LinkedList:
============================================================

- Doubly linked list; implements both List and Deque.
- It supports FIFO, LIFO and double-ended operations



Using LinkedList as a Queue:

Queue<Integer> queue = new LinkedList<>();

queue.offer(10);
queue.offer(20);
queue.offer(30);

queue.poll(); // 10
queue.poll(); // 20

- FIFO behavior:

Insertion → 30 → 20 → 10 → Removal

- offer() inserts at the tail, while poll() removes from the head.
- Both operations are O(1).



Using LinkedList as a Deque:

Deque<Integer> deque = new LinkedList<>();

deque.addFirst(10);
deque.addLast(20);
deque.addFirst(5);
deque.addLast(30);

deque.removeFirst(); // 5
deque.removeLast();  // 30

- Logical structure:

Front → 5 ⇄ 10 ⇄ 20 ⇄ 30 ← Rear

- Both are O(1), because LinkedList already maintains references to the head and tail.



Complexity:

Operation			Complexity
------------------------------------------
Insert at front/rear		O(1)
Remove from front/rear		O(1)
Peek at front/rear		O(1)
Search (contains)		O(n)
Remove arbitrary element	O(n)
Access by index			O(n)
Iteration			O(n)
Space				O(n), with per-node overhead



============================================================
Concurrency in Maps and Collections
============================================================

- None of the collections/maps is not synchronized. Hence, not thread-safe.
- Even though individual reads and writes are generally simple operations, a complete single operation involves multiple steps that are not atomic.
- This can cause lost updates or inconsistent state.

Other Alternatives:

- ConcurrentHashMap, Hashtable
- CopyOnWriteArrayList
- ConcurrentHashMap-backed Set
- ConcurrentLinkedQueue, BlockingQueue
- External locking (you control synchronization)
- Collections.synchronizedList(), Collections.synchronizedMap(), Collections.synchronizedSet() etc.,

Comparable & Comparator:
========================================================================================================================

Comparable:

- Used to naturally order the custom objects implementing Comparable interface and compareTo() abstract method

class Employee implements Comparable<Employee> {

    private int id;
    private String name;
    private double salary;

    @Override
    public int compareTo(Employee other) {
        return Integer.compare(this.id, other.id);
    }
}


Output:

101 - David
102 - Sam
103 - John

- Prefer Integer.compare() over subtraction (this.id - other.id), which can overflow.



Comparator:

- For custom ordering
- With Comparator, we dont have to keep changing the custom class's compareTo() implementation to define the objects ordering.


Ascending salary:

Comparator<Employee> bySalary = (e1, e2) -> Double.compare(e1.getSalary(), e2.getSalary());
employees.sort(bySalary);

Result:

45000 - Sam
50000 - John
60000 - David


Descending salary:

employees.sort(bySalary.reversed());


- We can define multiple comparators without modifying Employee.

Comparator<Employee> byName = Comparator.comparing(Employee::getName);
Comparator<Employee> byIdDescending = Comparator.comparingInt(Employee::getId).reversed();


- One of the most useful capabilities is sorting using multiple conditions.
- Suppose employees should be sorted by - Department ascending, Salary descending within each department, Name ascending when department and salary are equal.

Comparator<Employee> comparator =
    Comparator.comparing(Employee::getDepartment)
        .thenComparing(
            Comparator.comparingDouble(Employee::getSalary)
                      .reversed()
        )
        .thenComparing(Employee::getName);

employees.sort(comparator);
