===============================================================================================================================================================================
JVM vs JRE vs JDK:
===============================================================================================================================================================================

1. JVM (Java Virtual Machine)
- The execution engine that runs Java bytecode(.class). It is "virtual" because it provides a platform-independent interface that doesn't depend on the underlying hardware.
Components: Class Loader, Interpreter, JIT Compiler, Garbage Collector.

2. JRE (Java Runtime Environment)
- The deployment package that provides the minimum requirements to run a Java application. 
JRE = JVM + Class Libraries (e.g., rt.jar) + Supporting Files

3. JDK (Java Development Kit)
- The full toolkit for Java developers to create and run applications. 
JDK = JRE + Development Tools (javac, jdb, javadoc, etc.)

===============================================================================================================================================================================
The Java Lifecycle - Code to Execution:
===============================================================================================================================================================================

Source Code (.java) ----[Compiler (javac)]---> Bytecode (.class) ----[JVM (Interpreter + JIT Compiler)]---> Machine Code (0s & 1s)


1. The Source Code is initially compiled by javac (the Front-end Compiler) into Bytecode 						-------	(Write Once)

	This Bytecode is platform independent. The JVM is platform-specific, there is a JVM for windows, a JVM for Linux, MacOS etc

2. Now any JVM can translate this universal Bytecode into its specific OS instructions (Machine/Native Code) 				-------	(Run Anywhere)

	The JVM loads the Bytecode and uses two helpers to execute it:

	Interpreter: 
	- Immediately starts reading the bytecode line-by-line and telling the CPU what to do (Slow).

	JIT Compiler: 	
	- Unlike javac which compiles code before you run it, the JIT compiler compiles code while the program is running (In-Time).
	- It watches for "hot" parts of your code (like a loop running 1,000 times) and compiles that specific section into Native Machine Code (Fast).

===============================================================================================================================================================================
Advantages:
===============================================================================================================================================================================

Platform Independence: 
- Write code once and run it on any platform with a Java Virtual Machine (JVM).

Large Community and Ecosystem: 
- Benefits from a massive community, extensive libraries, and frameworks like Spring Boot, which support rapid development and problem-solving.

Object-Oriented: 
- Fully supports object-oriented programming principles, making it modular and reusable.

Robust and Secure:
- Includes features like garbage collection and a security model that protects against threats.

Multithreading: 
- Allows multiple threads of execution to run concurrently, improving performance and resource utilization.

Backward Compatibility: 
- Maintains compatibility with older versions, making it easier to upgrade existing applications. 


===============================================================================================================================================================================
Disadvantages:
===============================================================================================================================================================================

Performance: 
- Can be slower than compiled languages like C/C++ due to the JVM overhead and the JIT compiler's interpretation step.

High Memory Consumption: 
- Uses more memory because of the JVM and automatic garbage collection, which can impact performance in resource-constrained environments.

Verbose Syntax: 
- Code can be more verbose and require more lines to accomplish a task compared to more concise languages.

Lack of Low-Level Control: 
- The absence of low-level pointers makes it less suitable for tasks that require direct hardware manipulation, like driver development.

Slow Startup Time: 
- Applications can have a slower startup time, especially for short-lived processes, due to the JVM's startup process. 


===============================================================================================================================================================================
Memory management & Garbage Collection:
===============================================================================================================================================================================

- Java memory management is automatic, handled by the JVM
- With the crucial Garbage Collector (GC) cleaning up unused objects from the Heap, freeing developers from manual deallocation like in C/C++. 
- Focusing on main areas: 
	- The Stack (for temporary method execution state and stack frames for each thread) and
	- The Heap (for objects and String literals shared by the threads)

- You create objects with new (Heap), while method calls / local variables use the Stack (auto-cleared)

    // code

------------------------------------------------------------

- An Iterator provides a common way to traverse different collections without depending on their internal structure.

while (iterator.hasNext()) { // cursor starts at 0
    String name = iterator.next(); // returns the current element and moves the cursor to next
    System.out.println(name);
}

- The same traversal approach works with other collections, for example: setOfNames.

These define specific properties or logic constraints:

------------------------------------------------------------
static:
------------------------------------------------------------

static Variables: 

- The static variable belongs to the class itself, not instances. 
- All objects share the same copy.



Static Methods: 

- Can be called without creating an object of the class (e.g., Math.sqrt()).
- Use static methods when the operation:
	- Does not depend on individual object state.
	- Performs a general operation using its parameters.
	- Belongs logically to the class rather than a particular instance.
- A static method cannot directly access instance variables or instance methods.

class Employee {

    int id = 101;
    static int count = 10;

    static void display() {

        System.out.println(count); // Allowed
        // System.out.println(id); // Compilation error
    }
}

- However, you can access instance members through an explicitly supplied object:

static void display(Employee employee) {
    System.out.println(employee.id);
}



Static Classes:

- Java does not allow a top-level class to be declared static. Only nested classes can be static.

------------------------------------------------------------
final:
------------------------------------------------------------

Variables: Once assigned, the value cannot change (a constant).
Methods: Cannot be overridden by a subclass.
Classes: Cannot be inherited (extended).

------------------------------------------------------------
abstract:
------------------------------------------------------------

Methods: Has no body (logic). It acts as a requirement that subclasses must implement.
Classes: Cannot be instantiated (you can't do new MyClass()). It only exists to be a parent for other classes.

------------------------------------------------------------
void: 
------------------------------------------------------------

void methods return nothing

------------------------------------------------------------
synchronized & volatile:
------------------------------------------------------------

synchronized: Ensures a method can only be accessed by one thread at a time (prevents data corruption).
volatile: Ensures that changes to a variable are always read directly from main memory, not a thread's local cache.

------------------------------------------------------------
default:
------------------------------------------------------------

Methods: Allowed developers to add method implementations inside interfaces using the default keyword without breaking existing implementing classes.

The Four Pillars of OOP:

------------------------------------------------------------
1. Encapsulation: 
------------------------------------------------------------

- Encapsulation is the practice of bundling an object's data (state) and the methods that operate on that data within a class, while controlling access to its internal state.
- Simply declaring fields as private and providing public getters and setters for every field doesn't automatically achieve good encapsulation.
- Expose meaningful operations that represent what an object should allow callers to do and provide getters and setters only when genuinely required, rather than blindly exposing every field.
s

public class BankAccount {

    private double balance;

    public void deposit(double amount) { // meaningful operation that controls state transitions.
        if (amount <= 0) {
            throw new IllegalArgumentException("Invalid amount");
        }
        balance += amount;
    }

    public double getBalance() { // reasonable because reading the balance is allowed
        return balance;
    }

    // setBalance() — potentially dangerous because it bypasses business rules.
}


------------------------------------------------------------
2. Abstraction: 
------------------------------------------------------------

- Hides complex implementation details showing only the essential features to the caller. 
- It defines a simplified contract that allows different implementations to be used interchangeably without changing the caller's interaction with them.
- Java achieves abstraction using abstract classes and interfaces.

Example:

public interface PaymentProcessor {
    void processPayment(double amount);
}


public class RazorpayProcessor implements PaymentProcessor {

    public void processPayment(double amount) {
        // Razorpay implementation
    }
}


public class StripeProcessor implements PaymentProcessor {

    public void processPayment(double amount) {
        // Stripe implementation
    }
}


public class OrderService {

    private final PaymentProcessor processor;

    public OrderService(PaymentProcessor processor) {
        this.processor = processor;
    }

    public void checkout(double amount) {
        processor.processPayment(amount);
    }
}


- OrderService doesn't know whether the injected object is RazorpayProcessor implementation or StripeProcessor implementation
- But who creates and supplies the object? There are two common approaches:
	- Factory pattern
	- Spring Dependency Injection


------------------------------------------------------------
3. Inheritance: 
------------------------------------------------------------

- A mechanism that allows a class to acquire the properties and behaviors of another class (code reusability) by establishing an "is-a" relationship. 
- Beyond what it inherits, the child class can also define its own new properties and behaviors. 


Types of inheritance:

- Single inheritance
- Multilevel inheritance
- Hierarchical inheritance
- Multiple interface inheritance
- Multiple class inheritance: Java avoids the complexity of multiple class inheritance by allowing a class to extend only one class, while implementing multiple interfaces.



Method Overriding:

- A subclass can provide its own implementation of an inherited instance method.
- If a subclass declares a field or static method with the same name/signature as one in its superclass, the subclass declaration hides the superclass member even though it exists.


Overriding rules:

- Method name and parameter list must match.
- Return type must be the same or covariant.
- Access visibility cannot be reduced.
- Checked exceptions cannot be broadened beyond what the overridden method permits.



Static vs Dynamic Binding:

Static Binding: Java determines the member to access or implementation to execute at compile time, primarily using the reference type.
Dynamic Binding: Java determines which implementation to execute at runtime based on the actual object's type.


Member type			Inherited?	Overridden?		Hidden?			Binding / resolution
--------------------------------------------------------------------------------------------------------------------
Instance fields			Yes		No			Yes, if redeclared	Static
Static fields			Yes		No			Yes, if redeclared	Static
Static methods			Yes		No			Yes, if redeclared	Static
Normal instance methods		Yes		Yes, if overridden	No			Dynamic
Private instance methods	No		No			No			Static
Final instance methods		Yes		No			No			Static
Constructors			No		No			No			Constructor chaining



Constructor Chaining:

- Constructors aren't inherited, but a subclass constructor must initialize its superclass portion.
- super() invokes the immediate superclass constructor.
- If no explicit constructor invocation is provided, Java implicitly inserts super() where permitted.
- If the superclass has no accessible no-argument constructor, you must explicitly invoke an appropriate superclass constructor using super(arguments).
- this() invokes another constructor in the same class.


this vs super:

this:

- this refers to the current object as a whole and provides access to its members (fields and methods). 
- If the current class overrides a superclass method, this.methodName() invokes the overridden method in the current class through normal dynamic method dispatch.
- If the current class has a variable with the same name as a superclass variable (variable shadowing), this.variableName accesses the current class's variable

super:

- super refers to the superclass portion of the current object and provides access to accessible superclass members of the current object
- If a subclass overrides a superclass method, you can still invoke the original parent version using super.methodName().
- If a subclass has a variable with the same name as a parent class variable, super.variableName accesses the superclass's variable.


Example:

class Animal {

    // Property to demonstrate variable hiding
    String type = "General Animal";

    public static void getClassification() {
        System.out.println("Static Classification: Kingdom Animalia");
    }
    // Constructor 1
    public Animal() {
        System.out.println("1. Animal constructor called.");
    }

    public void eat() {
        System.out.println("Eating.");
    }

    public void reproduce() {
        System.out.println("Reproducing to create offspring.");
    }
}

class Mammal extends Animal {

    // Hides Animal.type
    String type = "Warm-blooded Mammal";
    public static void getClassification() {
        System.out.println("Static Classification: Class Mammalia");
    }
    // Constructor 2
    public Mammal() {
        super(); // Explicitly calls Animal() constructor
        System.out.println("2. Mammal constructor called.");
    }

    public void produceMilk() {
        System.out.print("producing milk");
    }

    @Override
    public void reproduce() {
        System.out.print("Giving live birth and ");
        this.produceMilk();
        System.out.println(); // Added for clean formatting
    }
}

class Dog extends Mammal {

    // Hides Mammal.type and Animal.type
    String type = "Domestic Dog";

    // Constructor 3
    public Dog() {
        super(); // Explicitly calls Mammal() constructor
        System.out.println("3. Dog constructor called.");
    }

    public void bark() {
        System.out.print(", barking bow wow ");
    }

    @Override
    public void reproduce() {
        System.out.print("Giving live birth to a litter of puppies, ");
        super.produceMilk();
        this.bark();
        System.out.println("and nursing them.");
    }
}


public class Main {
    public static void main(String[] args) {

        System.out.println("--- CONSTRUCTOR CHAINING ---");
        Animal myPet = new Dog(); 

        System.out.println("\n--- METHOD OVERRIDING (Runtime / Dynamic Dispatch) ---");
        myPet.reproduce(); 

        System.out.println("\n--- VARIABLE HIDING (Compile-time) ---");
        System.out.println("Reference as Animal: " + myPet.type);
        System.out.println("Reference as Mammal: " + ((Mammal) myPet).type);
        System.out.println("Reference as Dog:    " + ((Dog) myPet).type);

        System.out.println("\n--- STATIC METHOD HIDING (Compile-time / Static Dispatch) ---");
        // 1. Calling via object references (Resolved by reference type, NOT actual object)
        myPet.getClassification();             // Calls Animal's version
        ((Mammal) myPet).getClassification();  // Calls Mammal's version
        ((Dog) myPet).getClassification();     // Calls Dog's version

        // 2. Best practice: Calling directly via Class names
        System.out.println("\n--- CALLING STATIC METHODS VIA CLASS NAMES ---");
        Animal.getClassification();
        Mammal.getClassification();
        Dog.getClassification();
    }
}

4. Polymorphism: 
------------------------------------------------------------

- Polymorphism allows a single action to behave differently depending on the object it is acting upon


Types:

Compile-time Polymorphism (method overloading): The compiler selects the method based on the method signature and the compile-time types of the arguments.
Runtime Polymorphism (Dynamic): The JVM selects the overridden implementation based on the actual runtime object.


Vehicle vehicle = new Car();
vehicle.start(); // Car's implementation


- The reference type decides the scope (Vehicle), while the object type decides the implementation (car)


------------------------------------------------------------
Relationships:
------------------------------------------------------------

IS-A Relationship (Inheritance): 

- The IS-A relationship is based entirely on inheritance
- A subclass is a more specialized version of the superclass.
- It is tightly coupled (changes in the parent class directly affect child classes)
- Example: A Car IS-A Vehicle
 


HAS-A Relationship (Association):

- The HAS-A relationship occurs when an instance of one class is used as a field inside another class
- This establishes a loose coupling between classes.
- Association is divided into two sub-types based on how strictly the lifecycles of the objects are tied

Aggregation (Weak HAS-A): 

- The child object can exist independently of the parent.
- Lifecycle: Independent lifetimes. If the parent object is destroyed, the child object survives.
- Example: A Department HAS-A Professor. If the department closes, the professor still exists.

//Child
class Professor {
    	String name;
    	Professor(String name) { this.name = name; }
}

//Parent
class Department {
    	private Professor professor; // Aggregation
    	Department(Professor professor) {
        	this.professor = professor; // Professor is passed from outside
    	}
}

Composition (Strong HAS-A):

- The child object cannot exist independently of the parent.
- Lifecycle: Tightly bound lifetimes. If the parent object is destroyed, the child object is also destroyed.
- Example: A Department HAS-A Professor. If the department closes, the professor still exists.

//Child
class Engine {
    	void start() { System.out.println("Vroom!"); }
}

//Parent
class Car {
	private final Engine engine; // Composition
    	Car() {
        	this.engine = new Engine(); // Engine lifecycle is managed entirely by Car
    	}
}


Note: 

- A parent can receive an object through a constructor and still take exclusive ownership of it.
- Conversely, creating an object inside a constructor doesn't automatically establish composition if that object is shared or independently managed

Generics
------------------------------------------------------------

- Generics allow you to specify the type of data that a class or method can work with using angle brackets < >. 

- This provides:
	- Type Safety: Errors are caught during compilation rather than at runtime.
	- No Casting: You don't have to manually cast objects when retrieving them from a collection.
	- Code Reusability: One piece of logic can be applied to many different data types

- Initially Collection framework was introduced without generics in java, later the generics were introduced to provide type safety
- Generics only work with Class types, does not work with primitives



Without Generics:

ArrayList list = new ArrayList(); 
list.add("Hello");
String s = list.get(0).toString(); // Casting



With Generics:

ArrayList<String> list = new ArrayList<>(); 
list.add("Hello");
String s = list.get(0); // No casting needed
// list.add(10); // Compile-time error! (Type Safety)

===============================================================================================================================================================================
Exception handling:
===============================================================================================================================================================================

- When an exception is triggered (manually or automatically), it creates and throws a new exception object, which contains:	
	Class Name: e.getClass().getName()
	The Detail Message: e.getMessage()
	The Where: e.printStackTrace()

- The thrown exception has to be caught and handled using:
	- try{}: Defines the "danger zone" where you have code that might trigger an exception.
	- catch(){}: The "safety net" that intercepts a specific exception object and executes your Plan B logic.
	- finally{}: The "guaranteed cleanup" block that runs whether an exception happened or not, usually to close files or database connections.

- If no matching catch exists, the exception propagates after finally.
- finally may not execute in cases such as JVM termination using System.exit() or process termination.
- In multiple catch block exception handling, always place more specific exception types before their parent types.
- If an exception occurs inside try, and finally itself throws another exception and the try block exception is not caught and handled, the finally exception replaces the original try exception
 

------------------------------------------------------------
Exception Hierarchy:
------------------------------------------------------------

- All Java exceptions and errors derive from Throwable


java.lang.Throwable                              The base class for all objects that can be thrown or caught.
   |
   ├── java.lang.Error                          Represents serious, unrecoverable system-level issues. Applications are not expected to handle these.
   |
   └── java.lang.Exception                      Represents conditions that a program should typically handle or catch.
            |
            ├── java.lang.RuntimeException      A special subclass for all "unchecked" exceptions.
            |
            └── Other subclasses                All other subclasses of Exception are "checked" exceptions


------------------------------------------------------------
Checked vs Unchecked Exceptions: 
------------------------------------------------------------

Checked Exception:

- Checked Exceptions are checked at compile time. 
- These exceptions are external conditions that the caller may need to respond to.
- The compiler forces you to either handle them using try-catch or declare them using throws to propagate it to the caller.
- Typical response: Handle, retry, fallback, or propagate.


Unchecked Exception:

- Unchecked exceptions are checked at runtime
- unchecked exceptions often represent programming mistakes or business-rule violations
- These are not mandatory to handle
- Typical response: Fix the defect, validate input, reject the operation, or handle at an appropriate application boundary.


Category        Can be handled?      Checked By	    Best Action				 Example
-----------------------------------------------------------------------------------------------------------------------------
Checked         ✅ Yes (Mandatory)   Compiler	    Implement a Plan B                   IOException, SQLException, ClassNotFoundException
Unchecked       ✅ Yes (Optional)    Runtime        Fix the bug in logic or handle it	 NullPointerException, ArithmeticException, IndexOutOfBoundsException
Error           ❌ No                Runtime        Fix system or hardware               OutOfMemoryError, StackOverflowError

throw:

- Manually triggers exception and throws Exception object
- Use it when you want to explicitly throw an exception (built-in standard or custom exceptions).	


public static void withdraw(double amount) throws InsufficientFundsException {
    if (amount > balance) {

        double missing = amount - balance;
        throw new InsufficientFundsException(missing); //Throwing custom exception
    }
    balance -= amount;
    System.out.println("Withdrawal successful!");
}


throws (declaring):

- It is a warning to the caller saying, "Hey, this method is dangerous. You must handle the error yourself using a try-catch."
- throws is mandatory for Checked Exceptions if it is not handled
- Unchecked exceptions can propagate without declaration.
	

public void readFile() throws IOException {
    FileReader reader = new FileReader("data.txt");
}

Exception Propagation:
------------------------------------------------------------

- Suppose method A calls B, and B calls C.


public void methodA() {
    methodB();
}

public void methodB() {
    methodC();
}

public void methodC() {
    throw new IllegalArgumentException("Failure");
}


- If A doesn't catch the exception, it continues propagating up the call stack until a matching handler is found.
- If none is found, it reaches the thread's uncaught exception handler.

Custom Exceptions:
------------------------------------------------------------

//Creating custom checked exception by extending the class from Exception class
//if you want to create a custom unchecked exception, extend the class from RuntimeException
class InsufficientFundsException extends Exception {
    
    // Constructor that accepts a custom message
    public InsufficientFundsException(double amountNeeded) {
        // Pass a formatted string to the parent 'Exception' class
        super("Transaction failed! You are short by: ₹" + amountNeeded);
    }
}

public class CustomException {

    private static double balance = 500.00;

    // throws is mandatory since it is a custom checked exception
    public static void withdraw(double amount) throws InsufficientFundsException {

        if (amount > balance) {

            double missing = amount - balance;
            // Throwing our custom exception with specific data
            throw new InsufficientFundsException(missing);
        }

        balance -= amount;
        System.out.println("Withdrawal successful!");
    }

    public static void main(String[] args) {

        // handling the custom checked exception using try-catch
        try {
            withdraw(750.00); 
        } 
        catch (InsufficientFundsException e) {

            // This will print the custom message we built in the constructor
            System.out.println(e); 
        }
    }
}


------------------------------------------------------------
Exception wrapping
------------------------------------------------------------

- Sometimes you catch a low-level exception and throw a higher-level exception while preserving the original cause.


try {
    repository.save(order);
}
catch (SQLException e) {
    throw new OrderPersistenceException(
        "Unable to save order", e
    );
}


- The second constructor argument preserves the cause.
- This is useful when translating infrastructure exceptions into application-level exceptions without losing debugging information.


------------------------------------------------------------
try-with-resources
------------------------------------------------------------

- This is especially important for I/O, JDBC, and resource management.



Traditional approach:

BufferedReader reader = null;

try {
    reader = new BufferedReader(new FileReader("data.txt"));
    System.out.println(reader.readLine());
}
catch (IOException e) {
    e.printStackTrace();
}
finally {
    if (reader != null) {
        try {
            reader.close();
        } catch (IOException e) {
            e.printStackTrace();
        }
    }
}



Better approach:

try (BufferedReader reader =
         new BufferedReader(new FileReader("data.txt"))) {

    System.out.println(reader.readLine());

}
catch (IOException e) {
    // Handle failure
}


- Java automatically closes resources implementing AutoCloseable when the try block exits, including when an exception occurs.
- If the main operation throws an exception and closing the resource also throws one, the close exception is recorded as a suppressed exception rather than replacing the original exception. You can inspect these using getSuppressed().


------------------------------------------------------------
Best Practices
------------------------------------------------------------

- Don't swallow exceptions with empty catch blocks.
- Don't catch Exception everywhere without a reason.
- Preserve the original exception cause when wrapping.
- Don't use exceptions for normal control flow.
- Avoid logging the same exception at every layer.
- Use meaningful custom exceptions for domain failures.
- Use try-with-resources for resource cleanup.
- Don't catch Error or Throwable casually.
- Avoid throwing exceptions from finally
- Restore the interrupt flag when you cannot propagate InterruptedException
- In Spring Boot, centralize HTTP exception mapping with @RestControllerAdvice and @ExceptionHandler where appropriate.

Static Nested Class
------------------------------------------------------------

- It can directly access private static members of Employee.
- It cannot directly access non-static instance members of Employee because it doesn't have an enclosing Employee instance.
- It can access those instance members if it receives an Employee object.

Inner Class (Non-static nested class)

- It is associated with a particular enclosing Employee object.
- It can directly access both static and non-static members of Employee, including private members.
- It implicitly holds a reference to its enclosing Employee instance.

Lambda Expression (Java8+): 
========================================================================================================================

- An anonymous function that is defined and instantiated implementing a Functional Interface by defining its single abstract method in a highly concise, single expression.
- It simultaneously creates the object and provides the concrete logic for the abstract methods.


Implementation Examples: 

- Here, Runnable is a Functional Interface with only one abstract method named run()


1. Abstract method with no input and returns a result:

Runnable r = () -> "Hello world"; //If the body has one expression, braces and return are optional, it will auto return the value
r.run();


2. Abstract method with input(s), multiple statements and returns a result:

Runnable r = (a, b) -> {
	System.out.print("The sum is: ");
	return a+b;
};
System.out.println(r.run(10, 20));

Functional Interfaces
========================================================================================================================

- From java.util.function



Built-in Functional Interfaces:

Predicate<T>
	Purpose: Takes one input and returns a boolean. Used for filtering/testing.
	Method: boolean test(T t);
	Example: Predicate<String> isStringEmpty = s -> s.isEmpty();

Function<T, R>
	Purpose: Takes one input of type T and returns a result of type R. Used for transforming data.
	Method: R apply(T t);
	Example: Function<String, Integer> stringLength = s -> s.length();

Consumer<T>
	Purpose: Takes an input but returns nothing (void). Used for actions like printing.
	Method: void accept(T t);
	Example: Consumer<String> printer = s -> System.out.println(s);

Supplier<T>
	Purpose: Takes no input but returns a value. Used for lazy generation.
	Method: T get();
	Example: Supplier<Double> randomNum = () -> Math.random();

BiFunction<T,U,R>
	Purpose: Takes two inputs of type T and U and returns a result of type R
	Method: R apply(T,U);
	Example: BiFunction<Double, Double, Double> calculateBonus = (salary, percentage) -> salary * percentage / 100;

BiPredicate<T,U>
	Purpose: Comparing two inputs
	Method: boolean test(T,U);

BiConsumer<T,U>
	Purpose: Processing two inputs
	Method: void accept(T,U);

UnaryOperator<T>
	Purpose: Transforming same type.
	Method: T apply(T);

BinaryOperator<T>
	Purpose: Combining same-type values and produces a result of same-type.
	Method: T apply(T,T);




Primitive-specialized functional interfaces:

- Java also provides specialized interfaces to avoid unnecessary boxing and unboxing.
- This is useful when extracting primitive values, particularly in streams, without converting them to wrapper objects unnecessarily.

Interface		Purpose				Method
----------------------------------------------------------------
IntPredicate		Takes int, returns Boolean	test(int)
IntFunction<R>		Takes int, returns R		R apply(int)
ToIntFunction<T>	Takes T, returns int		int applyAsInt(T)
IntConsumer		Takes int, returns void		void accept(int)
IntSupplier		Returns int			int getAsInt()
IntUnaryOperator	Takes int, returns int		int applyAsInt(int)
IntBinaryOperator	Takes two ints, returns int	int applyAsInt(int, int)

- Similar interfaces available for Long and Double as well

Example:

ToIntFunction<Employee> salaryExtractor = Employee::getSalary;




Default methods and composition: 

- Functional interfaces have useful default methods that let you combine behavior.


Interface	Main composition methods
------------------------------------------------
Predicate	and(), or(), negate(), isEqual()
Function	andThen(), compose(), identity()
Consumer	andThen()
Supplier	No standard composition method
BiFunction	andThen()


Examples:

//Predicate composition
Predicate<Employee> highSalary = e -> e.getSalary() > 50000;
Predicate<Employee> inIT = e -> e.getDepartment().equals("IT");

Predicate<Employee> eligible = highSalary.and(inIT);
Predicate<Employee> notEligible = eligible.negate();


//Function composition
Function<String, String> trim = String::strip;
Function<String, String> upper = String::toUpperCase;

Function<String, String> normalize = trim.andThen(upper);

System.out.println(normalize.apply(" java ")); // JAVA




Method references:

- Method references are a shorter way to express certain lambdas.


Type							Example			Equivalent lambda
---------------------------------------------------------------------------------------------------------
Static method						String::valueOf		x -> String.valueOf(x)
Instance method of a particular object			System.out::println	x -> System.out.println(x)
Instance method of an arbitrary object of a type	String::toLowerCase	s -> s.toLowerCase()
Constructor reference					ArrayList::new		() -> new ArrayList<>()


Examples:

// Method reference
employees.forEach(System.out::println);

// Lambda
employees.forEach(e -> System.out.println(e));

// Method reference
employees.sort(Comparator.comparing(Employee::getName));

// Lambda
employees.sort((e1, e2) -> e1.getName().compareTo(e2.getName()));
