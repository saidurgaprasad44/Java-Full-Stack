=============================================================================================================================================================================
										HTTP PROTOCOL
=============================================================================================================================================================================

- HTTP (HyperText Transfer Protocol) is an application-layer protocol used for communication between systems over a network.
- HTTP follows a Request-Response communication model:

			─────────── ( HTTP Request Message ) ───────────►
[ Client / Browser ]									[ Server / Spring Boot ]
			◄────────── ( HTTP Response Message ) ───────────

- HTTP communication can occur between:

  • Client → Server
  • Server → Server
  • Service → Service

Example:

Client
│
│ HTTP Request
▼
Order Service
│
│ HTTP Request
▼
Payment Service

=============================================================================================================================================================================
HTTP REQUEST
=============================================================================================================================================================================

- An HTTP Request contains the information required by the receiver to process the request.
- An HTTP Request consists of:

• Request Line
• Request Headers
• Empty Line
• Request Body (Optional)


[ REQUEST LINE ]  	->  	POST   /api/v1/users/4521/posts?draft=false HTTP/1.1
			        └──┘  └────────┘└──┘└───────────┘  └────┘
			        Method       Path   PathVar     Query       Version

[ REQUEST HEADERS ]     ->  	Host: www.example.com					<- Key: Value pairs
                      		Content-Type: application/json
                      		Authorization: Bearer xyz123
				Cookie: session_id=xyz123; theme=dark; logged_in=true

-----------------------------------Empty Line----------------------------------------

[ REQUEST BODY ]  	->  	{
                        		"filename": "invoice.pdf",
                        		"size": 2048
                      		}


Example:

POST /users HTTP/1.1
Host: example.com
Content-Type: application/json
Accept: application/json

{
"name": "Sai"
}


------------------------------------------------------------------------------------------------------------------------
Request Line


- The Request Line contains:

	• HTTP Method: The verb telling the server what action to perform (GET, POST, PUT, DELETE).
	• Request Target: The request target is the specific resource, path, or URL the client wants to reach on the server.
	• HTTP Version: Tells the server which version of the web protocol the browser is using (e.g., HTTP/1.1 or HTTP/2)

Example:

POST /users HTTP/1.1


POST
→ HTTP Method

/users
→ Request Target

HTTP/1.1
→ HTTP Version

------------------------------------------------------------------------------------------------------------------------
Request Headers

- HTTP Headers provide additional information and instructions associated with an HTTP request or response.
- General format:

Header-Name: Header-Value


Examples:

Host: example.com
Content-Type: application/json
Accept: application/json
Authorization: Bearer abc123
Cookie: JSESSIONID=ABC123

- Headers are part of the HTTP protocol and are represented using a header name and value.
- They are not JSON objects.
- Different headers are defined to solve different communication requirements such as: 

  • Authentication
  • Caching
  • Cookies
  • Content negotiation
  • Conditional requests
  • Redirection
  • Cross-origin communication
  • Content representation

------------------------------------------------------------------------------------------------------------------------
Empty Line: 

- A blank line that separates the headers from the body.

------------------------------------------------------------------------------------------------------------------------
Request Body:

- The Request Body contains data sent as part of the HTTP request.
- It can be raw text, a JSON object, XML, HTML, or binary data (like an image file or PDF).
- A request body is commonly used with:

  • POST
  • PUT
  • PATCH

- The `Content-Type` header identifies the format of the request body.

=============================================================================================================================================================================
HTTP RESPONSE
=============================================================================================================================================================================

- An HTTP Response contains the result of processing an HTTP request.
- An HTTP Response consists of:

• Response Status Line
• Response Headers
• Empty Line
• Response Body (Optional)


[ STATUS LINE ]  	->  	HTTP/1.1   200   OK
				└────┘   └─┘   └┘
				Version   Code  Reason Phrase

[ RESPONSE HEADERS ]    ->  	Content-Type: application/json
				Set-Cookie: JSESSIONID=abc789; Path=/ ;HttpOnly
				Cache-Control: no-cache

--------------------------------Empty Line-------------------------------------

[ RESPONSE BODY ]  	->  	{
					"status": "success",
					"message": "File uploaded successfully"
				}


Example:

HTTP/1.1 200 OK
Content-Type: application/json

{
"id": 100,
"name": "Laptop"
}

------------------------------------------------------------------------------------------------------------------------
Response Status Line:

- The very first line returned by the server containing the structural health report of the action:
- The Status Line contains:

  • HTTP Version: Confirms the protocol standard used to send the data back.
  • Status Code: The 3-digit number telling the client if the request succeeded or failed.
  • Reason Phrase: A human-readable text description matching the code (e.g., "OK", "Not Found").


Example:

HTTP/1.1 200 OK



HTTP/1.1
→ HTTP Version

200
→ Status Code

OK
→ Reason Phrase

HTTP Status Code categories:

1xx → Informational
2xx → Successful
3xx → Redirection
4xx → Client Error
5xx → Server Error

------------------------------------------------------------------------------------------------------------------------
Response Headers:

- Background metadata sent by the server to instruct the browser how to handle the incoming payload.

Examples:

Content-Type: application/json
Set-Cookie: ID=value

------------------------------------------------------------------------------------------------------------------------
Response Body:

- The actual data requested by the client.
- Format: HTML text files for web page layouts, JSON data arrays for modern REST APIs, or raw byte streams for downloading files (Images/PDFs).

=============================================================================================================================================================================
HTTP METHODS
=============================================================================================================================================================================

- HTTP Methods indicate the intended operation associated with a request.

------------------------------------------------------------------------------------------------------------------------
GET

- GET is used to retrieve a resource.
- GET requests normally do not contain a request body.


Example:

GET /users/100 HTTP/1.1


------------------------------------------------------------------------------------------------------------------------
POST

- POST is used to submit data or request processing that may create a resource or perform a state-changing operation.

Example:

POST /users HTTP/1.1
Content-Type: application/json

{
"name": "Sai"
}

------------------------------------------------------------------------------------------------------------------------
PUT

- PUT is used to create or completely replace the target resource with the supplied representation.


Example:

PUT /users/100 HTTP/1.1
Content-Type: application/json

{
"id": 100,
"name": "Sai"
}

------------------------------------------------------------------------------------------------------------------------
PATCH

- PATCH is used to partially modify a resource.

Example:

PATCH /users/100 HTTP/1.1
Content-Type: application/json

{
"name": "Sai Kumar"
}

------------------------------------------------------------------------------------------------------------------------
DELETE

- DELETE is used to request deletion of a resource.

Example:

DELETE /users/100 HTTP/1.1

------------------------------------------------------------------------------------------------------------------------

HEAD

- HEAD is similar to GET, but the server returns the response headers without the response body.
- HEAD is useful when the client needs information about a resource without downloading its complete representation.

------------------------------------------------------------------------------------------------------------------------

OPTIONS

- OPTIONS is used to determine the communication options supported by a target resource.
- OPTIONS is commonly used by browsers for CORS preflight requests.

Example:

OPTIONS /users HTTP/1.1


------------------------------------------------------------------------------------------------------------------------
Safe Methods

- A safe HTTP method is a method intended only for retrieving information and not for requesting a state-changing operation on the target resource.

Safe methods include:

GET
HEAD
OPTIONS

- Safe does not mean that the request can never cause any side effects on the server.
- It means that the method's intended semantics are read-only with respect to the target resource.

------------------------------------------------------------------------------------------------------------------------
Idempotent Methods

- An HTTP method is idempotent when making the same request multiple times has the same intended effect on the server as making it once.


Example:

DELETE /users/100


First request:

text
User exists
   ↓
User is deleted


Repeated request:

text
User already deleted
   ↓
Resource remains deleted


- The final intended state is the same.

Idempotent methods:

GET
HEAD
OPTIONS
PUT
DELETE

- PATCH may or may not be idempotent depending on the operation.
- POST is generally non-idempotent.

=============================================================================================================================================================================
HTTP STATUS CODES
=============================================================================================================================================================================

- HTTP Status Codes indicate the result of processing an HTTP request.

The five categories are:

1xx → Informational
2xx → Successful
3xx → Redirection
4xx → Client Error
5xx → Server Error

------------------------------------------------------------------------------------------------------------------------

1xx — Informational

- Indicates that the request has been received and processing can continue.

Example:

100 Continue

------------------------------------------------------------------------------------------------------------------------

2xx — Successful

- Indicates that the request was successfully received, understood and processed.

Important status codes:

200 OK
→ Request successfully processed.

201 Created
→ A new resource was created.

202 Accepted
→ Request was accepted for processing, but processing may not yet be complete.

204 No Content
→ Request successfully processed, but there is no response body.

------------------------------------------------------------------------------------------------------------------------

3xx — Redirection

- Indicates that the client needs to take additional action or that the resource is available at another location.

Important status codes:

301 Moved Permanently
→ Permanent redirect.

302 Found
→ Temporary redirect.

303 See Other
→ Client should retrieve the result from another URI, commonly using GET.

307 Temporary Redirect
→ Temporary redirect while preserving the HTTP method and request body.

308 Permanent Redirect
→ Permanent redirect while preserving the HTTP method and request body.

------------------------------------------------------------------------------------------------------------------------

4xx — Client Error

- Indicates that the request contains a problem from the client's side.

Important status codes:

400 Bad Request
→ Request is invalid or malformed.

401 Unauthorized
→ Authentication is missing or invalid.

403 Forbidden
→ Access to the requested resource or operation is refused.

404 Not Found
→ Requested resource could not be found.

405 Method Not Allowed
→ HTTP method is not supported for the target resource.

409 Conflict
→ Request conflicts with the current state of the resource.

429 Too Many Requests
→ Client has sent too many requests within a given period.

------------------------------------------------------------------------------------------------------------------------

5xx — Server Error

- Indicates that the server failed to successfully process an otherwise valid request.

Important status codes:

500 Internal Server Error
→ Generic server-side error.

502 Bad Gateway
→ A server acting as a gateway or proxy received an invalid response from an upstream server.

503 Service Unavailable
→ Server is currently unable to handle the request.

504 Gateway Timeout
→ A gateway or proxy did not receive a timely response from an upstream server.

=============================================================================================================================================================================
HTTP HEADERS
=============================================================================================================================================================================

- HTTP Headers provide metadata, information and instructions associated with HTTP requests and responses.

General format:
Header-Name: Header-Value

Example:
Content-Type: application/json

- Headers are not represented as JSON.
- Different headers exist to solve different communication requirements.

------------------------------------------------------------------------------------------------------------------------
						Request Headers
------------------------------------------------------------------------------------------------------------------------
- Request Headers are sent by the client/requester to provide information about the request or to provide instructions to the server.


Important Request Headers:


Host: example.com
- Identifies the host to which the request is being sent.


Accept: application/json
- Tells the server which response media type the client prefers.


Content-Type: application/json
- Tells the server the media type of the request body.


Authorization: Bearer eyJhbGciOi...
- Carries authentication credentials such as a Bearer token (JWT/Opaque Token/API Key/OAuth2 Access Token...).


Authorization: Basic dXNlcjpwYXNz
- Carries Base64-encoded credentials using Basic Authentication.


Cookie: JSESSIONID=ABC123
- Sends cookies previously stored by the browser to the server.


User-Agent: Mozilla/5.0
- Identifies information about the client software making the request.


Origin: https://frontend.example.com
- Identifies the origin from which a browser request originated.


If-None-Match: "abc123"
- Sends a previously received ETag so the server can determine whether the cached representation has changed.


If-Modified-Since: Sat, 01 Aug 2026 10:00:00 GMT
- Sends the previously received modification time so the server can determine whether the resource has changed.


Accept-Language: en-US
- Tells the server which response language the client prefers.

Multiple preferences:

Accept-Language: en-US, en;q=0.9
- Indicates that `en-US` is preferred over `en`.


Accept-Encoding: gzip, br
- Tells the server which content encodings the client can handle.

------------------------------------------------------------------------------------------------------------------------
						Response Headers
------------------------------------------------------------------------------------------------------------------------
- Response Headers are sent by the server/receiver to provide information about the response or instructions to the client.


Important Response Headers:


Content-Type: application/json
- Tells the client the media type of the response body.


Content-Length: 1024
- Indicates the size of the response body in bytes.


Set-Cookie: JSESSIONID=ABC123; Path=/; Secure; HttpOnly
- Instructs the browser to store the specified cookie.


Cache-Control: max-age=3600
- Provides caching instructions to caches such as browsers, CDNs, and proxies.


ETag: "abc123"
- Provides an identifier for a specific representation of the resource for cache validation.


Last-Modified: Sat, 01 Aug 2026 10:00:00 GMT
- Indicates when the resource representation was last modified.


Location: https://example.com/new-page
- Specifies the location to which the client should redirect.
- Commonly used with 3xx responses.


WWW-Authenticate: Basic realm="example"
- Tells the client which authentication scheme can be used to authenticate with the server.


Access-Control-Allow-Origin: https://frontend.example.com
- Tells the browser which origin is allowed to access the response.


Access-Control-Allow-Methods: GET, POST, PUT
- Tells the browser which HTTP methods are allowed for the cross-origin request.


Access-Control-Allow-Headers: Authorization, Content-Type
- Tells the browser which request headers are allowed in the cross-origin request.


Access-Control-Allow-Credentials: true
- Indicates that the browser may include credentials in a credentialed cross-origin request.


Access-Control-Expose-Headers: ETag, X-Request-ID
- Tells the browser which response headers can be accessed by browser JavaScript.


Content-Language: en-US
- Indicates the language of the response representation.


Content-Encoding: gzip
- Indicates that the response representation has been encoded using gzip.

=============================================================================================================================================================================
HTTP BODY
=============================================================================================================================================================================

- The HTTP Body contains the actual data being transferred.
- The body can contain different representations depending on the use case.

Common representations include:

• JSON
• XML
• Form Data
• Multipart Data

------------------------------------------------------------------------------------------------------------------------
CONTENT-TYPE

- `Content-Type` identifies the media type of the message body.
- It can be present in both requests and responses.

Example:
Content-Type: application/json

Example body:

{
	name: "Sai"
}

------------------------------------------------------------------------------------------------------------------------
Standard Web & API Formats:


- application/json: 
	- Standard for modern REST APIs (JavaScript Object Notation).

- application/x-www-form-urlencoded: 
	- Used to send URL-encoded simple text string.
	- Formatted as key-value pairs separated by ampersands (&) with an equals sign (=) between each key and value
	- Example body: username=Sai&password=secret
	- It is the default format for submitting HTML forms and standard API requests

- multipart/form-data: 
	- Used for HTML forms that include multiple independent parts and file uploads.
	- Each part can contain its own headers and content.
	- Commonly used for:
		• File uploads
		• Form fields combined with files
		• Multiple pieces of data in one request

- application/xml or text/xml: 
	- Used for older SOAP APIs and XML data

------------------------------------------------------------------------------------------------------------------------
Text & Document Formats:

- text/html: Standard web pages.
- text/plain: Raw, unformatted text.
- text/css: Cascading Style Sheets for web design.
- text/javascript: JavaScript files.
- application/pdf: Portable Document Format.

------------------------------------------------------------------------------------------------------------------------
Image Formats:

- image/jpeg: Standard photographs.
- image/png: Portable Network Graphics (supports transparency).
- image/gif: Animated or static GIFs.
- image/svg+xml: Vector graphics.
- image/webp: Modern, highly compressed web images.

------------------------------------------------------------------------------------------------------------------------
Audio & Video Formats:

- audio/mpeg: MP3 audio files.
- audio/wav: Waveform audio format.
- video/mp4: MP4 video files.
- video/webm: WebM video format.

------------------------------------------------------------------------------------------------------------------------
Binary & Archive Formats:

- application/octet-stream: Raw binary data (used when the specific file type is unknown or a forced download is needed).
- application/zip: ZIP archive files.

------------------------------------------------------------------------------------------------------------------------
Special Wildcards (Mainly for the Accept Header):

- */*: Tells the server the client will accept any format.
- text/*: Accepts any text format (HTML, plain text, CSS, etc.).

=============================================================================================================================================================================
CONTENT NEGOTIATION
=============================================================================================================================================================================

- Content negotiation allows the client and server to determine an appropriate representation of a resource.
- A resource can have multiple representations.

Example:

Product Resource
│
├── JSON
├── XML
├── HTML
└── ....

- The client communicates its preferences using request headers.

------------------------------------------------------------------------------------------------------------------------
ACCEPT

- `Accept` specifies the media types that the client is willing to receive.

- Example:

Accept: application/json

- Multiple media types:

Accept: application/json, application/xml

- The client can specify preferences using quality values.

Accept: application/json, application/xml;q=0.8

- A higher quality value represents a higher preference.

------------------------------------------------------------------------------------------------------------------------
Accept-Language

- Specifies preferred response languages.

Example:

Accept-Language: en-US, en;q=0.9, hi;q=0.8

------------------------------------------------------------------------------------------------------------------------
Accept-Encoding

- Specifies content encodings that the client can handle.

Example:

Accept-Encoding: gzip, br

------------------------------------------------------------------------------------------------------------------------
Content-Type

- Indicates the actual media type of the message body.

Example:

Content-Type: application/json

------------------------------------------------------------------------------------------------------------------------
Content-Language

- Indicates the language of the representation being sent.

Example:

Content-Language: en-US

------------------------------------------------------------------------------------------------------------------------
Content-Encoding

- Indicates the encoding applied to the representation.

Example:

Content-Encoding: gzip

------------------------------------------------------------------------------------------------------------------------
Content Negotiation Flow

Request:

GET /products/100 HTTP/1.1
Accept: application/json, application/xml;q=0.8
Accept-Language: en-US
Accept-Encoding: gzip

Response:

HTTP/1.1 200 OK
Content-Type: application/json
Content-Language: en-US
Content-Encoding: gzip

Relationship:

Accept
→ Desired media types

Accept-Language
→ Desired languages

Accept-Encoding
→ Supported content encodings

Content-Type
→ Actual media type

Content-Language
→ Actual language

Content-Encoding
→ Applied content encoding

=============================================================================================================================================================================
HTTP STATELESSNESS & STATE MANAGEMENT:
=============================================================================================================================================================================

- HTTP is stateless.
- The server does not inherently maintain knowledge of previous HTTP requests simply because those requests came from the same client.

Example:

Request 1
│
▼
Server

Request 2
│
▼
Server

- The second request is independent from the first at the HTTP protocol level.
- Application-level mechanisms can associate multiple requests with the same user or client.

------------------------------------------------------------------------------------------------------------------------
Why HTTP is Stateless:

- Stateless communication allows each request to contain the information required to process it.
- The server does not need to inherently maintain protocol-level state for every previous request.
- This simplifies scaling because requests can be handled independently by different server instances when the application architecture supports it.

------------------------------------------------------------------------------------------------------------------------
State Management:

- Because HTTP is inherently a stateless protocol, The server treats every incoming request as if it is coming from a brand-new user and forgets it as soon as the response is sent.
- To create continuous user experiences (like staying logged in or keeping items in a shopping cart), developers must implement state management mechanisms on top of HTTP
- Here is how state is managed across HTTP, categorized by where the data is stored:

1. Client-Driven State Management (Sent with every request): These methods store data on the user's browser, and the browser automatically or manually attaches this data to subsequent HTTP requests

	- HTTP Cookies (Most Common)
	- Bearer Tokens (JWT)
	- URL Query Parameters

2. Server-Side State Management (The Session Pattern): Instead of passing all user data back and forth, the server stores the actual state in its own memory or a database, sending only a temporary reference to the client.

	- Cookie-Based Sessions
	- URL Rewriting

------------------------------------------------------------------------------------------------------------------------
						  HTTP Cookies
------------------------------------------------------------------------------------------------------------------------

- A Cookie is data stored by the browser and associated with a domain and cookie attributes.
- Cookies allow the browser to send applicable data with subsequent HTTP requests.
- Cookies are not inherently an authentication mechanism.
- They can contain:

  • Session identifiers
  • Authentication information
  • User preferences
  • Other application data

Example:

Server
│
│ Set-Cookie
▼
Browser
│
│ Cookie
▼
Server

------------------------------------------------------------------------------------------------------------------------
Set-Cookie - Response Header


- A server can instruct the browser to store a cookie using the `Set-Cookie` response header.

Example:

Set-Cookie: JSESSIONID=ABC123; Path=/; Secure; HttpOnly

- This represents one cookie:

  JSESSIONID
  → Cookie Name

  ABC123
  → Cookie Value

- The remaining values are attributes of the same cookie:

  Path=/
  Secure
  HttpOnly

- These attributes control how the browser handles the cookie.
- Multiple cookies are represented using multiple `Set-Cookie` headers:

Set-Cookie: JSESSIONID=ABC123; Path=/; Secure; HttpOnly
Set-Cookie: theme=dark; Path=/

------------------------------------------------------------------------------------------------------------------------
Cookie - Request Header


- The browser sends applicable stored cookies using the `Cookie` request header.

Example:
Cookie: JSESSIONID=ABC123; theme=dark

- The browser automatically includes applicable cookies according to the cookie's rules.
- Can send multiple cookies in the same Cookie header.

Cookie Flow:

Server
│
│ Set-Cookie
▼
Browser
│
│ Stores Cookie
▼
Browser
│
│ Cookie
▼
Server

------------------------------------------------------------------------------------------------------------------------
						   Bearer Tokens
------------------------------------------------------------------------------------------------------------------------

- A token can be sent with requests to represent authentication or other application-level information.
- A bearer token can be a JWT, an Opaque Token (Random string), an API Key or an OAuth2 Access Token

Example:

Authorization: Bearer ABC123...

- The token can allow the server to associate the request with an authenticated identity or permissions.

------------------------------------------------------------------------------------------------------------------------
						   URL Query Parameters
------------------------------------------------------------------------------------------------------------------------

- State is appended directly to the end of the URL (e.g., /profile?user=john&theme=dark).
- Best for: Sharing links that need to preserve a specific view or search filter.

------------------------------------------------------------------------------------------------------------------------
							Sessions
------------------------------------------------------------------------------------------------------------------------

- A session allows the server to maintain state associated with a client across multiple requests.

Typical flow:

Login
│
▼
Server creates Session
│
▼
Session ID sent to client
│
▼
Client sends Session ID
│
▼
Server identifies Session

------------------------------------------------------------------------------------------------------------------------
						  URL Rewriting
------------------------------------------------------------------------------------------------------------------------

- What it is: A backup mechanism that appends the Session ID directly onto the end of web links.
- Purpose: Used as a fallback when a paranoid user explicitly disables cookies in their browser settings.
- Behind the scenes: Links transform from /dashboard into /dashboard;jsessionid=abc789. The server reads the URL path to reconstruct the session state.


=============================================================================================================================================================================
AUTHENTICATION MECHANISMS
=============================================================================================================================================================================

- Authentication establishes the identity associated with a request.
- HTTP provides mechanisms for carrying authentication information.

------------------------------------------------------------------------------------------------------------------------
WWW-AUTHENTICATE


- A server can indicate that authentication is required using the `WWW-Authenticate` response header.
- `WWW-Authenticate` and `Authorization` have a direct, cause-and-effect relationship.

The 4-Step Relationship (How they talk to each other):

    - Client->>Server: 	1. GET /dashboard (No credentials)
    - Server->>Client: 	2. HTTP 401 Unauthorized <br> [WWW-Authenticate: Basic realm="Secure Site"] / [WWW-Authenticate: Bearer realm="API Access", error="invalid_token"]
    - Client->>Server: 	3. GET /dashboard <br> [Authorization: Basic dXNlcjpwYXNz] / [Authorization: Bearer dXNlcjpwYXNz]
    - Server->>Client: 	4. HTTP 200 OK (Access Granted)

------------------------------------------------------------------------------------------------------------------------
Basic Authentication


- Basic Authentication sends username and password credentials through the `Authorization` header.

Example: 

Authorization: Basic <credentials>

- The credentials are based on: username:password
- The resulting value is Base64 encoded.
- Base64 is encoding, not encryption.
- Therefore Basic Authentication should be used over HTTPS/TLS so that the credentials are protected while travelling over the network.
- The credentials in Basic authentication are sent to the server in every request followed by server validation

------------------------------------------------------------------------------------------------------------------------
Bearer Token Authentication


- A Bearer token can be a JWT, Opaque tokens (Random strings), API Keys or OAuth Access Tokens.
- After User Credentials validation by server, the server creates a Bearer Token and it is sent to the Client via:

---------------------------------------------
Response Body (Most Common for REST APIs):

Example HTTP Response:

HTTP/1.1 200 OK
Content-Type: application/json

{
  "accessToken":"eyJhbGciOiJIUzI1NiIs...",
  "refreshToken":"..."
}

- The client extracts the token from the response body and stores it (memory, local storage, session storage, etc., depending on the application's design).
- The Subsequent requests by client uses Authorization header to send the Token back to the Server

Example:
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...

---------------------------------------------
Set-Cookie (Also Very Common):

Example HTTP Response:

HTTP/1.1 200 OK
Set-Cookie: accessToken=eyJhbGciOi...; HttpOnly; Secure; SameSite=Lax

- The browser stores the cookie automatically.
- Subsequent requests ->	Cookie: accessToken=eyJhbGciOi...
- The client does not send ->	Authorization: Bearer ...
- Many modern applications use JWT inside an HttpOnly cookie instead of using the Authorization header.


------------------------------------------------------------------------------------------------------------------------
Session-Based Authentication


- After User Credentials validation, a server creates a session object with user state and sends its identifier to the client using a cookie.

Example:
Set-Cookie: JSESSIONID=ABC123; Secure; HttpOnly

- The browser automatically sends the cookie in the subsequent applicable requests.

Example:
Cookie: JSESSIONID=ABC123

- The server uses the session identifier to identify the associated session.

------------------------------------------------------------------------------------------------------------------------
How are user credentials passed to the Server?:


- In Basic Authentication, the credentials are sent to the server directly in the "Authorization: Basic ..." header
- In Bearer Token and Session based Authentications, the credentials are sent to the server in the request body
- Example:

POST /login

{
    "username":"sai",
    "password":"mypassword"
}



User enters credentials
          │
          ▼
POST /login
(username + password)
          │
          ▼
Server validates
          │
          ├── Session → Set-Cookie
          │
          └── Token → Access Token


After that:
Basic Authentication → Client continues sending username/password with every request.
Bearer Authentication → Client sends the bearer token.
Session Authentication → Browser sends the session cookie.

------------------------------------------------------------------------------------------------------------------------

401 vs 403

401 Unauthorized

→ Authentication is missing or invalid.

403 Forbidden

→ Access to the requested resource or operation is refused.

=============================================================================================================================================================================
CSRF — CROSS-SITE REQUEST FORGERY
=================================

* CSRF is a security problem where an attacker causes a user's browser to make an unintended request to another application.

* It is particularly relevant when authentication information such as cookies is automatically included with requests.

Conceptually:

Attacker / Other Website
│
│ Causes Browser to Send Request
▼
Target Application
│
│ Authentication Cookie
▼
Authenticated Request

* CSRF protection can use mechanisms such as:

  • CSRF Tokens
  • Cookie attributes

* These mechanisms help distinguish legitimate requests from forged cross-site requests.

CORS — CROSS-ORIGIN RESOURCE SHARING
====================================

* CORS controls how browsers permit a web application running on one origin to interact with resources on another origin.

Example:

https://frontend.example.com
│
│ Browser Request
▼
https://api.example.com

* The browser can identify the requesting origin using the `Origin` header.

Example:

Origin: https://frontend.example.com

* The server can specify whether the origin is allowed using:

Access-Control-Allow-Origin: https://frontend.example.com

* The browser evaluates the response according to the CORS policy.
* CORS is primarily enforced by the browser.

ACCESS-CONTROL-ALLOW-ORIGIN
===========================

* Specifies which origin is permitted to access the response.

Access-Control-Allow-Origin: https://frontend.example.com

=============================================================================================================================================================================
CORS PREFLIGHT
==============

* For certain cross-origin requests, the browser first sends an `OPTIONS` request to determine whether the actual request is permitted.

Example:

OPTIONS /orders HTTP/1.1
Origin: https://frontend.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: Authorization, Content-Type

* The server can respond with:

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://frontend.example.com
Access-Control-Allow-Methods: POST, GET
Access-Control-Allow-Headers: Authorization, Content-Type

* The browser evaluates the response before sending the actual request.

=============================================================================================================================================================================
HTTP CACHING & CONDITIONAL REQUESTS
=============================================================================================================================================================================

- HTTP caching allows previously received responses to be stored and reused.
- HTTP caches can exist at different locations:

  • Browser
  • CDN
  • Proxy

- Caching can reduce:

  • Network traffic
  • Latency
  • Server processing
  • Bandwidth usage

------------------------------------------------------------------------------------------------------------------------
Cache-Control

- `Cache-Control` provides caching directives to HTTP caches.

Example:
Cache-Control: max-age=3600

- Cache-Control can apply to different HTTP caches, not only browser caches.

------------------------------------------------------------------------------------------------------------------------
max-age

Example:
Cache-Control: max-age=3600

- Specifies how long the response can remain fresh.

------------------------------------------------------------------------------------------------------------------------
no-store

Example:
Cache-Control: no-store

- Instructs caches not to store the response.

------------------------------------------------------------------------------------------------------------------------
no-cache

Example:
Cache-Control: no-cache

- Does not mean that the response cannot be stored.

- It means that a stored response must be revalidated before reuse.

Therefore:

no-store
→ Do not store

no-cache
→ May store, but must revalidate before reuse

------------------------------------------------------------------------------------------------------------------------
CACHE FRESHNESS AND REVALIDATION

- A cached response isn't necessarily usable forever.
- It can be either fresh or require revalidation.

For example: 
Cache-Control: max-age=3600

- Means, the cached data is fresh for 3600 seconds.
- While the response is fresh, the cache can generally reuse it without contacting the origin server, subject to the applicable caching rules.


Fresh Response:

Request
│
▼
Cache
│
│ Fresh
▼
Use Cached Response


The Problem With Expired Cache:

- Suppose, after one hour the cached response becomes stale
- The browser now needs to determine: "Has the resource changed on the server?"
- One option would be: GET /product/100
- and download the entire response again.
- But HTTP provides a more efficient mechanism: Conditional Requests

------------------------------------------------------------------------------------------------------------------------
ETag


------------------------------------------------------------------------------------------------------------------------
Last-Modified


------------------------------------------------------------------------------------------------------------------------
Conditional Requests

- Conditional requests allow the client/cache to ask the server whether the cached representation is still valid, instead of blindly downloading the resource again.
- The two important mechanisms are: ETag, Last-Modified and their corresponding request headers


ETag:
- identifies a particular representation of a resource.

Example:
ETag: "abc123"

- The cache can store the representation together with the ETag.



Last-Modified:
- indicates when a representation was last modified.

Example:
Last-Modified: Sat, 01 Aug 2026 10:00:00 GMT



ETag-based validation:

GET /profile HTTP/1.1
If-None-Match: "abc123"



Last-Modified-based validation:

GET /profile HTTP/1.1
If-Modified-Since: Sat, 01 Aug 2026 10:00:00 GMT

------------------------------------------------------------------------------------------------------------------------

304 Not Modified

- `304 Not Modified` indicates that the cached representation is still valid.

Flow:

Client Cache
│
│ Conditional Request
▼
Server
│
│ 304 Not Modified
▼
Client uses existing cached representation

- If the representation has changed, the server returns the updated representation instead.

Example:

HTTP/1.1 200 OK
ETag: "xyz789"

<new representation>

HTTP REDIRECTS
=============================================================================================================================================================================

- A redirect tells the client that the requested resource or operation should be handled at another location.
- Redirect responses generally contain:

  • 3xx Status Code
  • Location Header

Example:

HTTP/1.1 301 Moved Permanently
Location: https://example.com/new-page

Client
│
│ Request
▼
Server
│
│ 3xx + Location
▼
Client
│
│ New Request
▼

------------------------------------------------------------------------------------------------------------------------

Location

- The `Location` header identifies the target of the redirect.

Example:

Location: https://example.com/products

- It can also contain a relative location:

Location: /products

------------------------------------------------------------------------------------------------------------------------

301 — Moved Permanently

- Indicates that a resource has permanently moved.

Example:

HTTP/1.1 301 Moved Permanently
Location: /new-resource

------------------------------------------------------------------------------------------------------------------------

302 — Found

- Indicates a temporary redirect.

Example:

HTTP/1.1 302 Found
Location: /temporary-resource

------------------------------------------------------------------------------------------------------------------------

303 — See Other

- Indicates that the client should retrieve the result from another URI, commonly using GET.

Typical flow:

POST
↓
303 See Other
↓
GET

------------------------------------------------------------------------------------------------------------------------

307 — Temporary Redirect

- Indicates a temporary redirect while preserving the original HTTP method and request body.

Example:

POST /payment
│
▼
307 Temporary Redirect
│
▼
POST /new-payment

------------------------------------------------------------------------------------------------------------------------

308 — Permanent Redirect

- Indicates a permanent redirect while preserving the original HTTP method and request body.

Example:

POST /old-payment
│
▼
308 Permanent Redirect
│
▼
POST /new-payment
