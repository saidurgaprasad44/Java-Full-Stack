===============================================================================================================================================================================
State Management:
===============================================================================================================================================================================


Because raw HTTP is 100% stateless, servers have no natural memory. State Management is the collective set of workarounds developers use to remember a user across multiple page clicks.


Cookies:
- What they are: Tiny key-value string files stored directly inside the browser's local memory to identify the users and remember their preferences.
- Purpose: Used for light, persistent client-side tracking (e.g., remembering a user's dark-mode preference or shopping cart ID).
- Behind the scenes: The server sets them using the Set-Cookie header. The browser automatically stores them and silently attaches them to the Cookie header of every single subsequent request to that exact domain.


Sessions:
- What they are: A secure data storage area kept entirely on the server side (RAM or database).
- Purpose: Used to hold highly sensitive or heavy data (like login user states, user privileges, or checkout forms).
- Behind the scenes (Java Ecosystem): When a user logs in, Java creates an HttpSession object and assigns it a unique text string called a JSESSIONID. The server passes this ID to the browser as a cookie. The browser doesn't see your data; it only holds the luggage ticket (JSESSIONID) to claim the data on the server.


URL Rewriting:
- What it is: A backup mechanism that appends the Session ID directly onto the end of web links.
- Purpose: Used as a fallback when a paranoid user explicitly disables cookies in their browser settings.
- Behind the scenes: Links transform from /dashboard into /dashboard;jsessionid=abc789. The server reads the URL path to reconstruct the session state.


Hidden Form Fields:
- What they are: Invisible inputs embedded inside an HTML data form (<input type="hidden" name="userId" value="42">).
- Purpose: Used to transiently pass contextual values from page to page during complex forms. The data is hidden from view on the screen, but it is sent directly to the server payload when the user hits submit.


------------------------------------------------------------------------------------------------------------------------
TRACE

- TRACE is used for diagnostic purposes to perform a loop-back of the request.
- It is generally disabled in production environments because of security considerations.

------------------------------------------------------------------------------------------------------------------------
CONNECT

- CONNECT is used to establish a tunnel to the server identified by the target.
- It is commonly used with HTTP proxies.






































=============================================================================================================================================================================
										HTTP PROTOCOL
=============================================================================================================================================================================

- HTTP (HyperText Transfer Protocol) is an application-layer protocol used for communication between systems over a network.
- HTTP follows a Request-Response communication model:

			─────────── ( HTTP Request Message ) ───────────►
[ Client / Browser ]									[ Server / Spring Boot ]
			◄────────── ( HTTP Response Message ) ───────────

- HTTP communication can occur between:

  • Client → Server
  • Server → Server
  • Service → Service

Example:

Client
│
│ HTTP Request
▼
Order Service
│
│ HTTP Request
▼
Payment Service

=============================================================================================================================================================================
HTTP REQUEST
=============================================================================================================================================================================

- An HTTP Request contains the information required by the receiver to process the request.
- An HTTP Request consists of:

• Request Line
• Request Headers
• Empty Line
• Request Body (Optional)


[ REQUEST LINE ]  	->  	POST   /api/v1/users/4521/posts?draft=false HTTP/1.1
			        └──┘  └────────┘└──┘└───────────┘  └────┘
			        Method       Path   PathVar     Query       Version



[ REQUEST HEADERS ]     ->  	Host: www.example.com					<- Key: Value pairs
                      		Content-Type: application/json
                      		Authorization: Bearer xyz123
				Cookie: session_id=xyz123; theme=dark; logged_in=true

-----------------------------------Empty Line----------------------------------------

[ REQUEST BODY ]  	->  	{
                        		"filename": "invoice.pdf",
                        		"size": 2048
                      		}


Example:

POST /users HTTP/1.1
Host: example.com
Content-Type: application/json
Accept: application/json

{
"name": "Sai"
}


------------------------------------------------------------------------------------------------------------------------
Request Line


- The Request Line contains:

	• HTTP Method: The verb telling the server what action to perform (GET, POST, PUT, DELETE).
	• Request Target: The request target is the specific resource, path, or URL the client wants to reach on the server.
	• HTTP Version: Tells the server which version of the web protocol the browser is using (e.g., HTTP/1.1 or HTTP/2)

Example:

POST /users HTTP/1.1


POST
→ HTTP Method

/users
→ Request Target

HTTP/1.1
→ HTTP Version

------------------------------------------------------------------------------------------------------------------------
Request Headers

- HTTP Headers provide additional information and instructions associated with an HTTP request or response.
- General format:

Header-Name: Header-Value


Examples:

Host: example.com
Content-Type: application/json
Accept: application/json
Authorization: Bearer abc123
Cookie: JSESSIONID=ABC123

- Headers are part of the HTTP protocol and are represented using a header name and value.
- They are not JSON objects.
- Different headers are defined to solve different communication requirements such as: 

  • Authentication
  • Caching
  • Cookies
  • Content negotiation
  • Conditional requests
  • Redirection
  • Cross-origin communication
  • Content representation

------------------------------------------------------------------------------------------------------------------------
Empty Line: 

- A blank line that separates the headers from the body.

------------------------------------------------------------------------------------------------------------------------
Request Body:

- The Request Body contains data sent as part of the HTTP request.
- It can be raw text, a JSON object, XML, HTML, or binary data (like an image file or PDF).
- A request body is commonly used with:

  • POST
  • PUT
  • PATCH

- The `Content-Type` header identifies the format of the request body.

=============================================================================================================================================================================
HTTP RESPONSE
=============================================================================================================================================================================

- An HTTP Response contains the result of processing an HTTP request.
- An HTTP Response consists of:

• Response Status Line
• Response Headers
• Empty Line
• Response Body (Optional)


[ STATUS LINE ]  	->  	HTTP/1.1   200   OK
				└────┘   └─┘   └┘
				Version   Code  Reason Phrase

[ RESPONSE HEADERS ]    ->  	Content-Type: application/json
				Set-Cookie: JSESSIONID=abc789; Path=/ ;HttpOnly
				Cache-Control: no-cache

--------------------------------Empty Line-------------------------------------

[ RESPONSE BODY ]  	->  	{
					"status": "success",
					"message": "File uploaded successfully"
				}


Example:

HTTP/1.1 200 OK
Content-Type: application/json

{
"id": 100,
"name": "Laptop"
}

------------------------------------------------------------------------------------------------------------------------
Response Status Line:

- The very first line returned by the server containing the structural health report of the action:
- The Status Line contains:

  • HTTP Version: Confirms the protocol standard used to send the data back.
  • Status Code: The 3-digit number telling the client if the request succeeded or failed.
  • Reason Phrase: A human-readable text description matching the code (e.g., "OK", "Not Found").


Example:

HTTP/1.1 200 OK



HTTP/1.1
→ HTTP Version

200
→ Status Code

OK
→ Reason Phrase

HTTP Status Code categories:

1xx → Informational
2xx → Successful
3xx → Redirection
4xx → Client Error
5xx → Server Error

------------------------------------------------------------------------------------------------------------------------
Response Headers:

- Background metadata sent by the server to instruct the browser how to handle the incoming payload.

Examples:

Content-Type: application/json
Set-Cookie: ID=value

------------------------------------------------------------------------------------------------------------------------
Response Body:

- The actual data requested by the client.
- Format: HTML text files for web page layouts, JSON data arrays for modern REST APIs, or raw byte streams for downloading files (Images/PDFs).

=============================================================================================================================================================================
HTTP METHODS
=============================================================================================================================================================================

- HTTP Methods indicate the intended operation associated with a request.

------------------------------------------------------------------------------------------------------------------------
GET

- GET is used to retrieve a resource.
- GET requests normally do not contain a request body.


Example:

GET /users/100 HTTP/1.1


------------------------------------------------------------------------------------------------------------------------
POST

- POST is used to submit data or request processing that may create a resource or perform a state-changing operation.

Example:

POST /users HTTP/1.1
Content-Type: application/json

{
"name": "Sai"
}

------------------------------------------------------------------------------------------------------------------------
PUT

- PUT is used to create or completely replace the target resource with the supplied representation.


Example:

PUT /users/100 HTTP/1.1
Content-Type: application/json

{
"id": 100,
"name": "Sai"
}

------------------------------------------------------------------------------------------------------------------------
PATCH

- PATCH is used to partially modify a resource.

Example:

PATCH /users/100 HTTP/1.1
Content-Type: application/json

{
"name": "Sai Kumar"
}

------------------------------------------------------------------------------------------------------------------------
DELETE

- DELETE is used to request deletion of a resource.

Example:

DELETE /users/100 HTTP/1.1

------------------------------------------------------------------------------------------------------------------------

HEAD

- HEAD is similar to GET, but the server returns the response headers without the response body.
- HEAD is useful when the client needs information about a resource without downloading its complete representation.

------------------------------------------------------------------------------------------------------------------------

OPTIONS

- OPTIONS is used to determine the communication options supported by a target resource.
- OPTIONS is commonly used by browsers for CORS preflight requests.

Example:

OPTIONS /users HTTP/1.1


------------------------------------------------------------------------------------------------------------------------
Safe Methods

- A safe HTTP method is a method intended only for retrieving information and not for requesting a state-changing operation on the target resource.

Safe methods include:

GET
HEAD
OPTIONS

- Safe does not mean that the request can never cause any side effects on the server.
- It means that the method's intended semantics are read-only with respect to the target resource.

------------------------------------------------------------------------------------------------------------------------
Idempotent Methods

- An HTTP method is idempotent when making the same request multiple times has the same intended effect on the server as making it once.

Example:

DELETE /users/100

First request:

text
User exists
   ↓
User is deleted


Repeated request:

text
User already deleted
   ↓
Resource remains deleted


- The final intended state is the same.

Idempotent methods:

GET
HEAD
OPTIONS
PUT
DELETE

- PATCH may or may not be idempotent depending on the operation.
- POST is generally non-idempotent.

=============================================================================================================================================================================
HTTP STATUS CODES
=============================================================================================================================================================================

- HTTP Status Codes indicate the result of processing an HTTP request.

The five categories are:

1xx → Informational
2xx → Successful
3xx → Redirection
4xx → Client Error
5xx → Server Error

------------------------------------------------------------------------------------------------------------------------

1xx — Informational

- Indicates that the request has been received and processing can continue.

Example:

100 Continue

------------------------------------------------------------------------------------------------------------------------

2xx — Successful

- Indicates that the request was successfully received, understood and processed.

Important status codes:

200 OK
→ Request successfully processed.

201 Created
→ A new resource was created.

202 Accepted
→ Request was accepted for processing, but processing may not yet be complete.

204 No Content
→ Request successfully processed, but there is no response body.

------------------------------------------------------------------------------------------------------------------------

3xx — Redirection

- Indicates that the client needs to take additional action or that the resource is available at another location.

Important status codes:

301 Moved Permanently
→ Permanent redirect.

302 Found
→ Temporary redirect.

303 See Other
→ Client should retrieve the result from another URI, commonly using GET.

307 Temporary Redirect
→ Temporary redirect while preserving the HTTP method and request body.

308 Permanent Redirect
→ Permanent redirect while preserving the HTTP method and request body.

------------------------------------------------------------------------------------------------------------------------

4xx — Client Error

- Indicates that the request contains a problem from the client's side.

Important status codes:

400 Bad Request
→ Request is invalid or malformed.

401 Unauthorized
→ Authentication is missing or invalid.

403 Forbidden
→ Access to the requested resource or operation is refused.

404 Not Found
→ Requested resource could not be found.

405 Method Not Allowed
→ HTTP method is not supported for the target resource.

409 Conflict
→ Request conflicts with the current state of the resource.

429 Too Many Requests
→ Client has sent too many requests within a given period.

------------------------------------------------------------------------------------------------------------------------

5xx — Server Error

- Indicates that the server failed to successfully process an otherwise valid request.

Important status codes:

500 Internal Server Error
→ Generic server-side error.

502 Bad Gateway
→ A server acting as a gateway or proxy received an invalid response from an upstream server.

503 Service Unavailable
→ Server is currently unable to handle the request.

504 Gateway Timeout
→ A gateway or proxy did not receive a timely response from an upstream server.

=============================================================================================================================================================================
HTTP STATELESSNESS
=============================================================================================================================================================================

- HTTP is stateless.

- The server does not inherently maintain knowledge of previous HTTP requests simply because those requests came from the same client.

Example:

Request 1
│
▼
Server

Request 2
│
▼
Server

- The second request is independent from the first at the HTTP protocol level.

- Application-level mechanisms can associate multiple requests with the same user or client.

------------------------------------------------------------------------------------------------------------------------

Why HTTP is Stateless

- Stateless communication allows each request to contain the information required to process it.

- The server does not need to inherently maintain protocol-level state for every previous request.

- This simplifies scaling because requests can be handled independently by different server instances when the application architecture supports it.

------------------------------------------------------------------------------------------------------------------------

Cookies

- Cookies allow the browser to store data and send applicable data with subsequent requests.

Example:

Server
│
│ Set-Cookie
▼
Browser
│
│ Cookie
▼
Server

Example:

Set-Cookie: JSESSIONID=ABC123

Subsequent request:

Cookie: JSESSIONID=ABC123

------------------------------------------------------------------------------------------------------------------------

Sessions

- A session allows the server to maintain state associated with a client across multiple requests.

Typical flow:

Login
│
▼
Server creates Session
│
▼
Session ID sent to client
│
▼
Client sends Session ID
│
▼
Server identifies Session

------------------------------------------------------------------------------------------------------------------------

Tokens

- A token can be sent with requests to represent authentication or other application-level information.

Example:

Authorization: Bearer ABC123

- The token can allow the server to associate the request with an authenticated identity or permissions.

=============================================================================================================================================================================
AUTHENTICATION MECHANISMS
=============================================================================================================================================================================

- Authentication establishes the identity associated with a request.

- HTTP provides mechanisms for carrying authentication information.

------------------------------------------------------------------------------------------------------------------------

Basic Authentication

- Basic Authentication sends username and password credentials through the `Authorization` header.

Example:

Authorization: Basic <credentials>

- The credentials are Base64 encoded.

- Base64 is encoding, not encryption.

- HTTPS/TLS should be used to protect the credentials during transmission.

------------------------------------------------------------------------------------------------------------------------

Bearer Authentication

- Bearer Authentication sends a token through the `Authorization` header.

Example:

Authorization: Bearer <token>

- A JWT can be used as a Bearer token.

- Bearer authentication itself does not require the token to be a JWT.

------------------------------------------------------------------------------------------------------------------------

Session-Based Authentication

- A server can create a session and send its identifier using a cookie.

Example:

Set-Cookie: JSESSIONID=ABC123; Secure; HttpOnly

- The browser sends the cookie with subsequent applicable requests.

Example:

Cookie: JSESSIONID=ABC123

- The server uses the session identifier to identify the associated session.

------------------------------------------------------------------------------------------------------------------------

Authentication vs Authorization

Authentication

→ Establishes who is making the request.

Authorization

→ Determines what the authenticated requester is allowed to access or perform.

------------------------------------------------------------------------------------------------------------------------

401 vs 403

401 Unauthorized

→ Authentication is missing or invalid.

403 Forbidden

→ Access to the requested resource or operation is refused.

=============================================================================================================================================================================
HTTP CACHING & CONDITIONAL REQUESTS
=============================================================================================================================================================================

- HTTP caching allows previously received responses to be stored and reused.

- HTTP caches can exist at different locations:

  • Browser
  • CDN
  • Proxy

- Caching can reduce:

  • Network traffic
  • Latency
  • Server processing
  • Bandwidth usage

------------------------------------------------------------------------------------------------------------------------

Cache-Control

- `Cache-Control` provides caching directives to HTTP caches.

Example:

Cache-Control: max-age=3600

- Cache-Control can apply to different HTTP caches, not only browser caches.

------------------------------------------------------------------------------------------------------------------------

max-age

Example:

Cache-Control: max-age=3600

- Specifies how long the response can remain fresh.

------------------------------------------------------------------------------------------------------------------------

no-store

Example:

Cache-Control: no-store

- Instructs caches not to store the response.

------------------------------------------------------------------------------------------------------------------------

no-cache

Example:

Cache-Control: no-cache

- Does not mean that the response cannot be stored.

- It means that a stored response must be revalidated before reuse.

Therefore:

no-store
→ Do not store

no-cache
→ May store, but must revalidate before reuse

------------------------------------------------------------------------------------------------------------------------

ETag

- `ETag` identifies a particular representation of a resource.

Example:

ETag: "abc123"

- The cache can store the representation together with the ETag.

------------------------------------------------------------------------------------------------------------------------

Last-Modified

- `Last-Modified` indicates when a representation was last modified.

Example:

Last-Modified: Sat, 01 Aug 2026 10:00:00 GMT

------------------------------------------------------------------------------------------------------------------------

Conditional Requests

- Conditional requests allow the client/cache to ask the server whether the cached representation is still valid.

ETag-based validation:

GET /profile HTTP/1.1
If-None-Match: "abc123"

Last-Modified-based validation:

GET /profile HTTP/1.1
If-Modified-Since: Sat, 01 Aug 2026 10:00:00 GMT

------------------------------------------------------------------------------------------------------------------------

304 Not Modified

- `304 Not Modified` indicates that the cached representation is still valid.

Flow:

Client Cache
│
│ Conditional Request
▼
Server
│
│ 304 Not Modified
▼
Client uses existing cached representation

- If the representation has changed, the server returns the updated representation instead.

Example:

HTTP/1.1 200 OK
ETag: "xyz789"

<new representation>

------------------------------------------------------------------------------------------------------------------------

ETag vs Last-Modified

ETag

→ Identifies a representation.

If-None-Match

→ Sends the ETag for conditional validation.

Last-Modified

→ Identifies the modification time.

If-Modified-Since

→ Sends the modification time for conditional validation.

=============================================================================================================================================================================
CONTENT NEGOTIATION
=============================================================================================================================================================================

- Content negotiation allows the client and server to determine an appropriate representation of a resource.

- A resource can have multiple representations.

Example:

Product Resource
│
├── JSON
├── XML
└── HTML

- The client communicates its preferences using request headers.

------------------------------------------------------------------------------------------------------------------------

Accept

- `Accept` specifies the media types that the client is willing to receive.

Example:

Accept: application/json

Multiple media types:

Accept: application/json, application/xml

- Preferences can be specified using quality values.

Example:

Accept: application/json, application/xml;q=0.8

------------------------------------------------------------------------------------------------------------------------

Accept-Language

- Specifies preferred response languages.

Example:

Accept-Language: en-US, en;q=0.9, hi;q=0.8

------------------------------------------------------------------------------------------------------------------------

Accept-Encoding

- Specifies content encodings that the client can handle.

Example:

Accept-Encoding: gzip, br

------------------------------------------------------------------------------------------------------------------------

Content-Type

- Indicates the actual media type of the message body.

Example:

Content-Type: application/json

------------------------------------------------------------------------------------------------------------------------

Content-Language

- Indicates the language of the representation being sent.

Example:

Content-Language: en-US

------------------------------------------------------------------------------------------------------------------------

Content-Encoding

- Indicates the encoding applied to the representation.

Example:

Content-Encoding: gzip

------------------------------------------------------------------------------------------------------------------------

Accept vs Content-Type

Accept

→ Representation the client is willing to receive.

Content-Type

→ Representation format of the actual message body.

Example:

GET /products/100 HTTP/1.1
Accept: application/json

Response:

HTTP/1.1 200 OK
Content-Type: application/json

------------------------------------------------------------------------------------------------------------------------

Content Negotiation Flow

Request:

GET /products/100 HTTP/1.1
Accept: application/json, application/xml;q=0.8
Accept-Language: en-US
Accept-Encoding: gzip

Response:

HTTP/1.1 200 OK
Content-Type: application/json
Content-Language: en-US
Content-Encoding: gzip

Relationship:

Accept
→ Desired media types

Accept-Language
→ Desired languages

Accept-Encoding
→ Supported content encodings

Content-Type
→ Actual media type

Content-Language
→ Actual language

Content-Encoding
→ Applied content encoding

=============================================================================================================================================================================
COOKIES
=======

* A Cookie is data stored by the browser and associated with a domain and cookie attributes.
* Cookies allow information to be carried between multiple HTTP requests.

=============================================================================================================================================================================
SET-COOKIE
==========

* A server can instruct the browser to store a cookie using the `Set-Cookie` response header.

Example:

Set-Cookie: JSESSIONID=ABC123; Path=/; Secure; HttpOnly

* This represents one cookie:

  JSESSIONID
  → Cookie Name

  ABC123
  → Cookie Value

* The remaining values are attributes of the same cookie:

  Path=/
  Secure
  HttpOnly

* These attributes control how the browser handles the cookie.

=============================================================================================================================================================================
MULTIPLE COOKIES
================

* Multiple cookies are represented using multiple `Set-Cookie` headers.

Example:

Set-Cookie: JSESSIONID=ABC123; Path=/; Secure; HttpOnly
Set-Cookie: theme=dark; Path=/

* The above response sets two separate cookies.

=============================================================================================================================================================================
COOKIE REQUEST HEADER
=====================

* The browser sends applicable stored cookies using the `Cookie` request header.

Example:

Cookie: JSESSIONID=ABC123; theme=dark

* The browser automatically includes applicable cookies according to the cookie's rules.

Cookie Flow:

Server
│
│ Set-Cookie
▼
Browser
│
│ Stores Cookie
▼
Browser
│
│ Cookie
▼
Server

* Cookies are not inherently an authentication mechanism.
* They can contain:

  • Session identifiers
  • Authentication information
  • User preferences
  • Other application data

AUTHENTICATION
==============

* Authentication establishes the identity associated with a request.

* HTTP provides mechanisms for carrying authentication information.

=============================================================================================================================================================================
BASIC AUTHENTICATION
====================

* Basic Authentication sends credentials using the `Authorization` header.

Example:

Authorization: Basic <credentials>

* The credentials are based on:

username:password

* The resulting value is Base64 encoded.

* Base64 is encoding, not encryption.

* Therefore Basic Authentication should be used over HTTPS/TLS so that the credentials are protected while travelling over the network.

=============================================================================================================================================================================
WWW-AUTHENTICATE
================

* A server can indicate that authentication is required using the `WWW-Authenticate` response header.

Example:

HTTP/1.1 401 Unauthorized
WWW-Authenticate: Basic realm="example"

* The client can then provide the credentials using:

Authorization: Basic <credentials>

Relationship:

WWW-Authenticate
→ Server indicates an authentication scheme

Authorization
→ Client provides authentication credentials

=============================================================================================================================================================================
BEARER AUTHENTICATION
=====================

* Bearer Authentication sends a token using the `Authorization` header.

Example:

Authorization: Bearer ABC123

* The token represents the authentication credential.

* Bearer Authentication and JWT are not the same concept.

  JWT
  → A token format

  Bearer
  → An authentication scheme for sending a token

* A JWT can be used as a Bearer token, but a Bearer token does not have to be a JWT.

=============================================================================================================================================================================
SESSION-BASED AUTHENTICATION
============================

* A server can create a server-side session and send a session identifier to the browser using a cookie.

Example:

Set-Cookie: JSESSIONID=ABC123; Secure; HttpOnly

* The browser stores the cookie.

* Subsequent applicable requests can contain:

Cookie: JSESSIONID=ABC123

* The server uses the session identifier to identify the corresponding server-side session.

Flow:

Login Request
│
▼
Server creates session
│
▼
Set-Cookie: JSESSIONID=ABC123
│
▼
Browser stores cookie
│
▼
Subsequent Request
│
▼
Cookie: JSESSIONID=ABC123
│
▼
Server identifies session

=============================================================================================================================================================================
AUTHORIZATION HEADER VS COOKIE HEADER
=====================================

Authorization:

Authorization: Bearer ABC123

* Carries authentication credentials according to an HTTP authentication scheme.

Cookie:

Cookie: JSESSIONID=ABC123

* Carries cookies stored by the browser.

* A cookie can contain a session identifier used for authentication, but the Cookie mechanism itself is not an authentication mechanism.

=============================================================================================================================================================================
AUTHENTICATION VS AUTHORIZATION
===============================

Authentication:

→ Establishes who is making the request.

Authorization:

→ Determines what the authenticated requester is allowed to access or perform.

Example:

Authenticated User
│
├── View Profile
├── Create Order
└── Cannot Access Admin Resources

=============================================================================================================================================================================
401 UNAUTHORIZED
================

* `401 Unauthorized` generally indicates that authentication credentials are missing or invalid.

Example:

HTTP/1.1 401 Unauthorized

=============================================================================================================================================================================
403 FORBIDDEN
=============

* `403 Forbidden` indicates that access to the requested resource or operation is refused.

Example:

HTTP/1.1 403 Forbidden

Common distinction:

401
→ Authentication is missing or invalid

403
→ Access is refused

=============================================================================================================================================================================
CSRF — CROSS-SITE REQUEST FORGERY
=================================

* CSRF is a security problem where an attacker causes a user's browser to make an unintended request to another application.

* It is particularly relevant when authentication information such as cookies is automatically included with requests.

Conceptually:

Attacker / Other Website
│
│ Causes Browser to Send Request
▼
Target Application
│
│ Authentication Cookie
▼
Authenticated Request

* CSRF protection can use mechanisms such as:

  • CSRF Tokens
  • Cookie attributes

* These mechanisms help distinguish legitimate requests from forged cross-site requests.

=============================================================================================================================================================================
CORS — CROSS-ORIGIN RESOURCE SHARING
====================================

* CORS controls how browsers permit a web application running on one origin to interact with resources on another origin.

Example:

https://frontend.example.com
│
│ Browser Request
▼
https://api.example.com

* The browser can identify the requesting origin using the `Origin` header.

Example:

Origin: https://frontend.example.com

* The server can specify whether the origin is allowed using:

Access-Control-Allow-Origin: https://frontend.example.com

* The browser evaluates the response according to the CORS policy.
* CORS is primarily enforced by the browser.

=============================================================================================================================================================================
ORIGIN
======

* The `Origin` request header identifies the origin from which a browser request originated.

Example:

Origin: https://frontend.example.com

An origin consists of:

Scheme
Host
Port

=============================================================================================================================================================================
ACCESS-CONTROL-ALLOW-ORIGIN
===========================

* Specifies which origin is permitted to access the response.

Example:

Access-Control-Allow-Origin: https://frontend.example.com

=============================================================================================================================================================================
CORS PREFLIGHT
==============

* For certain cross-origin requests, the browser first sends an `OPTIONS` request to determine whether the actual request is permitted.

Example:

OPTIONS /orders HTTP/1.1
Origin: https://frontend.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: Authorization, Content-Type

* The server can respond with:

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://frontend.example.com
Access-Control-Allow-Methods: POST, GET
Access-Control-Allow-Headers: Authorization, Content-Type

* The browser evaluates the response before sending the actual request.

=============================================================================================================================================================================
IMPORTANT CORS HEADERS
======================

Origin
→ Identifies the requesting origin.

Access-Control-Allow-Origin
→ Specifies allowed origins.

Access-Control-Allow-Methods
→ Specifies allowed HTTP methods.

Access-Control-Allow-Headers
→ Specifies request headers that may be used.

Access-Control-Allow-Credentials
→ Controls whether credentials can be included in credentialed cross-origin requests.

Access-Control-Expose-Headers
→ Specifies response headers that browser JavaScript is allowed to access.

=============================================================================================================================================================================
HTTP CACHING
============

* HTTP caching stores previously received responses so that they can be reused instead of repeatedly retrieving the same representation.

* HTTP caches can exist at different locations:

  • Browser Cache
  • CDN Cache
  • Proxy Cache

* Caching can reduce:

  • Network traffic
  • Latency
  • Server processing
  • Bandwidth usage

=============================================================================================================================================================================
CACHE-CONTROL
=============

* `Cache-Control` provides caching directives to HTTP caches.

Example:

Cache-Control: max-age=3600

* The response can be reused while it remains fresh according to the specified caching rules.

* `Cache-Control` can apply to different HTTP caches, not only the browser cache.

=============================================================================================================================================================================
MAX-AGE
=======

* `max-age` specifies how long a response can remain fresh.

Example:

Cache-Control: max-age=3600

* The response can be considered fresh for 3600 seconds.

=============================================================================================================================================================================
NO-STORE
========

Example:

Cache-Control: no-store

* Instructs caches not to store the response.

=============================================================================================================================================================================
NO-CACHE
========

Example:

Cache-Control: no-cache

* `no-cache` does not mean that the response cannot be stored.
* It means that a stored response must be revalidated before it is reused.

Therefore:

no-store
→ Do not store

no-cache
→ May store, but must revalidate before reuse

=============================================================================================================================================================================
CACHE FRESHNESS AND REVALIDATION
================================

* A cached response can be either fresh or require revalidation.

Fresh Response:

Request
│
▼
Cache
│
│ Fresh
▼
Use Cached Response

* No request to the origin server is required while the cached response can be reused directly.

When revalidation is required:

Cache
│
│ Conditional Request
▼
Server
│
├──► 304 Not Modified
│
└──► 200 OK + New Representation

=============================================================================================================================================================================
ETAG
====

* `ETag` identifies a particular representation of a resource.

Example:

ETag: "abc123"

* A cache can store the representation together with its ETag.

Conceptually:

Cached Representation
+
ETag

* During revalidation, the ETag can be sent back to the server using `If-None-Match`.

=============================================================================================================================================================================
IF-NONE-MATCH
=============

* `If-None-Match` is a conditional request header used with ETags.

Example:

GET /profile HTTP/1.1
If-None-Match: "abc123"

* The server compares the supplied ETag with the current representation.

If unchanged:

HTTP/1.1 304 Not Modified

If changed:

HTTP/1.1 200 OK
ETag: "xyz789"

<new representation>

=============================================================================================================================================================================
LAST-MODIFIED
=============

* `Last-Modified` indicates when a representation was last modified.

Example:

Last-Modified: Sat, 01 Aug 2026 10:00:00 GMT

* A cache can store the modification time together with the representation.

=============================================================================================================================================================================
IF-MODIFIED-SINCE
=================

* `If-Modified-Since` is a conditional request header used with `Last-Modified`.

Example:

GET /profile HTTP/1.1
If-Modified-Since: Sat, 01 Aug 2026 10:00:00 GMT

* The server checks whether the representation has been modified since the specified time.

If it has not changed:

HTTP/1.1 304 Not Modified

* If it has changed, the server returns the updated representation.

=============================================================================================================================================================================
304 NOT MODIFIED
================

* `304 Not Modified` indicates that the cached representation is still valid.
* The server does not need to send the representation again.

Initial Request:

Client
│
│ Request
▼
Server
│
│ 200 OK
│ ETag / Last-Modified
▼
Client Cache

Revalidation:

Client Cache
│
│ Conditional Request
│ If-None-Match / If-Modified-Since
▼
Server
│
│ 304 Not Modified
▼
Client uses existing cached representation

If the representation has changed:

Client Cache
│
│ Conditional Request
▼
Server
│
│ 200 OK
│ New Representation
▼
Client updates cache

=============================================================================================================================================================================
ETAG VS LAST-MODIFIED
=====================

ETag
↓
Identifies a representation
↓
If-None-Match

Last-Modified
↓
Identifies modification time
↓
If-Modified-Since

* Both mechanisms can be used for HTTP cache revalidation and conditional requests.

=============================================================================================================================================================================
HTTP REDIRECTS
==============

* A redirect tells the client that the requested resource or operation should be handled at another location.

* A redirect generally contains:

  • 3xx Status Code
  • Location Header

Example:

HTTP/1.1 301 Moved Permanently
Location: https://example.com/new-page

Redirect Flow:

Client
│
│ Request
▼
Server
│
│ 3xx + Location
▼
Client
│
│ New Request
▼
New Location

=============================================================================================================================================================================
LOCATION
========

* The `Location` header identifies the target of a redirect.

Example:

Location: https://example.com/products

* It can also contain a relative location:

Location: /products

=============================================================================================================================================================================
301 — MOVED PERMANENTLY
=======================

* Indicates that a resource has permanently moved.

Example:

HTTP/1.1 301 Moved Permanently
Location: /new-resource

* Common uses include:

  • Permanent URL changes
  • Website restructuring
  • HTTP → HTTPS redirection

=============================================================================================================================================================================
302 — FOUND
===========

* Indicates a temporary redirect.

Example:

HTTP/1.1 302 Found
Location: /temporary-resource

* Historical behavior of clients for 301/302 can change the request method to GET when following the redirect.

=============================================================================================================================================================================
303 — SEE OTHER
===============

* Indicates that the client should retrieve the result from another URI, commonly using GET.

Typical flow:

POST
↓
303 See Other
↓
GET

* This is commonly used in the Post/Redirect/Get pattern.

=============================================================================================================================================================================
307 — TEMPORARY REDIRECT
========================

* Indicates a temporary redirect while preserving the original HTTP method and request body.

Example:

POST /payment
│
▼
307 Temporary Redirect
│
▼
POST /new-payment

* The method and request body are preserved.

=============================================================================================================================================================================
308 — PERMANENT REDIRECT
========================

* Indicates a permanent redirect while preserving the original HTTP method and request body.

Example:

POST /old-payment
│
▼
308 Permanent Redirect
│
▼
POST /new-payment

=============================================================================================================================================================================
REDIRECT STATUS CODE COMPARISON
===============================

301
→ Permanent Redirect

302
→ Temporary Redirect

303
→ See Other
→ Commonly followed using GET

307
→ Temporary Redirect
→ Preserve method and body

308
→ Permanent Redirect
→ Preserve method and body

=============================================================================================================================================================================
CONTENT NEGOTIATION
===================

* Content negotiation allows the client and server to determine an appropriate representation of a resource.

* A single resource can have multiple representations.

Example:

Product Resource
│
├──► JSON Representation
├──► XML Representation
└──► HTML Representation

* The client can communicate its preferences using request headers.

=============================================================================================================================================================================
ACCEPT
======

* `Accept` specifies the media types that the client is willing to receive.

Example:

Accept: application/json

Multiple media types:

Accept: application/json, application/xml

* The client can specify preferences using quality values.

Example:

Accept: application/json, application/xml;q=0.8

* A higher quality value represents a higher preference.

=============================================================================================================================================================================
ACCEPT VS CONTENT-TYPE
======================

Accept:

Accept: application/json

→ Indicates the response representation the client is willing to receive.

Content-Type:

Content-Type: application/json

→ Indicates the actual representation of the message body.

Therefore:

Accept
→ Desired / acceptable response representation

Content-Type
→ Actual representation of the message body

=============================================================================================================================================================================
ACCEPT-LANGUAGE
===============

* `Accept-Language` specifies preferred response languages.

Example:

Accept-Language: en-US

Multiple preferences:

Accept-Language: en-US, en;q=0.9, hi;q=0.8

* The server can use this information to select an appropriate language representation.

=============================================================================================================================================================================
CONTENT-LANGUAGE
================

* `Content-Language` indicates the language of the representation being sent.

Example:

Content-Language: en-US

Relationship:

Accept-Language
→ Client preference

Content-Language
→ Language of the representation

=============================================================================================================================================================================
ACCEPT-ENCODING
===============

* `Accept-Encoding` specifies content encodings that the client can handle.

Example:

Accept-Encoding: gzip, br

* The server can use this information when determining how to encode the response.

=============================================================================================================================================================================
CONTENT-ENCODING
================

* `Content-Encoding` identifies the encoding applied to the representation.

Example:

Content-Encoding: gzip

Content-Type and Content-Encoding describe different properties.

Example:

Content-Type: application/json
Content-Encoding: gzip

Means:

Content-Type
→ Representation is JSON

Content-Encoding
→ gzip encoding has been applied

=============================================================================================================================================================================
CONTENT NEGOTIATION FLOW
========================

Example request:

GET /products/100 HTTP/1.1
Accept: application/json, application/xml;q=0.8
Accept-Language: en-US
Accept-Encoding: gzip

* The server selects an appropriate representation based on the request preferences.

Example response:

HTTP/1.1 200 OK
Content-Type: application/json
Content-Language: en-US
Content-Encoding: gzip

Relationship:

Accept
→ Desired media types

Accept-Language
→ Desired languages

Accept-Encoding
→ Supported content encodings

Content-Type
→ Actual media type

Content-Language
→ Actual language

Content-Encoding
→ Applied content encoding
