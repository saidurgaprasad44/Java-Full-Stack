=============================================================================================================================================================================
WHAT IS AN API?
=============================================================================================================================================================================

- API stands for Application Programming Interface.
- An API defines an interface through which one software component can communicate with another.
- The communicating components do not need to know each other's internal implementation.
- They only need to follow the API contract.

Examples:
* A Java application communicating with a payment service.
* A mobile application communicating with a backend.
* One backend service communicating with another service.

=============================================================================================================================================================================
WHAT IS A WEB API?
=============================================================================================================================================================================

- A Web API is an API exposed over web technologies, typically HTTP.
- A client communicates with the server by sending HTTP requests.
- The server processes the request and returns an HTTP response.
- A REST API is one architectural style for designing Web APIs.

=============================================================================================================================================================================
WHAT IS REST?
=============================================================================================================================================================================

- REST stands for Representational State Transfer.
- REST is an architectural style for designing networked applications and Web APIs.
- REST is not a programming language.
- REST is not a framework.
- REST is not a protocol.
- REST commonly uses HTTP for communication.
- REST APIs are generally designed around resources and their representations.
- The basic idea is:

  Resource
  ↓
  Representation
  ↓
  Transfer between client and server

=============================================================================================================================================================================
REST CLIENTS
=============================================================================================================================================================================

- A REST API is not limited to browser clients.
- Any client capable of making HTTP requests can consume a REST API.

- Web application
- React application
- Mobile application
- Desktop application
- Another backend service
- Command-line client

=============================================================================================================================================================================
REST RESOURCES
=============================================================================================================================================================================

- A resource is a conceptual entity exposed by an API.
- Resources are identified using URIs.
- REST APIs generally use nouns to represent resources.

- Product
- Customer
- Order
- Employee
- Account

- Example:

  /products

  → Product resource collection

  /products/101

  → A specific Product resource

=============================================================================================================================================================================
RESOURCE URI DESIGN
=============================================================================================================================================================================

- REST APIs generally use resource-oriented URIs.
- The URI identifies the resource.
- The HTTP method expresses the operation to perform on the resource.

- Prefer:

  /products
  /products/101
  /customers
  /customers/25/orders

- Avoid operation-oriented URLs such as:

  /getProducts
  /createProduct
  /deleteProduct

- Example:

  GET /products/101

  → GET expresses the operation.
  → /products/101 identifies the resource.

=============================================================================================================================================================================
REST API ENDPOINTS
=============================================================================================================================================================================

- An endpoint represents a specific API entry point through which a client can interact with a resource.
- An endpoint is generally defined by a combination of HTTP method and URI.

- GET /products
  → Retrieve products

- GET /products/101
  → Retrieve product 101

- POST /products
  → Create a product

- PUT /products/101
  → Replace product 101

- PATCH /products/101
  → Partially update product 101

- DELETE /products/101
  → Delete product 101

=============================================================================================================================================================================
HTTP METHODS IN REST
=============================================================================================================================================================================

- REST uses HTTP methods to express operations on resources.

- GET

  - Retrieve a resource or collection of resources.

- POST

  - Create a new resource or perform an operation where POST semantics are appropriate.

- PUT

  - Replace the representation of an existing resource.

- PATCH

  - Partially modify an existing resource.

- DELETE

  - Delete a resource.

=============================================================================================================================================================================
REST REQUEST AND RESPONSE
=============================================================================================================================================================================

- A REST API uses the HTTP request/response model.
- A REST request can contain:

  - HTTP method
  - URI
  - Headers
  - Path parameters
  - Query parameters
  - Request body

- A REST response can contain:

  - HTTP status code
  - Headers
  - Response body

- REST APIs commonly use JSON or XML as the representation in the request or response body.

=============================================================================================================================================================================
JSON
=============================================================================================================================================================================

- JSON stands for JavaScript Object Notation.
- JSON is a lightweight, language-independent data-interchange format.
- JSON is the most commonly used representation format for modern REST APIs.

- Example:

  {
  "id": 101,
  "name": "Laptop",
  "price": 75000
  }

- JSON supports:

  - Objects
  - Arrays
  - Strings
  - Numbers
  - Boolean values
  - null

- JSON object:

  {
  "id": 101,
  "name": "Laptop"
  }

- JSON array:

  [
  {
  "id": 101,
  "name": "Laptop"
  },
  {
  "id": 102,
  "name": "Phone"
  }
  ]

=============================================================================================================================================================================
XML
=============================================================================================================================================================================

- XML stands for Extensible Markup Language.
- XML is another representation format that can be used by REST APIs.
- XML represents data using elements/tags.
- XML is generally more verbose than JSON.

- Example:

  <product>
      <id>101</id>
      <name>Laptop</name>
      <price>75000</price>
  </product>

- REST does not require JSON specifically.
- JSON and XML are representations that can be used by REST APIs.

=============================================================================================================================================================================
REPRESENTATION
=============================================================================================================================================================================

- A REST API does not directly transfer the server's internal Java object to the client.
- The resource is represented in a transferable format such as JSON or XML.
- Example:

  Java Product object
  ↓
  JSON representation
  ↓
  HTTP response
  ↓
  Client

- The same resource can have different representations.
- Product resource represented as JSON:

  {
  "id": 101,
  "name": "Laptop"
  }

- Product resource represented as XML:

  <product>
      <id>101</id>
      <name>Laptop</name>
  </product>

=============================================================================================================================================================================
CONTENT-TYPE
=============================================================================================================================================================================

- Content-Type is an HTTP header that specifies the media type of the message body.

- JSON:

  Content-Type: application/json

- XML:

  Content-Type: application/xml

- Example:

  POST /products

  Content-Type: application/json

  {
  "name": "Laptop",
  "price": 75000
  }

- Content-Type describes the format of the body being sent.

=============================================================================================================================================================================
ACCEPT
=============================================================================================================================================================================

- Accept is an HTTP request header.

- It indicates the media types that the client can accept in the response.

- Example:

  Accept: application/json

  → Client requests a JSON response.

- Another example:

  Accept: application/xml

  → Client requests an XML response.

- Difference:

  Content-Type
  ↓
  Format of the body being sent

  Accept
  ↓
  Format the client can accept in the response

=============================================================================================================================================================================
PATH PARAMETERS
=============================================================================================================================================================================

- Path parameters are values embedded in the URI path.
- They are commonly used to identify a specific resource.

- Example:

  /products/101

- Here:

  101
  ↓
  Product identifier

- Example:

  GET /products/101

  → Retrieve Product 101

=============================================================================================================================================================================
QUERY PARAMETERS
=============================================================================================================================================================================

- Query parameters are additional parameters provided after `?` in a URI.
- They are commonly used for filtering, searching, sorting, pagination, and other optional criteria.

- /products?category=electronics

- /products?page=2

- /products?page=2&size=20

- /products?sort=price

------------------------------------------------------------
PATH PARAMETERS VS QUERY PARAMETERS

- Path parameters generally identify a resource.

  /products/101

  → Product 101

- Query parameters generally provide additional criteria for retrieving resources.

  /products?category=electronics

  → Products filtered by category

- General principle:

  Path
  ↓
  Resource identification

  Query parameters
  ↓
  Filtering / sorting / pagination / optional criteria

=============================================================================================================================================================================
REQUEST BODY
=============================================================================================================================================================================

- A request body contains data sent by the client to the server.

- POST, PUT, and PATCH commonly use request bodies when submitting resource data.

- Example:

  POST /products

  Content-Type: application/json

  {
  "name": "Laptop",
  "price": 75000
  }

- The server can deserialize this JSON into a Java object for processing.

=============================================================================================================================================================================
RESPONSE BODY
=============================================================================================================================================================================

- A response body contains data returned by the server to the client.
- REST APIs commonly return JSON or XML representations.

- Example:

  GET /products/101

  Response:

  Content-Type: application/json

  {
  "id": 101,
  "name": "Laptop",
  "price": 75000
  }

=============================================================================================================================================================================
REST API STATELESSNESS
=============================================================================================================================================================================

- Statelessness is an important REST architectural constraint.
- Each request should contain the information necessary for the server to process that request.
- The server should not depend on stored client-specific conversational state from previous requests.

- Example:

  GET /products/101
  Authorization: ...

  GET /products/102
  Authorization: ...

- Each request independently provides the required context.
- Stateless does not mean:

  - The server cannot have a database.
  - The server cannot store application data.
  - The server cannot use caching.

- It means the server does not depend on client-specific session state to understand the current request.

=============================================================================================================================================================================
REST API DESIGN PRINCIPLES
=============================================================================================================================================================================

- Design URIs around resources.

- /products
- /products/101
- /customers/25/orders

- Use HTTP methods to express operations.

- GET /products
- POST /products
- DELETE /products/101

- Use appropriate HTTP status codes.

- 200 OK
- 201 Created
- 204 No Content
- 400 Bad Request
- 404 Not Found
- 409 Conflict
- 500 Internal Server Error

- Use appropriate representations.

- JSON
- XML

- Use Content-Type to describe the body format.
- Use Accept to indicate acceptable response formats.
- Use path parameters to identify resources.
- Use query parameters for filtering, sorting, pagination, and other optional criteria.
- Keep REST APIs stateless.
