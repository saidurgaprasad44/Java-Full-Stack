=======================================================================================================================================================================
KAFKA — ARCHITECTURE
=======================================================================================================================================================================

- Kafka is an event streaming platform used to publish, store, and consume streams of events.
- It is commonly used when multiple applications/services need to communicate through events without being tightly coupled.
- Kafka is especially useful for high-volume event processing, independent consumers, durable event storage, replay, and scalable processing.

Examples:
* Order Service publishes OrderCreated → Kafka → Payment Service, Inventory Service, Analytics Service.

------------------------------------------------------------
WHY KAFKA?
------------------------------------------------------------

- Direct service-to-service communication creates tight coupling.
- If Order Service directly calls Payment, Inventory, Notification, and Analytics services, the Order Service depends on all of them being available and responsive.
- Different consumers may also process data at different speeds.
- Multiple independent consumers may need the same event.
- Applications may need durable storage of events and the ability to process old events again.
- High-volume systems may need scalable event ingestion and processing.
- Kafka provides an intermediary durable event stream between producers and consumers.
- Producers publish events to Kafka without directly communicating with every consumer.
- Consumers independently read the events they need.

Examples:
* Order Service → Kafka → Payment Service
                     → Inventory Service
                     → Notification Service
                     → Analytics Service

- Payment, Inventory, and Analytics can process the same order event independently.

------------------------------------------------------------
KAFKA AS AN EVENT STREAMING PLATFORM
------------------------------------------------------------

- An event stream is a continuous sequence of events produced over time.
- Kafka stores these events and allows consumers to read them from the stream.
- Kafka is more than a temporary message delivery mechanism because records remain available according to the configured retention policy.
- Different consumers can read the same stream independently.
- Different consumer groups can be at different positions in the same stream.
- A consumer can process events at its own pace.
- Consumers can replay older events by reading from an earlier position, provided the records are still retained.
- Kafka does not necessarily mean real-time processing.
- An event can remain in Kafka until a consumer processes it later.

Examples:
* OrderCreated events continuously arrive in the orders topic.
* Payment Service may process them immediately.
* Analytics Service may process them later or replay historical events.

------------------------------------------------------------
KAFKA VS TRADITIONAL MESSAGE QUEUE
------------------------------------------------------------

- A traditional message queue commonly focuses on work distribution.
- A message is generally consumed and acknowledged, after which it may no longer be available as an active queue item.
- Kafka is based around a durable event log where records remain available according to retention.
- Multiple consumer groups can independently read the same Kafka records.
- Each consumer group maintains its own progress.
- Kafka also provides partition-based ordering and scalable parallel processing.

- Traditional queue mental model:
  Producer → Queue → Consumer
  Message is generally treated as work waiting to be processed.

- Kafka mental model:
  Producer → Kafka topic → Multiple independent consumer groups
  Records remain available for consumers to read according to their positions and retention.

Examples:
* Payment Service can consume OrderCreated events.
* Analytics Service can independently consume the same OrderCreated events.
* Analytics can later replay retained events without requiring the Order Service to publish them again.

------------------------------------------------------------
KAFKA ARCHITECTURE
------------------------------------------------------------

- Kafka consists of applications producing records, Kafka brokers storing records, and applications consuming records.
- Topics organize records into logical event streams.
- Topics are divided into partitions.
- Partitions are ordered logs where records are stored.
- Brokers are Kafka servers that store and serve partitions.
- A Kafka cluster consists of multiple Kafka brokers working together.

- Basic flow:

  Producer Application
          ↓
      Kafka Cluster
          ↓
      Topic / Partition
          ↓
      Consumer Application


Simple Production Flow:

  Order Service
       │
       │ produces OrderCreated
       ↓
  Kafka Producer
       │
       ↓
  orders Topic
       │
       ├── Partition 0
       ├── Partition 1
       └── Partition 2
              │
              ↓
       Kafka Consumer Group
          ├── Consumer 1
          ├── Consumer 2
          └── Consumer 3
              │
              ↓
       Payment / Inventory / Analytics processing


- A real application can be both a producer and a consumer.
- A service can consume an event from one topic, process it, and publish another event to another topic.

Examples:
* Order Service publishes OrderCreated.
* Payment Service consumes OrderCreated.
* Payment Service publishes PaymentCompleted.

------------------------------------------------------------
BROKER
------------------------------------------------------------

- A broker is an individual Kafka server.
- It provides storage and network access for Kafka data.
- Topics and their partitions are stored on brokers.
- A broker is infrastructure; it is not the topic or partition itself.
- Multiple brokers together form a Kafka cluster.

Examples:
* Kafka Cluster:
  Broker 1
  Broker 2
  Broker 3

- Kafka can distribute partitions across these brokers.
- Replication can also place copies of partitions on different brokers.

------------------------------------------------------------
KAFKA CLUSTER
------------------------------------------------------------

- A Kafka cluster is a group of Kafka brokers working together.
- The cluster provides distributed storage and processing infrastructure for Kafka.
- Topics can contain multiple partitions distributed across brokers.
- Multiple brokers allow Kafka to distribute storage and request load.
- Think of:
  Broker = one Kafka server
  Cluster = collection of Kafka servers

Examples:
* A three-broker cluster may contain different partitions of the orders topic across Broker 1, Broker 2, and Broker 3.

------------------------------------------------------------
TOPIC
------------------------------------------------------------

- A topic is a named logical stream/category of records.
- Applications publish records to topics.
- Consumers subscribe to topics and read records from them.
- Topics commonly represent a business event stream or domain of related events.

Examples:
* orders
* payments
* shipments
* notifications

- An orders topic can contain order-related events such as:
  OrderCreated
  OrderUpdated
  OrderCancelled
  OrderShipped

- A topic can therefore be thought of as a durable stream of related events.
- However, an event is not the same thing as the service operation that produced it.

Examples:
* Service operation:
  cancelOrder()

* Resulting event:
  OrderCancelled

- The operation is what the application does.
- The event represents something that happened and is communicated to other components.

- A topic is not:
  - A service
  - A database table
  - A server

- A topic is a logical stream of records that Kafka stores using partitions.

------------------------------------------------------------
PARTITION
------------------------------------------------------------

- A partition is an individual ordered log within a Kafka topic.
- A topic can contain multiple partitions.
- Each partition stores records in order.
- Each partition has its own sequence of offsets.
- Partitions are the fundamental unit used for Kafka's scalable parallel consumption.

- A topic with three partitions can be viewed as:

  orders
    ├── Partition 0
    ├── Partition 1
    └── Partition 2

- Each partition is an independent ordered log.
- Records within a partition have a defined order.
- There is no guaranteed global ordering across different partitions.

- Partitions allow Kafka to distribute:
  - Storage
  - Network/request load
  - Consumer processing

- Partitions can be distributed across different brokers.
- A partition is not a separate server.
- A broker is the server; a partition is a logical log stored on broker infrastructure.

Examples:
* orders topic:
  Partition 0 → some order events
  Partition 1 → some order events
  Partition 2 → some order events

- Producers determine which partition receives a record.
- A partition key can be used to influence partition selection.
- Adding partitions provides the potential for more parallelism, but does not automatically make an application faster.
- Actual processing speed also depends on consumers, application concurrency, CPU, database performance, network calls, and other bottlenecks.

------------------------------------------------------------
PRODUCER
------------------------------------------------------------

- A producer is the application component/client that publishes records to Kafka.
- A Kafka producer is normally a client library running inside an application.
- It is not a separate Kafka server.

- Basic flow:

  Order Service
       ↓
  Kafka Producer Client
       ↓
  Kafka Cluster
       ↓
  Topic / Partition

- The producer sends records to Kafka.
- The producer does not directly send records to consumers.
- Kafka stores the records, and consumers independently read them.

- A Kafka record can contain:
  - Topic
  - Key
  - Value/payload
  - Headers
  - Timestamp

Examples:
* Topic = orders
* Key = O100
* Value = OrderCreated event payload

- The producer may use a key to determine the target partition.
- Producer acknowledgements, retries, and delivery details are covered later under Kafka internals.

------------------------------------------------------------
CONSUMER
------------------------------------------------------------

- A consumer is an application component/client that reads records from Kafka and processes them.
- A Kafka consumer is normally a client library running inside an application.
- It is not a separate Kafka server.

- Basic flow:

  Kafka Topic / Partition
          ↓
      Consumer
          ↓
   Application Logic

- A consumer reads records from its assigned partitions.
- It processes the records using application logic.
- A consumer does not have to process an event at exactly the time it is produced.
- A consumer can process events later depending on its processing capacity and position.
- Reading a record and successfully processing it are separate concepts.
- A consumer may read a record and fail during processing.
- Consumer progress and commits are therefore important.

------------------------------------------------------------
CONSUMER GROUP
------------------------------------------------------------

- A consumer group is a set of consumers that cooperate to consume a topic.
- Consumers belonging to the same group share the work across partitions.
- A partition is assigned to one consumer within a consumer group at a time.

Examples:
* Topic has three partitions:
  Partition 0 → Consumer 1
  Partition 1 → Consumer 2
  Partition 2 → Consumer 3

- The consumers above can process their assigned partitions concurrently.
- Multiple consumer instances of the same service commonly belong to the same consumer group.
- This allows the service to scale its Kafka consumption horizontally.
- If there are more consumers than partitions in a group, some consumers remain idle.

Examples:
* 3 partitions + 5 consumers
  → Only up to 3 consumers can actively consume those partitions at that time.

- Multiple services that all need every event normally use different consumer groups.

Examples:
* orders topic
  Payment Group → processes OrderCreated events
  Inventory Group → independently processes OrderCreated events
  Analytics Group → independently processes OrderCreated events

- Consumers in the same group share the workload.
- Consumers in different groups independently consume the same stream.
- When consumers join or leave a group, Kafka can redistribute partition assignments.
- This redistribution is called a rebalance.

------------------------------------------------------------
OFFSET
------------------------------------------------------------

- An offset is the sequential position assigned to a record within a Kafka partition.
- Offsets are local to a partition.
- Each partition has its own offset sequence.

Examples:
* Partition 0:
  Offset 0 → Record A
  Offset 1 → Record B
  Offset 2 → Record C

* Partition 1 can independently have:
  Offset 0 → Record X
  Offset 1 → Record Y

- An offset identifies a record's position within its partition.
- It is not a global position across the entire topic.

- Consumer groups maintain their own progress through partitions.
- The committed offset represents the position from which the consumer group can resume.
- Conceptually, if a consumer has successfully processed through offset 2 and commits its progress, it can resume with the next record.

- Offsets enable:
  - Progress tracking
  - Recovery after consumer restart
  - Replay
  - Independent progress between consumer groups

Examples:
* Payment Group may be processing recent records.
* Analytics Group may be replaying older retained records.

------------------------------------------------------------
PARTITION KEY
------------------------------------------------------------

- A partition key is a value attached to a record that helps determine which partition receives the record.
- A common key is an entity identifier such as orderId or customerId.
- Kafka's keyed partitioning generally hashes the key to select a partition.

Examples:
* Key = orderId
  O100 → Partition 1
  O101 → Partition 2
  O102 → Partition 0

- With the same partitioning configuration and partition count, records with the same key will normally map to the same partition.
- Using orderId as the key can therefore keep events for the same order in the same partition.

Examples:
* O100:
  OrderCreated
  PaymentCompleted
  OrderShipped

  These can be routed to the same partition.

- This is useful because Kafka preserves ordering within a partition.
- Key selection also affects workload distribution.
- A poorly chosen key can create a hot partition.
- A hot partition occurs when a disproportionate amount of traffic is concentrated on one partition.

Examples:
* If customerId is the key and one customer generates a very large amount of traffic, that customer's records may concentrate on one partition.

------------------------------------------------------------
ORDERING WITHIN PARTITIONS
------------------------------------------------------------

- Kafka guarantees ordering within a partition.
- Kafka does not guarantee global ordering across partitions.

Examples:
* Partition 0:
  Offset 0 → OrderCreated O100
  Offset 1 → PaymentCompleted O100
  Offset 2 → OrderShipped O100

- A consumer reading this partition sees records according to their partition order.
- If records are placed in different partitions:

  Partition 0:
  Order A
  Order B

  Partition 1:
  Order C
  Order D

- Kafka does not define a global ordering between Partition 0 and Partition 1.
- This is why partition keys are important when ordering is required for a particular entity.

Examples:
* orderId = O100
  → all O100 events go to the same partition
  → ordering for O100 can be maintained within that partition.

- Partition ordering means the order in which records exist in that partition.
- It does not automatically guarantee that business processing will complete in the same order if the consumer application processes records concurrently.
- The important distinction:
  Same partition → ordered log
  Different partitions → no guaranteed ordering between them.

------------------------------------------------------------
CONSUMER SCALING
------------------------------------------------------------

- Consumer scaling means running multiple consumer instances so that a workload can be processed concurrently.
- Multiple instances of the same service commonly belong to the same consumer group.

Examples:
* Payment Service:
  Instance 1
  Instance 2
  Instance 3

  All belong to:
  Payment Consumer Group

- Kafka distributes partitions among consumers in the group.

Examples:
* 4 partitions:
  P0 → Consumer 1
  P1 → Consumer 2
  P2 → Consumer 3
  P3 → Consumer 4

- This allows multiple partitions to be processed concurrently.
- The number of active consumers in a group cannot provide partition-level parallelism beyond the number of available partitions.

Examples:
* 4 partitions + 5 consumers
  → one consumer may remain idle.

- Consumer scaling is similar to load balancing conceptually, but the unit being distributed is different.

- REST load balancing:
  Load balancer distributes requests across service instances.

- Kafka consumer group:
  Kafka distributes partitions across consumer instances.

- If a consumer instance fails, Kafka can reassign its partitions to other consumers in the group.
- Consumer scaling therefore provides both:
  - Increased processing capacity
  - Fault tolerance through reassignment

------------------------------------------------------------
CONCURRENCY, PARALLELISM AND CONSUMER PROCESSING
------------------------------------------------------------

- Multiple consumer instances can process different partitions concurrently.
- Within an application, multiple threads can also provide concurrent processing.
- CPU cores determine how many CPU-bound threads can execute truly in parallel.

- Concurrency:
  Multiple tasks are in progress and execution may switch between them.

- Parallelism:
  Multiple tasks are actually executing at the same time on multiple CPU cores.

- A multi-core machine can execute multiple CPU-bound threads in parallel.
- Multiple threads do not automatically mean multiple CPU cores are used simultaneously; the operating system schedules threads onto available cores.
- A single-core machine can still have multiple application threads.
- Those threads cannot execute CPU instructions simultaneously.
- The operating system uses time-slicing and context switching to switch between threads.

Examples:
* Single core:
  Thread 1 → executes
  Thread 2 → executes
  Thread 3 → executes
  Thread 1 → executes again

- This is concurrency, not CPU-level parallelism.
- I/O-bound applications can still handle many concurrent operations on a single core because threads can make progress while other operations are waiting for I/O.
- CPU-heavy workloads benefit more directly from multiple CPU cores.

------------------------------------------------------------
CONSUMER LAG
------------------------------------------------------------

- Consumer lag represents how far behind a consumer group is from the latest available records in Kafka.
- It can be thought of as the consumer's backlog.

Examples:
* Latest available record is around offset 99.
* Consumer group has processed through offset 89.
* Roughly 10 records are still ahead of the consumer.

- Conceptually:

  Older records                              Latest records
  0 ─────────────────── 89 ──────────────── 99
                         ↑                   ↑
                  Consumer position     Latest position

                         ← Consumer lag →

- Lag commonly increases when records arrive faster than the consumer can process them.

Examples:
* Producer → 1,000 events/sec
* Consumer →   700 events/sec
* Result → backlog increases.

- Lag can also decrease when the consumer processes records faster than new records arrive.

Examples:
* Producer → 500 events/sec
* Consumer → 800 events/sec
* Result → consumer catches up and lag decreases.

- Temporary lag is not necessarily a problem.
- Persistent or continuously increasing lag indicates that the consumer group is not keeping up with the incoming workload.
- Possible causes of high or increasing lag include:
  - Insufficient consumer processing capacity
  - CPU limitations
  - Database bottlenecks
  - Slow external API calls
  - Network latency
  - Insufficient partitions for required parallelism
  - Too few consumer instances
  - Application/threading limitations
  - Processing errors or retries

- Consumer lag is therefore an important production monitoring metric.

- Overall relationship:

  Producer rate
       ↓
  Kafka partitions
       ↓
  Consumer instances
       ↓
  Application processing capacity
       ↓
  Consumer lag

=======================================================================================================================================================================
KAFKA — INTERNALS
=======================================================================================================================================================================

------------------------------------------------------------
Append-only log model

- Kafka stores records in an append-only log; new records are appended rather than updating arbitrary existing records.
- This supports efficient sequential writes and is fundamental to Kafka's high-throughput design.
- See Kafka Architecture notes for the basic broker/topic/partition model; this section focuses on the internal behavior resulting from that model.

------------------------------------------------------------
Partition as an ordered log

- Each partition is an ordered, append-only sequence of records identified by offsets.


Partition 0

Offset 0 → A
Offset 1 → B
Offset 2 → C
Offset 3 → D


- Ordering is guaranteed within a partition, not across the entire topic.
- Partition is also the unit of replication and the unit of consumer-group parallelism.

------------------------------------------------------------
Why partitions provide scalability

- A topic can be divided into multiple partitions, allowing different partitions to be processed concurrently.


Topic
 ├── P0 → Broker 1
 ├── P1 → Broker 2
 ├── P2 → Broker 3
 └── P3 → Broker 4


- Producer and consumer workload can therefore be distributed across brokers and consumer instances.
- Within a consumer group, one partition is assigned to only one consumer instance at a time.
- Number of partitions therefore determines the potential parallelism of a consumer group.
- More partitions do not guarantee proportional throughput; CPU, network, disk, broker capacity and application processing can still be bottlenecks.
- Partitioning and consumer-group behavior are covered conceptually in Kafka Architecture; here the important internal relationship is that partitioning enables parallel data processing.

------------------------------------------------------------
Offset and replay

- Each record in a partition has an offset representing its position in that partition.
- A consumer can start reading from a previous offset, allowing already-retained records to be replayed.


Partition

100 → A
101 → B
102 → C
103 → D

Consumer
       ↑
    start here


- Kafka does not normally delete a record when a consumer reads it.
- Replay is possible only while the required record is still retained.
- Offset represents position/progress; it is not a record identifier or a business ID.

------------------------------------------------------------
Retention

- Kafka retains records according to topic retention configuration rather than consumer processing status.
- Common retention controls are time-based and size-based.


Oldest                              Newest
  |                                    |
  v                                    v
[expired] [ retained records ........ ] [new]
     X


- A consumer not having processed a record does not prevent retention-based deletion.
- Retention therefore defines the practical window in which consumers can replay data.
- Kafka deletes data using log segments rather than individually deleting arbitrary records from the middle of a partition.
- Retention is independent of consumer offsets and producer acknowledgements.
- Long-term archival, when required, can be handled by databases, object storage or other dedicated storage systems; Kafka retention is primarily the streaming/replay window.

------------------------------------------------------------
Basic replication

- A partition can have multiple replicas distributed across different brokers.


Partition 0

Broker 1 → Replica
Broker 2 → Replica
Broker 3 → Replica


- Replication factor specifies the number of replicas for each partition.
- Replication provides fault tolerance and availability when brokers fail.
- Partition is the unit of replication.
- Replication increases storage and network overhead, so replication factor is a durability/availability versus resource-cost trade-off.
- Replication is not the same as long-term backup or archival.

------------------------------------------------------------
Leader / follower

- Among the replicas of a partition, one replica is the leader and the others are followers.


Producer
   |
   v
Leader
   |
   +----> Follower
   |
   +----> Follower


- The leader is the authoritative replica for writes to that partition.
- Followers replicate the leader's partition log.
- Different partitions can have different leaders, allowing leadership and workload to be distributed across brokers.
- If the leader fails, an eligible follower can become the new leader.
- Leader/follower therefore connects replication with partition availability and failure recovery.
- Leader is defined per partition, not per topic.

------------------------------------------------------------
Producer acknowledgements

- `acks` controls when the producer considers a record successfully acknowledged by Kafka.


acks=0
Producer → Leader
          no acknowledgement wait

acks=1
Producer → Leader → ACK

acks=all
Producer → Leader
              |
              +--> required in-sync replicas
              |
              +--> ACK


- `acks=0` does not wait for a broker acknowledgement; the producer has the weakest write confirmation.
- `acks=1` waits for the partition leader to acknowledge the record; followers may not have replicated it yet.
- `acks=all` waits for the configured replication/ISR condition, providing stronger durability.
- `acks=all` does not simply mean waiting for every configured replica regardless of its state; in-sync replicas and `min.insync.replicas` are relevant.
- `min.insync.replicas` can cause writes to be rejected when insufficient replicas are in sync, trading availability during failures for the configured durability requirement.
- `acks` describes producer-to-Kafka acknowledgement; it does not indicate that any consumer has processed the record.

------------------------------------------------------------
Consumer offset / commit

- Consumer progress is tracked separately for each consumer group, topic and partition.


Partition 0
100 → A
101 → B
102 → C
103 → D

Payment Group     → position 103
Analytics Group   → position 101


- Different consumer groups can independently consume and track the same partition.
- Processing a record and committing its offset are separate operations.


Read
 ↓
Process
 ↓
Commit


- If processing succeeds but the commit fails, the record can be processed again after restart or rebalance.
- This is the Kafka-specific reason consumer processing can result in duplicate delivery; apply the idempotency strategies to the business operation.
- Committing before successful business processing can cause a record to be skipped after a failure.
- A committed position conceptually represents the next position from which processing should resume.


Processed through 102
        ↓
Committed position = 103
        ↓
Resume from 103


- Consumer commits do not delete records from Kafka; retention still determines how long those records remain available.
- Consumer-group rebalancing allows another consumer instance to take over partitions after a consumer failure and continue from the group's committed position.

------------------------------------------------------------
Why Kafka provides high throughput

- Kafka's throughput comes from several design decisions working together rather than from a single optimization.


Append-only log
      ↓
Sequential I/O
      ↓
Batching + compression
      ↓
Partition-level parallelism
      ↓
Producer / consumer concurrency


- Append-only writes avoid the general cost of constantly modifying arbitrary locations in the log.
- Sequential disk access is efficient compared with random updates.
- Producers can batch multiple records into fewer requests, reducing network and request-processing overhead.
- Batch compression can reduce network traffic and storage/I/O requirements.
- Multiple partitions allow data to be processed concurrently across brokers and consumers.
- Consumers can process different partitions concurrently within a consumer group.
- Replication adds network and storage overhead; it is primarily a fault-tolerance/durability mechanism rather than a throughput optimization.
- More partitions provide potential parallelism but do not guarantee unlimited throughput; hardware and application bottlenecks still apply.
