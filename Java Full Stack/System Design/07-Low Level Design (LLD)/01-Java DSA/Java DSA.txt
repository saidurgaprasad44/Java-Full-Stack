Complexity fundamentals

Common Time Complexities:

O(1): constant; Array index access
O(log n): logarithmic; Binary search
O(n): linear traversal; Single loop
O(n log n): Linearithmic; Merge sort
O(n²): Quadratic; Nested loops


Common Space Complexities:

O(1): Constant space; Using a few variables
O(log n): logarithmic; Recursive binary search
O(n): linear traversal; Creating another array of n elements
O(n log n): Linearithmic; Some divide-and-conquer algorithms (not very common)
O(n²): Quadratic space; Creating an n× 	n matrix
O(2ⁿ): Exponential space; Storing all subsets of a set
O(n!): Factorial space; Storing all permutations

String: 
------------------------------------------------------------

- Immutable, so its contents cannot be changed after creation, any change will create a completely new object in string pool, so automatically thread-safe.

- String Literal: 
	- Example: String str = "Java"; // Declared and initialized using a literal
	- The most common way. It uses the String Pool for memory efficiency.
	- If "Java" already exists in the pool, the new reference points to the existing object.

- Using the new Keyword: 
	- Example: String s = new String("Java"); // Explicit instantiation
	- This forces the creation of a new object in the standard heap memory, even if "Java" already exists in the pool.
	- Less efficient; creates redundant objects.

	String s2 = "Hello";
	String s3 = new String("Hello");
	System.out.println(s1 == s2); // true (same reference in pool)
	System.out.println(s1 == s3); // false (different objects in memory)

HashMap: 

- Offers fast lookups but no specific order.


Internal data structure: 

- A HashMap internally uses an array of buckets. Each bucket can hold entries containing:
	- Hash value
	- Key
	- Value
	- Reference to the next entry (to connect entries that have the same bucket index called chaining collision-resolution technique)

- The bucket array is called the table in the OpenJDK implementation.
- Each entry is represented by a Node object, conceptually containing:

static class Node<K,V> {
    int hash;
    K key;
    V value;
    Node<K,V> next;
}

- Consider:

Map<Integer, String> employees = new HashMap<>();

employees.put(101, "John");
employees.put(102, "Alice");
employees.put(103, "David");

- Conceptually:

Index	Bucket
-------------------
0	Empty
1	101 → John
2	103 → David
3	Empty
4	102 → Alice
5	Empty
6	Empty
7	Empty


Mutability & Modifiability: 


How do operations work?:

put(): 
	
Step 1: Calculate the key's hash
- It obtains the key's hashCode() and applies an additional hash-spreading operation.

Step 2: Calculate the bucket index
- HashMap determines where the entry should be stored using: index = (capacity - 1) & hash;
- A single bucket can have multiple entries (hash collision)

Step 3: Check the bucket
- If the bucket is empty, insert a new node.
- If the bucket already contains an entry, compare (==) search hash with stored hash and search key with (equals()) stored key.
- If the same key exists, replace its value.
- Otherwise, handle the collision by adding another node to that bucket.

Step 4: Check whether resizing is required
- HashMap monitors its size against its threshold.
- With the default configuration:
	- Initial capacity: 16 (allocated lazily when first needed).
	- Load factor: 0.75.
	- Resize threshold: 16 × 0.75 = 12.
- When the number of entries exceeds the threshold, the table generally doubles in capacity (16, 32, 64, ....).
- For example if the current capacity is 16, then resize threshold = 12; At this moment, if a 13th element is added, it resizes itself to 32

get():

- Calculates the hash of key 101 using hashCode().
- Calculates the bucket index.
- Goes directly to that bucket.
- Checks the hash and key equality with equals().
- Returns the matching value.


Time complexity:

------------------------------------------------------------
equals() vs hashCode()

- These two methods are particularly important when working with custom objects in hash-based collections.
- hashCode() helps locate the bucket; equals() distinguishes objects within that bucket.


equals():

- By default, the equals() method inherited from Object compares object references, just like ==
- The equals() method is overridden in String class to define content based equality
- Override equals() in custom Java classes to define business logic based equality.


Overriding equals():

class Employee{
	private String name;
	private int id;
	
	@Override
	public boolean equals(Object obj) {
		if (this == obj) return true;
		
		if (obj == null || !(obj instanceof Employee)) return false;
		
		Employee other = (Employee)obj;
		
		return Objects.equals(this.name,other.name) && this.id == other.id;
	}	

	//getters & setters.....

	//Overridden hashCode().....
}


hashCode():

- hashCode() returns an integer to determine where an object should be stored.
- If hashCode() isn't overridden in custom classes, the default implementation from Object guarantees a distinct integer for every single unique object instance created in memory, regardless of whether their internal fields hold identical data.
- Override hashCode() in custom classes to use hash based collections like HashMap, HashSet etc.,


Overriding hashCode():

class Employee{

	......

	@Override
	public int hashCode() {
    		return Objects.hash(name, id);
	}	

	......

}

- For custom objects as HashMap keys, make sure the equals-hashCode contract is followed

The equals-hashCode contract:

Rule				Meaning
--------------------------------------------
If a.equals(b) is true		a.hashCode() must equal b.hashCode()
If hash codes are equal		Objects are not necessarily equal
If equals() is overridden	You should also override hashCode()
If objects are unequal		They may still have the same hash code (collision)

- If mutable fields are used for HashMap key equality and hashing, the lookup may fail, if the field is changed after inserting the object 
- Why? The entry was stored using the original hash, but lookup now calculates a hash using the modified ID
- Use immutable fields for HashMap key equality and hashing wherever possible.

------------------------------------------------------------
Hash Collision:

- A hash collision occurs when their hash values map to the same bucket index.
- The nodes from the same bucket maintain links to next node for node traversal (Single linked list)

How does HashMap retrieve an element from a collided bucket?

- Suppose John and Alice are in the same bucket.

HashMap:

- Calculates Alice's hash.
- Identifies bucket 5.
- Checks the first node (John).
- Compares the stored hash and key.
- John doesn't match.
- Follows next to the second node.
- Finds Alice and returns 200.

------------------------------------------------------------
Treeification:

- If a bucket gets too crowded, the long linked list can make lookups expensive.
- To improve performance, modern Java HashMap implementations can convert a heavily collided bucket into a Red-Black Tree called treeification.
- In OpenJDK Java 17/21, the relevant thresholds are:

Constant		Value	Meaning
-------------------------------------------
TREEIFY_THRESHOLD	8	Collision-chain threshold that triggers treeification consideration
UNTREEIFY_THRESHOLD	6	Threshold used when splitting tree bins during resizing
MIN_TREEIFY_CAPACITY	64	Minimum table capacity for treeification

- Treeification improves lookup in heavily collided buckets from O(n) toward O(log n).

------------------------------------------------------------
Resizing:

- Allocate a new bucket array with double the capacity.
- Redistribute existing entries into the new table.
- Update the table reference and threshold.

Note: Existing nodes already store their spread hash, so HashMap reuses it during resizing

------------------------------------------------------------
LinkedHashMap:


Internal Data Structure:

- LinkedHashMap extends HashMap. 
- It retains the hash-based lookup mechanism but adds a doubly linked list connecting entries to maintain iteration order.
- The LinkedHashMap entry contains additional before and after references alongside the normal HashMap node fields (i.e., hash, key, value, next).
- The trade-off is additional memory for the two linked-list references in every entry.



Mutability & Modifiability:

 

How do operations work?: 

Insertion:

- HashMap calculates the hash and identifies the bucket.
- The entry is inserted into the bucket.
- LinkedHashMap links the new entry after the current tail.
- The insertion order is maintained.

Retrieval:

- Retrieval uses the normal HashMap mechanism for finding the key in the bucket array
- And it uses next node to traverse through the nodes in the collided bucket

Removal:

- HashMap locates the entry.
- The entry is removed from its bucket.
- Its previous and next entries are linked together.
- The removed entry is unlinked from the ordering list.



Time and space complexity:

Operation	Average complexity
----------------------------------
put()		O(1)
get()		O(1)
remove()	O(1)
containsKey()	O(1)
Iteration	O(n)



Insertion order vs access order:

- By default, it preserves insertion order, but you can configure it to preserve access order instead.

Map<Integer, String> employees = new LinkedHashMap<>(16, 0.75f, true); //LinkedHashMap(int initialCapacity, float loadFactor, boolean accessOrder)

- When accessOrder is true, accessing an entry moves it to the end of the linked list.
- This behavior is the foundation of a classic LRU (Least Recently Used) cache.

Example: Suppose a cache can hold only three entries.

Operation	Cache order (oldest → newest)
Add A		A
Add B		A → B
Add C		A → B → C
Access A	B → C → A
Add D		C → A → D

- B is evicted because it is now the least recently used entry.



Thread safety: 

- LinkedHashMap is not thread-safe.



Null handling: 

- One null key.
- Multiple null values.

- Keeps keys in a sorted order.

ArrayList:

Internal data structure: 

- An ArrayList internally uses a resizable array of Objects (Dynamic Array).
- It has spare capacity to accommodate future additions.
- If the internal array is full and you still append elements
- The ArrayList must:
	- Allocate a larger array.
	- Copy existing elements into it.
	- Insert the new element.
	- Replace the reference to the old array.

- In OpenJDK Java 17/21, the usual growth policy is approximately 1.5 times the previous capacity.
- Resizing involves allocating a new array and copying existing references, which takes O(n) time.
- However, resizing doesn't happen on every insertion. Therefore, repeated add() operations at the end have amortized O(1) time complexity.
- If you know the approximate number of elements beforehand, you can reduce resizing:

List<Employee> employees = new ArrayList<>(1000);

or

ArrayList<Employee> employees = new ArrayList<>();
employees.ensureCapacity(1000);

LinkedList: 

- Better for frequent insertions and deletions at the beginning or end.
- Implements both List and Deque, so it can be used as a list, queue, or deque.


Internal data structure:

- LinkedList uses a doubly linked list.
- Each node contains:
	- The element.
	- A reference to the previous node.
	- A reference to the next node.

- Java's LinkedList maintains references to the first, last nodes and the size, allowing efficient insertion and removal at both ends.


Mutability & Modifiability: 


How do operations work?:

- Insertion/removal at a known node is O(1), but reaching that position from the beginning generally takes O(n).

Operation			Internal behavior		Complexity
--------------------------------------------------------------------------
get(index)			Traverse nodes from an end	O(n)
add(value)			Create node and link at tail	O(1)
addFirst()/addLast()		Link new node at head/tail	O(1)
removeFirst()/removeLast()	Unlink head/tail		O(1)
remove(index)			Traverse to node, then unlink	O(n)
contains()			Traverse and compare		O(n)


Memory Overhead: 

- Every element requires a separate node containing: The object reference, a previous-node reference, a next-node reference, object-header and alignment overhead.


Thread safety: 

- Not thread-safe; concurrent modifications require synchronization.

 
Null handling: 

- Allows multiple null elements.


Optimization considerations: 

- Use it when you genuinely need efficient insertions/removals at both ends or already have an iterator positioned at the required node.

Queue (Order of Processing)
------------------------------------------------------------

- A Queue is designed for holding elements prior to processing, typically following the FIFO (First-In-First-Out) principle. 
- Queue: First In, First Out. Elements are added at the back and removed from the front.
- Deque: Allows insertion and removal at both ends.



Important Queue APIs:

Purpose		Methods			Behavior
----------------------------------------------------
Insert		add(), offer()		add() throws on capacity restriction; offer() returns false.
Remove head	remove(), poll()	remove() throws if empty; poll() returns null.
Inspect head	element(), peek()	element() throws if empty; peek() returns null.



Deque-specific APIs:

Purpose			Methods
-------------------------------------
Insert at front		addFirst(), offerFirst()
Insert at rear		addLast(), offerLast()
Remove from front	removeFirst(), pollFirst()
Remove from rear	removeLast(), pollLast()
Inspect front		getFirst(), peekFirst()
Inspect rear		getLast(), peekLast()

LinkedList:

- Doubly linked list; implements both List and Deque.

// Add objects
employees.add(new Employee(101, "John", "IT", 75000));
employees.add(new Employee(102, "Alice", "HR", 65000));

// Find an employee
Employee employee = employees.stream()
        .filter(e -> e.getId() == 101)
        .findFirst()
        .orElse(null);

// Create a lookup map using employee ID
Map<Integer, Employee> employeeById = employees.stream()
        .collect(Collectors.toMap(Employee::getId, Function.identity()));

// Group employees by department
Map<String, List<Employee>> byDepartment = employees.stream()
        .collect(Collectors.groupingBy(Employee::getDepartment));
