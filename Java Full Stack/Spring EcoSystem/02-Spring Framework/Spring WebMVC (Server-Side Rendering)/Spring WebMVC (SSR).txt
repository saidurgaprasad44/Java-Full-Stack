=======================================================================================================================================================================
SPRING MVC ARCHITECTURE
=======================================================================================================================================================================

- Spring MVC is a web framework built on top of the Servlet API.
- A Servlet container such as Tomcat receives the HTTP request and invokes the `DispatcherServlet`.
- `DispatcherServlet` acts as the Front Controller of the Spring MVC application.
- It coordinates the different components involved in processing a request.

- Basic request flow:

Browser
   |
   | HTTP request
   v
Servlet Container (Tomcat)
   |
   v
DispatcherServlet
   |
   +--> HandlerMapping
   |       |
   |       v
   |   Controller method
   |
   +--> HandlerAdapter
   |
   v
Controller <--> Service <--> Repository <--> Database
   |
   |View Name
   v
ViewResolver
   |
   |JSP
   v
Browser

------------------------------------------------------------
DISPATCHERSERVLET


- `DispatcherServlet` is a Spring MVC `Servlet`.
- It acts as the central entry point for Spring MVC requests.
- The Servlet container invokes it when the incoming request matches its servlet mapping.
- It coordinates request processing rather than containing application-specific business logic.
- Major responsibilities include:

  - Finding the appropriate handler.
  - Invoking the handler.
  - Processing the handler's result.
  - Resolving the view.
  - Coordinating exception handling.

------------------------------------------------------------
FRONT CONTROLLER PATTERN


- Front Controller is a design pattern where a single central component receives and coordinates requests.
- Spring MVC implements the Front Controller pattern using `DispatcherServlet`.

- Without a Front Controller:

Request A → Servlet A
Request B → Servlet B
Request C → Servlet C

- With Spring MVC:

Request A ─┐
Request B ─┼→ DispatcherServlet
Request C ─┘          
                       ↓
             Appropriate Controller

- Centralizing request processing allows common concerns such as routing and exception handling to be handled consistently.

=======================================================================================================================================================================
HANDLERMAPPING
=======================================================================================================================================================================

- `HandlerMapping` is responsible for finding the handler that should process an incoming request.
- In annotation-based Spring MVC applications, the handler is typically a controller method.
- It uses request information such as URL, HTTP method, and mapping conditions to identify the appropriate handler.

- Example:

@GetMapping("/employees")
public String getEmployees() {
    ...
}

- For:

GET /employees

- HandlerMapping identifies:

EmployeeController.getEmployees()

- Spring MVC provides the HandlerMapping implementations.
- Developers normally do not implement HandlerMapping themselves.
- For annotation-based controllers, an important implementation is `RequestMappingHandlerMapping`.
- It understands annotations such as:

  - `@RequestMapping`
  - `@GetMapping`
  - `@PostMapping`
  - `@PutMapping`
  - `@DeleteMapping`

- An application can have multiple HandlerMappings.
- They are application-level MVC infrastructure components.
- They are not created separately for each controller.

- Conceptually:

DispatcherServlet
      ↓
HandlerMapping 1
HandlerMapping 2
HandlerMapping 3
      ↓
Appropriate Handler

=======================================================================================================================================================================
HANDLERADAPTER
=======================================================================================================================================================================

- `HandlerAdapter` is responsible for invoking the handler selected by HandlerMapping.
- `DispatcherServlet` does not directly invoke every possible type of handler.
- It delegates handler invocation to an appropriate HandlerAdapter.

- Flow:

DispatcherServlet
      ↓
HandlerMapping
      ↓
Find Handler
      ↓
HandlerAdapter
      ↓
Invoke Handler

- For annotation-based controller methods, the HandlerAdapter also participates in:

  - Resolving controller method arguments.
  - Processing method-related annotations.
  - Invoking the controller method.
  - Processing the controller method's return value.

- Spring MVC provides HandlerAdapter implementations.
- For annotation-based controller methods, an important implementation is `RequestMappingHandlerAdapter`.
- Developers normally do not implement HandlerAdapter themselves.
- An application can have multiple HandlerAdapters.
- They are application-level infrastructure components, not one per controller.

=======================================================================================================================================================================
CONTROLLER
=======================================================================================================================================================================

- A controller handles incoming web requests.
- In Spring MVC SSR applications, controllers are commonly annotated with `@Controller`.
- `@Controller` makes the class a Spring-managed component suitable for MVC request handling.
- The controller generally delegates business logic to the service layer.

- Example:

@Controller
public class EmployeeController {

    @GetMapping("/employees")
    public String getEmployees(Model model) {

        List<Employee> employees =
                employeeService.findAll();

        model.addAttribute("employees", employees);

        return "employees";
    }
}

- Controller methods can:

  - Receive request information.
  - Call service-layer operations.
  - Add data to the Model.
  - Return a logical view name.

------------------------------------------------------------
REQUEST MAPPING


- Spring MVC maps HTTP requests to controller methods using mapping annotations.
- Common annotations:

@RequestMapping
@GetMapping
@PostMapping
@PutMapping
@DeleteMapping

- Example:

@GetMapping("/employees")
public String getEmployees() {
    return "employees";
}

- Mapping:

GET /employees
      ↓
getEmployees()

=======================================================================================================================================================================
MODEL
=======================================================================================================================================================================

- `Model` is a Spring MVC abstraction used to carry data from the controller to the view.
- It is not the same as a JPA entity model or database model.
- It represents data that should be made available to the view during the current request.

- Example:

model.addAttribute("employees", employees);

- Conceptually:

Model
┌──────────────────────────────┐
│ "employees" → List<Employee>          │
└──────────────────────────────┘

------------------------------------------------------------
MODEL.ADDATTRIBUTE()


- `addAttribute()` adds data to the Model using a name-value pair.

- Example:

model.addAttribute("employees", employees);

- `employees` is the model attribute name.
- `employees` is the value made available to the view.
- The view can then access the model attribute while rendering the response.

------------------------------------------------------------
Passing data from Controller → View

- When the controller returns, the DispatcherServlet has the model and the logical view name
- It passes these to the view-rendering mechanism
- Then the ViewResolver resolves the view name 
- Finally when the JSP is rendered, the model attributes are made available to the JSP's request context.

How does the JSP access it?

- For example, with JSTL:

<c:forEach var="employee" items="${employees}">
    <p>${employee.name}</p>
</c:forEach>

------------------------------------------------------------
MODEL VS SERVLET REQUEST ATTRIBUTES


- In a traditional Servlet application, data can be passed to a JSP using request attributes.
- Servlet approach:

request.setAttribute("employees", employees);
RequestDispatcher dispatcher = request.getRequestDispatcher("/employees.jsp");
dispatcher.forward(request, response);

- Spring MVC provides the higher-level `Model` abstraction.
- Spring MVC approach:

model.addAttribute("employees", employees);
return "employees";

- Spring MVC handles the underlying request-to-view processing.
- Conceptually:


Servlet

request.setAttribute()
        ↓
RequestDispatcher.forward()
        ↓
JSP


Spring MVC

model.addAttribute()
        ↓
return "employees"
        ↓
ViewResolver
        ↓
JSP

=======================================================================================================================================================================
VIEW
=======================================================================================================================================================================

- A View is responsible for generating the response representation.
- In Spring MVC SSR, the View typically generates HTML on the server.
- JSP is one traditional server-side view technology.
- The controller generally returns a logical view name rather than directly generating HTML.

------------------------------------------------------------
LOGICAL VIEW NAME


- A controller can return a `String` representing a logical view name.

- Example:

return "employees";

- `"employees"` is a logical view name.
- It is not necessarily the physical path of the JSP file.
- Spring MVC passes the logical view name to the ViewResolver.

- Conceptually:

"employees"
     ↓
ViewResolver
     ↓
employees.jsp

------------------------------------------------------------
JSP AS A SERVER-SIDE VIEW


- JSP can be used as the View in a Spring MVC SSR application.
- The JSP executes on the server and generates HTML.
- The generated HTML is then sent to the browser.

- Conceptually:

Controller
    ↓
Model
    ↓
JSP
    ↓
HTML
    ↓
Browser

- JSP is a traditional view technology; Spring MVC is not limited to JSP.

=======================================================================================================================================================================
VIEWRESOLVER
=======================================================================================================================================================================

- `ViewResolver` maps a logical view name to an actual View.
- It separates the controller from the physical location and technology of the view.

- Example:

return "employees";

- ViewResolver can resolve this to:

/WEB-INF/views/employees.jsp

- Conceptually:

Controller
    ↓
"employees"
    ↓
ViewResolver
    ↓
/WEB-INF/views/employees.jsp

- Spring MVC provides ViewResolver implementations.
- Developers normally configure the appropriate ViewResolver rather than implementing one themselves.
- An application can have multiple ViewResolvers.
- They are application-level infrastructure components, not one per controller.

------------------------------------------------------------
JSP PREFIX AND SUFFIX


- A JSP ViewResolver can be configured with a prefix and suffix.

- Example:

Prefix: /WEB-INF/views/
Suffix: .jsp

- When the controller returns:

return "employees";

- Spring resolves it conceptually as:

/WEB-INF/views/ + employees + .jsp → /WEB-INF/views/employees.jsp

- Example configuration:

@Bean
public InternalResourceViewResolver viewResolver() {

    InternalResourceViewResolver resolver = new InternalResourceViewResolver();

    resolver.setPrefix("/WEB-INF/views/");
    resolver.setSuffix(".jsp");

    return resolver;
}

------------------------------------------------------------
MULTIPLE VIEWRESOLVERS


- Spring MVC can have multiple ViewResolvers.
- They are application-level infrastructure components.
- They are not created separately for every controller.

- Conceptually:

DispatcherServlet
      ↓
ViewResolver 1
ViewResolver 2
ViewResolver 3
      ↓
Resolved View

SPRING MVC SSR REQUEST FLOW
=======================================================================================================================================================================

- Consider:

GET /employees


- The complete request processing flow is:


Client
  ↓
GET /employees
  ↓
Tomcat
  ↓
DispatcherServlet
  ↓
HandlerMapping
  ↓
Find EmployeeController.getEmployees()
  ↓
HandlerAdapter
  ↓

  ↓

  ↓

  ↓

  ↓

  ↓

  ↓

  ↓
HTTP Response
  ↓

- The important responsibilities are:


DispatcherServlet
    → Coordinates request processing

HandlerMapping
    → Finds the appropriate handler

HandlerAdapter
    → Invokes the handler

Controller
    → Handles the web request

Model
    → Carries data to the View

ViewResolver
    → Resolves logical view name to View

JSP
    → Generates HTML

CONFIGURATION
=======================================================================================================================================================================

- Traditional Spring MVC applications require explicit configuration for the web layer and Spring MVC infrastructure.
- Configuration can be done using:

  - XML-based configuration
  - Java-based configuration

- The main configuration areas are:

  - DispatcherServlet
  - WebApplicationContext
  - Spring MVC infrastructure
  - Component scanning
  - ViewResolver
  - Filters
  - Interceptors

- Spring Boot can automatically configure much of this infrastructure through auto-configuration.

------------------------------------------------------------
XML-BASED CONFIGURATION
------------------------------------------------------------

web.xml
    → Servlet-container configuration
    → DispatcherServlet registration
    → Root context creation
    → Filters

root-context.xml
    → Configuration for Root ApplicationContext
    → Services / Repositories / DB / Transactions / ...

dispatcher-servlet.xml
    → DispatcherServlet's child WebApplicationContext
    → Spring MVC infrastructure
    → Controllers
    → ViewResolver
    → Interceptors

------------------------------------------------------------
JAVA-BASED CONFIGURATION
------------------------------------------------------------

WebAppInitializer.java
    → Servlet-container bootstrap
    → DispatcherServlet registration
    → Root + Child context connection
    → Filters

RootConfig.java
    → Configuration for Root ApplicationContext
    → Services / Repositories / DB / Transactions / ...

WebConfig.java
    → DispatcherServlet's child WebApplicationContext
    → Spring MVC infrastructure
    → Controllers
    → ViewResolver
    → Interceptors

------------------------------------------------------------
DISPATCHERSERVLET CONFIGURATION
------------------------------------------------------------

- The Servlet container must know about the `DispatcherServlet`.
- The DispatcherServlet must be registered so that the Servlet Container forwards the requests to DispatcherServlet.
- Traditionally, this registration was commonly done using `web.xml`.
- With Java-based configuration, the Servlet can be registered programmatically.


XML-based configuration:

- Configure in `web.xml`.


<servlet>
    <servlet-name>dispatcher</servlet-name>

    <servlet-class>
        org.springframework.web.servlet.DispatcherServlet
    </servlet-class>
</servlet>

<servlet-mapping>
    <servlet-name>dispatcher</servlet-name>
    <url-pattern>/</url-pattern>
</servlet-mapping>


- `/` means requests are mapped to the `DispatcherServlet` according to Servlet URL-mapping rules.
- By convention, when no explicit context configuration location is provided, the DispatcherServlet looks for: dispatcher-servlet.xml


Java-based configuration:

- Configure in `WebAppInitializer.java`.

public class WebAppInitializer
        extends AbstractAnnotationConfigDispatcherServletInitializer {

    @Override
    protected Class<?>[] getServletConfigClasses() {
        return new Class<?>[] { WebConfig.class };
    }

    @Override
    protected String[] getServletMappings() {
        return new String[] { "/" };
    }
}

- `AbstractAnnotationConfigDispatcherServletInitializer` allows the DispatcherServlet and its WebApplicationContext to be configured without `web.xml`.
- The Servlet container discovers the initializer through Servlet 3+ container startup mechanisms.


------------------------------------------------------------
WEBAPPLICATIONCONTEXT
------------------------------------------------------------

- Spring's ApplicationContext is the container that creates and manages the application's Spring beans.
- `WebApplicationContext` is a web-aware implementation of Spring's `ApplicationContext`.
- Spring Web MVC applications (both SSR & REST) can contain TWO WebApplicationContexts

  - DispatcherServlet's WebApplicationContext: It contains the Spring MVC web-layer beans and can also contain application beans if Root Context is not configured.
  - Root WebApplicationContext (Optional): It is to maintain the application level infrastructure like Services, Repositories, DB, Transactions, etc.,

- A traditional Spring MVC application can have:

  - Only the DispatcherServlet's WebApplicationContext
  - A root WebApplicationContext + a DispatcherServlet's child WebApplicationContext

- A separate root context is optional and created manually by configuring the ContextLoaderListener


Without a root context:

Tomcat
   ↓
DispatcherServlet
   ↓
WebApplicationContext
   ├── Controllers
   ├── Services
   ├── Repositories
   └── MVC infrastructure


With a root and child context:

Root WebApplicationContext
   ├── Services
   ├── Repositories
   ├── DataSource
   └── Transaction infrastructure
              ↑
              │ parent
              │
Child WebApplicationContext
   ├── Controllers
   ├── HandlerMappings
   ├── HandlerAdapters
   └── ViewResolvers

- The child WebApplicationContext can access beans from the root context.
- The root context normally does not access beans from its child.
- The root context is commonly used for application/business infrastructure.
- The DispatcherServlet's child context is commonly used for web/MVC infrastructure.


XML-based root context configuration:

- Configure the root context in `root-context.xml`.
- Configure `ContextLoaderListener` and the root context location in `web.xml`.


web.xml:

<context-param>
    <param-name>contextConfigLocation</param-name>
    <param-value>
	classpath:application-config.xml
	classpath:Jpa-Config.xml
    </param-value>
    
</context-param>

<listener>
    <listener-class>
        org.springframework.web.context.ContextLoaderListener
    </listener-class>
</listener>

- `ContextLoaderListener` creates the root WebApplicationContext.
- `root-context.xml` contains the bean definitions for that root context.



Java-based root context configuration:

- Configure the root context in `RootConfig.java` or in multiple config classes like AppConfig.java, JpaConfig.java etc.,
- Tell `WebAppInitializer.java` to use `RootConfig`.

public class WebAppInitializer extends AbstractAnnotationConfigDispatcherServletInitializer {

    // 1. Point to your root application context configuration (Services, Security, Repositories)
    @Override
    protected Class<?>[] getRootConfigClasses() {
        return new Class<?>[] { RootConfig.java };
        //return new Class<?>[] { AppConfig.java, JpaConfig.java };
    }

    // 2. Point to your Web/MVC configuration class (ViewResolvers, Controllers, Interceptors)
    @Override
    protected Class<?>[] getServletConfigClasses() {
        return new Class<?>[] { WebConfig.class };
    }

    // 3. This replaces your <servlet-mapping> <url-pattern>/</url-pattern> block
    @Override
    protected String[] getServletMappings() {
        return new String[] { "/" };
    }
}

- `getRootConfigClasses()` defines configuration for the root context.
- `getServletConfigClasses()` defines configuration for the DispatcherServlet's child WebApplicationContext.

ENABLE SPRING MVC INFRASTRUCTURE
------------------------------------------------------------

- Spring MVC infrastructure must be enabled so that Spring can configure the infrastructure required for annotation-based MVC processing.

- This includes infrastructure responsible for things such as:
  - Request mappings
  - Controller method invocation
  - Handler processing
  - Other annotation-based MVC support


XML-based configuration:

- Configure in `dispatcher-servlet.xml`.

<mvc:annotation-driven />

- The XML configuration requires the Spring MVC namespace.

<beans xmlns:mvc="http://www.springframework.org/schema/mvc"...>
    <mvc:annotation-driven />
</beans>



Java-based configuration:

- Configure in `WebConfig.java`.

@Configuration
@EnableWebMvc
public class WebConfig {
}

- `@EnableWebMvc` enables Spring MVC configuration support.

- `@EnableWebMvc` / `<mvc:annotation-driven>` enables the annotation-based MVC infrastructure required for mappings and controller method processing.


------------------------------------------------------------
COMPONENT SCAN
------------------------------------------------------------

- Component Scan tells Spring which packages to scan for Spring components.
- Spring discovers component classes and registers them as Spring beans.

- Common component annotations:

@Controller
@Service
@Repository
@Component


XML-based configuration:

- Configure in the appropriate Spring XML context.

- Controllers are normally scanned in `dispatcher-servlet.xml`:

<context:component-scan base-package="com.example.controller"/>

- Services and Repositories are commonly scanned in `root-context.xml`:

<context:component-scan base-package="com.example.service,com.example.repository"/>

- The XML configuration requires the Spring Context namespace.


Java-based configuration:

- Controllers are normally scanned in `WebConfig.java`:

@Configuration
@EnableWebMvc
@ComponentScan("com.example.controller")
public class WebConfig {
}

- Services and Repositories are commonly scanned in `RootConfig.java`:

@Configuration
@ComponentScan("com.example.service")
public class RootConfig {
}

- Conceptually:

@ComponentScan / <context:component-scan>
                  ↓
             Package scanning
                  ↓
          Find Spring components
                  ↓
       Register components as Beans


------------------------------------------------------------
VIEWRESOLVER CONFIGURATION
------------------------------------------------------------

- A ViewResolver maps a logical view name returned by a controller to an actual View.
- In SSR applications, the View is commonly a JSP.

- Configure the ViewResolver in the DispatcherServlet's child context.


- XML:
  - Configure in `dispatcher-servlet.xml`.

- Java:
  - Configure in `WebConfig.java`.


- Example controller:

return "employees";

- If the prefix is `/WEB-INF/views/` and suffix is `.jsp`:

"employees"
     ↓
/WEB-INF/views/employees.jsp



Java-based configuration:

- Configure in `WebConfig.java`.

@Bean
public InternalResourceViewResolver viewResolver() {

    InternalResourceViewResolver resolver =
            new InternalResourceViewResolver();

    resolver.setPrefix("/WEB-INF/views/");
    resolver.setSuffix(".jsp");

    return resolver;
}



XML-based configuration:

- Configure in `dispatcher-servlet.xml`.

<bean class="org.springframework.web.servlet.view.InternalResourceViewResolver">
    <property name="prefix" value="/WEB-INF/views/" />
    <property name="suffix" value=".jsp" />
</bean>

- The controller does not need to know the physical JSP location.


------------------------------------------------------------
FILTER CONFIGURATION
------------------------------------------------------------

- Filters are Servlet API components.
- They are configured at the Servlet-container level rather than through Spring MVC's HandlerMapping/HandlerAdapter mechanism.
- A Filter can be configured using:
  - `web.xml`
  - Java-based Servlet configuration


XML-based configuration:

- Configure in `web.xml`.

<filter>
    <filter-name>loggingFilter</filter-name>
    <filter-class>
        com.example.filter.LoggingFilter
    </filter-class>
</filter>

<filter-mapping>
    <filter-name>loggingFilter</filter-name>
    <url-pattern>/*</url-pattern>
</filter-mapping>


Java-based configuration:

- Configure in `WebAppInitializer.java`.

public class WebAppInitializer
        extends AbstractAnnotationConfigDispatcherServletInitializer {

    @Override
    protected Filter[] getServletFilters() {
        return new Filter[] {
            new LoggingFilter()
        };
    }

    ...
}

- Filter configuration determines which requests pass through the Filter.
- Filters can therefore execute before and/or after the DispatcherServlet processing.


------------------------------------------------------------
INTERCEPTOR CONFIGURATION
------------------------------------------------------------

- Spring MVC Interceptors are configured as part of Spring MVC configuration.
- They are associated with Spring MVC request processing.
- Interceptors are configured using:
  - XML-based Spring MVC configuration
  - Java-based Spring MVC configuration

- XML:
  - Configure in `dispatcher-servlet.xml`.

- Java:
  - Configure in `WebConfig.java`.


Java-based configuration:

@Configuration
@EnableWebMvc
public class WebConfig implements WebMvcConfigurer {

    @Override
    public void addInterceptors(
            InterceptorRegistry registry) {

        registry.addInterceptor(
                new LoggingInterceptor());
    }
}


XML-based configuration:

<mvc:interceptors>
    <bean class="com.example.interceptor.LoggingInterceptor"/>
</mvc:interceptors>


- Interceptors can also be configured for specific URL patterns.

Java-based example:

registry.addInterceptor(new LoggingInterceptor())
        .addPathPatterns("/employees/**");


XML-based example:

<mvc:interceptor>
    <mvc:mapping path="/employees/**"/>

    <bean class="com.example.interceptor.LoggingInterceptor"/>
</mvc:interceptor>


- Interceptor configuration is part of Spring MVC configuration, unlike Servlet Filters which belong to the Servlet container layer.

=======================================================================================================================================================================
EXCEPTION HANDLING
=======================================================================================================================================================================

- Spring MVC provides mechanisms to handle exceptions thrown during request processing.
- The main mechanisms covered are:

  - `@ExceptionHandler`
  - `@ControllerAdvice`

------------------------------------------------------------
@EXCEPTIONHANDLER


- `@ExceptionHandler` identifies a method that handles a particular exception.
- It can be defined inside a controller.
- The handler method can return a logical view name in an SSR application.

- Example:

@Controller
public class EmployeeController {

    @GetMapping("/employees/{id}")
    public String getEmployee(
            @PathVariable Long id,
            Model model) {

        ...
    }

    @ExceptionHandler(EmployeeNotFoundException.class)
    public String handleEmployeeNotFound() {

        return "employee-not-found";
    }
}

- If the controller throws `EmployeeNotFoundException`, Spring MVC can invoke the corresponding exception handler.

- SSR flow:


Controller
    ↓
Exception
    ↓
@ExceptionHandler
    ↓
Logical View Name
    ↓
ViewResolver
    ↓
JSP
    ↓
HTML Response

------------------------------------------------------------
@CONTROLLERADVICE


- `@ControllerAdvice` allows controller-related behavior to be applied across multiple controllers.
- It is commonly used to centralize exception handling.
- It avoids duplicating the same exception-handling methods in every controller.

- Without `@ControllerAdvice`:

```text
EmployeeController
    ↓
Exception Handler

DepartmentController
    ↓
Exception Handler

ProjectController
    ↓
Exception Handler

- With `@ControllerAdvice`:

EmployeeController ─┐
DepartmentController ├──→ @ControllerAdvice
ProjectController ───┘
                           ↓
                    Exception Handlers

- Example:

@ControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(EmployeeNotFoundException.class)
    public String handleEmployeeNotFound() {

        return "employee-not-found";
    }

    @ExceptionHandler(IllegalArgumentException.class)
    public String handleIllegalArgument(
            IllegalArgumentException ex) {

        return "bad-request";
    }
}


- `@ControllerAdvice` itself is not limited to a particular exception or controller.
- The exception type specified on each `@ExceptionHandler` determines which exception that particular method handles.
- A single `@ControllerAdvice` can contain multiple exception handlers.
- In SSR applications, these handlers can return logical view names.


- Example:

Any Controller
      ↓
Exception
      ↓
@ControllerAdvice
      ↓
Matching @ExceptionHandler
      ↓
View Name
      ↓
ViewResolver
      ↓
JSP
      ↓
HTML

- `@RestControllerAdvice` is the REST-oriented variant and is covered with Spring REST.
