PASSWORD & CREDENTIAL SECURITY
=======================================================================================================================================================================

PASSWORD STORAGE

- Spring Security does not store user passwords as plain text.
- The application stores an encoded password value.
- PasswordEncoder provides the abstraction for creating and verifying password hashes.
- In a database-backed application, the encoded password is normally loaded into UserDetails.
- DaoAuthenticationProvider uses the stored encoded password during username/password authentication.

- Example:

Database
|
v
User
|
+-- username = alice
+-- password = {bcrypt}$2a$10$...
+-- role = USER
|
v
UserDetails
|
v
DaoAuthenticationProvider
|
v
PasswordEncoder
|
v
Password verification

------------------------------------------------------------
PASSWORD ENCODING

- PasswordEncoder is the Spring Security abstraction used for password encoding and verification.

- The main operations are:

  - encode()
  - matches()

- encode() is used when creating or changing a password.

- Example:

PasswordEncoder encoder = new BCryptPasswordEncoder();

String encodedPassword = encoder.encode("admin123");

- The resulting encoded password is stored in the database.

- Password encoding uses a one-way password hashing mechanism rather than reversible encryption.

- The original password cannot be obtained from the stored hash through normal reversal.

------------------------------------------------------------
BCrypt

- BCryptPasswordEncoder is a commonly used PasswordEncoder implementation.

- BCrypt is specifically designed for password hashing.

- It incorporates a salt into the generated hash.

- Therefore, encoding the same password multiple times can produce different encoded values.

- Example:

encoder.encode("admin123")
|
+-------------------------------------------------------------> $2a$10$...
|
+-------------------------------------------------------------> $2a$10$...

- Both encoded values can represent the same raw password.
- PasswordEncoder.matches() handles the comparison correctly.

------------------------------------------------------------
PASSWORD VERIFICATION

- During authentication, Spring Security does not simply encode the supplied password again and compare two strings.
- It uses:

matches(rawPassword, storedEncodedPassword)

- Example:

User enters:
admin123

Stored value:
{bcrypt}$2a$10$...

PasswordEncoder.matches(
"admin123",
"{bcrypt}$2a$10$..."
)

Result:
true

- If the supplied password is incorrect:

Result:
false

- A failed password comparison results in authentication failure.

- UserDetailsService is responsible for loading the user and stored password.

- PasswordEncoder performs password verification.
- Successful authentication produces an authenticated Authentication object.
- The successful Authentication is placed into the SecurityContext for the current request.
- In a stateful form-login application, the SecurityContext can subsequently be persisted through the configured SecurityContextRepository and HTTP session.

------------------------------------------------------------
DELEGATING PASSWORD ENCODER

- DelegatingPasswordEncoder allows Spring Security to work with multiple password-encoding strategies through one PasswordEncoder.
- The stored password contains an encoding identifier.

- Example:

{bcrypt}$2a$10$...

- The `{bcrypt}` portion identifies the encoder that should be used.

- Simplified flow:

Stored password
|
v
{bcrypt}$2a$10$...
|
v
DelegatingPasswordEncoder
|
v
BCryptPasswordEncoder
|
v
Password verification

- This allows an application to support different encoding formats and migrate password hashes between encoding strategies without changing the authentication architecture.

------------------------------------------------------------
CREDENTIAL HANDLING

- Raw credentials should exist only for the period required to perform authentication.
- Application code should not unnecessarily retain raw passwords.
- Passwords should never be written to logs.
- Passwords should not be returned in API responses.
- Passwords should not be included in exception messages.
- Database records should contain encoded password values rather than raw passwords.

- Avoid:

System.out.println(password);

- Avoid:

logger.info("Login password: " + password);

- The goal is that the password supplied by the user is used for verification and is not unnecessarily exposed elsewhere in the application.

------------------------------------------------------------
PASSWORD SECURITY WITH USERDETAILS

- UserDetails represents the application's authenticated user's security information.
- For username/password authentication, its password value should normally be the stored encoded password.

- Example:

UserDetails
|
+-- username = alice
+-- password = {bcrypt}$2a$10$...
+-- authorities = ROLE_USER

- During authentication:

Username/password
|
v
UsernamePasswordAuthenticationFilter
|
v
AuthenticationManager
|
v
DaoAuthenticationProvider
|
+-- UserDetailsService
|       |
|       v
|   UserDetails
|
+-- PasswordEncoder
|
v
password verification

- UserDetailsService loads the stored security information.
- PasswordEncoder verifies the submitted password.
- DaoAuthenticationProvider creates the successful Authentication when verification succeeds.

------------------------------------------------------------
PASSWORD CREATION FLOW

- Password encoding normally occurs when a user is created or when a password is changed.

Raw password
|
v
PasswordEncoder.encode()
|
v
Encoded password
|
v
Store in database
|
v
UserDetailsService loads it during authentication

- The application should not store the raw password after it has been processed for storage.
