=============================================================================================================================================================================
=============================================================================================================================================================================
										Proxies
=============================================================================================================================================================================
=============================================================================================================================================================================

Goal:

To separate Cross-Cutting Concerns (Logging, Transactions, Security, Caching, etc.) from the Business Logic without modifying the Business Class.

=============================================================================================================================================================================
Why Proxies:
=============================================================================================================================================================================

Imagine we are building an Online Payment System.
Initially, our service looks like this:


public class PaymentService {

    public void processPayment() {
        // Business Logic
	repository.savePayment();
    }
}


Initially, the class contains only the business logic.
As the application grows, new requirements are introduced.

For example:

Logging
Transaction Management
Security Checks
Performance Monitoring
Caching
Retry Mechanism
Exception Handling
Audit Logging

Without Proxies, all these concerns are added directly into the business method.


Example:

public void processPayment() {

    logStart();
    securityCheck();
    startTransaction();
    repository.savePayment();
    commitTransaction();
    logEnd();

}


Cross-Cutting Concerns are functionalities that are required by multiple classes but are NOT part of the actual business logic.

Examples:

- PaymentService
- OrderService
- InvoiceService
- RefundService

Every service requires:

- Logging
- Transactions
- Security



Without Proxy: Client -> PaymentService

Problems:

- Business Logic becomes difficult to read.
- Same code is duplicated across multiple services.
- Maintenance becomes difficult.
- Violates the Single Responsibility Principle (SRP).

------------------------------------------------------------

- Instead of writing them in every class, Spring allows us to separate them using Proxies.
- A Proxy is an object that stands between the Client and the Real Object.
- Instead of directly calling the actual object, the client communicates with the Proxy.
- The Proxy can perform additional work before and after invoking the actual business method.


With Proxies: Client -> Proxy -> PaymentService

- Separates Cross-Cutting Concerns from Business Logic.
- Keeps Business Classes clean and maintainable.
- Eliminates duplicate code.
- Follows the Single Responsibility Principle (SRP).
- Allows Spring to add framework features without modifying the Business Class.


The Proxy decides what should happen:

Before Business Method: Logging, Security, Start Transaction
	↓
Business Method
	↓
After Business Method: Commit Transaction, Logging, Performance Monitoring


=============================================================================================================================================================================
BeanPostProcessors vs Proxies:
=============================================================================================================================================================================

BeanPostProcessors and Proxies work at different stages of a Spring Application.

------------------------------------------------------------
BeanPostProcessors

* BeanPostProcessors execute during the Bean Lifecycle (Application Startup).
* They are responsible for preparing, initializing, inspecting, modifying or enhancing the bean before it is stored inside the IoC Container.
* During the BeanPostProcessor (After Initialization) phase, Spring may create a Proxy instead of storing the original bean.
* Once the bean is fully prepared, Spring stores the original bean or the Proxy inside the IoC Container.

------------------------------------------------------------
Proxies

* Proxies execute during Runtime (Application Execution).
* They are created during the Bean Lifecycle but are used only after the application has started.
* Every time another object invokes a proxied bean through the IoC Container, the method call first reaches the Proxy.
* The Proxy executes additional framework logic before and after invoking the actual business method.

------------------------------------------------------------
Relationship Between BeanPostProcessors and Proxies

* BeanPostProcessors create the Proxy during the Bean Lifecycle.
* The Proxy is then stored inside the IoC Container instead of the original bean.
* During Runtime, every external method invocation reaches the Proxy first, which then delegates the call to the actual bean.


Application Startup:

Instantiate Bean
↓
Dependency Injection
↓
Aware Callbacks
↓
BeanPostProcessor (Before Initialization)
↓
@PostConstruct
↓
BeanPostProcessor (After Initialization)
↓
Proxy Created (If Required)
↓
Bean Ready (Original Bean or Proxy)

------------------------------------------------------------

Application Runtime:


Client
↓
Proxy
↓
Business Method
↓
Return Result


Important Note:

- The Proxy intercepts only external method calls that pass through the IoC Container.
- If one method inside the bean directly calls another method of the same bean (Self Invocation), the call bypasses the Proxy and the additional framework logic is not executed.

=============================================================================================================================================================================
Static Proxy:
=============================================================================================================================================================================

Goal: To separate Cross-Cutting Concerns (Logging, Transactions, Security, Caching, etc.) from the Business Logic without modifying the Business Class.


Consider the following PaymentService:


public class PaymentService {

    public void processPayment() {
        System.out.println("Processing Payment...");
    }
}


- Now suppose a new requirement is introduced "We need to log every payment request."
- One approach is to modify the PaymentService. Although this works, the business class is now responsible for both: Business Logic and Logging
- As more requirements are added (Transactions, Security, Caching, etc.), the business class becomes cluttered.
- Instead of modifying the business class, we create another class called a Proxy.
- The Proxy performs the additional work and then delegates the request to the real object.

------------------------------------------------------------

Business Interface:

public interface PaymentService {
    void processPayment();
}



Business Class:

public class PaymentServiceImpl implements PaymentService {

    @Override
    public void processPayment() {
        System.out.println("Processing Payment...");
    }
}



Proxy Class:

public class PaymentServiceProxy implements PaymentService {

    private PaymentServiceImpl service = new PaymentServiceImpl();
    
    @Override
    public void processPayment() {

        System.out.println("Payment Started");
        service.processPayment();
        System.out.println("Payment Completed");
    }
}



Client:

public class Main {

    public static void main(String[] args) {

        PaymentService proxy = new PaymentServiceProxy(new PaymentServiceImpl);
        proxy.processPayment();
    }
}

------------------------------------------------------------

Client
↓
PaymentServiceProxy.processPayment()
↓
Logging Before
↓
PaymentService.processPayment()
↓
Logging After
↓
Return

------------------------------------------------------------

Notice that the Client never directly communicates with the PaymentService. It always communicates with the Proxy.

This way:

- Business Logic remains clean and Cross-Cutting Concerns are separated.
- Existing Business Class does not need modification.
- Follows the Single Responsibility Principle (SRP).

This is called a static proxy.
Because, the proxy class is manually written by the developer at compile time.
And, before the application even runs, the compiler already knows about it.

Now, suppose we have the following services:

* PaymentService
* OrderService
* RefundService
* NotificationService

Each service now requires its own Proxy.


PaymentService
↓
PaymentServiceProxy

--------------------------------

OrderService
↓
OrderServiceProxy

--------------------------------

RefundService
↓
RefundServiceProxy

--------------------------------

NotificationService
↓
NotificationServiceProxy
```

Problems:

* Large amount of duplicate code.
* One Proxy class is required for every Business Class.
* Difficult to maintain.
* Every new service requires writing another Proxy manually.

This problem led to the introduction of Dynamic Proxies.

=============================================================================================================================================================================
JDK Dynamic Proxy:
=============================================================================================================================================================================

Goal: To eliminate the need to manually create a separate Proxy class for every Business Class.

- With Static Proxies, every Business Class requires its own Proxy.
- Although the business classes are different, the Proxy logic is almost identical.
- The only thing that changes is the target object.
- Instead of manually creating a Proxy class, Java can generate the Proxy automatically during Runtime.

The developer only provides:

* The Target Object.
* The additional logic to execute before and after every method invocation.

Java generates the Proxy class automatically.


Client
↓
Dynamic Proxy (Generated at Runtime)
↓
Target Object


- Java introduces an interface called: InvocationHandler
- Instead of writing a complete Proxy class, we implement only one method:

	public Object invoke(Object proxy, Method method, Object[] args);

- This method is executed whenever any method on the Proxy is called.
- Inside this method, we can write:

	* Logging
	* Security
	* Transaction Handling
	* Performance Monitoring

- Then invoke the actual business method.

------------------------------------------------------------

Business Interface:

public interface PaymentService {
    void processPayment();
}


Business Class:

public class PaymentServiceImpl implements PaymentService {

    @Override
    public void processPayment() {

        System.out.println("Processing Payment...");
    }
}


Invocation Handler:

public class LoggingHandler implements InvocationHandler {

    private Object target;

    public LoggingHandler(Object target) {
        this.target = target;
    }

    @Override
    public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {

        System.out.println("Payment Started");

        Object result = method.invoke(target, args);

        System.out.println("Payment Completed");

        return result;
    }
}


Client:

PaymentService service = new PaymentServiceImpl();

PaymentService proxy =
        (PaymentService) Proxy.newProxyInstance(
                service.getClass().getClassLoader(),	// To tell Java which class loader to be loaded
                service.getClass().getInterfaces(),	// To tell Java which interface should be implementing
                new LoggingHandler(service));		// For the method body

proxy.processPayment();

------------------------------------------------------------

Notice:
We never created PaymentServiceProxy. Java generated it automatically.


Client
↓
Generated Proxy
↓
invoke()
↓
Logging Before
↓
method.invoke(target)
↓
PaymentServiceImpl.processPayment()
↓
Logging After
↓
Return


Now, this proxy can be used with any service class PaymentService, OrderService, RefundService,...


Problems:

* JDK Dynamic Proxies can create Proxies only for Interfaces.
* If the Business Class does not implement an Interface, Java cannot generate a JDK Dynamic Proxy.

This limitation led to the introduction of CGLIB Proxies, which can create Proxies for concrete classes.

=============================================================================================================================================================================
CGLIB Dynamic Proxy:
=============================================================================================================================================================================

Goal: To create Dynamic Proxies for Concrete Classes that do not implement an Interface.

------------------------------------------------------------
Why was CGLIB introduced?

- JDK Dynamic Proxies can create Proxies only for Interfaces.
- Now consider the following class:


public class PaymentService {

    public void processPayment() {

        System.out.println("Processing Payment...");

    }

}


- Since there is no Interface, JDK Dynamic Proxy cannot create a Proxy.

------------------------------------------------------------
Solution - CGLIB Proxy


- Instead of implementing an Interface, CGLIB generates a Subclass of the Target Class during Runtime.

Example:

PaymentService
↓
PaymentService$$EnhancerByCGLIB


- The generated subclass overrides the methods of the original class.
- It executes additional logic before and after calling the original method.

------------------------------------------------------------

Business Class:

public class PaymentService {

    public void processPayment() {
        System.out.println("Processing Payment...");
    }
}


Method Interceptor:

public class LoggingInterceptor implements MethodInterceptor {

    @Override
    public Object intercept(Object obj, Method method, Object[] args, MethodProxy proxy) throws Throwable {

        System.out.println("Payment Started");

        Object result = proxy.invokeSuper(obj, args);

        System.out.println("Payment Completed");

        return result;
    }
}


Client:

Enhancer enhancer = new Enhancer();

enhancer.setSuperclass(PaymentService.class);

enhancer.setCallback(new LoggingInterceptor());

PaymentService proxy = (PaymentService) enhancer.create();

proxy.processPayment();

------------------------------------------------------------
Execution Flow


Client
↓
CGLIB Generated Subclass
↓
Logging Before
↓
super.processPayment()
↓
Logging After
↓
Return


- Instead of calling another object, the generated subclass invokes the original implementation using super.processPayment();

------------------------------------------------------------
Advantages:

* Works with Concrete Classes.
* No Interface is required.
* Eliminates the need for manually writing Proxy classes.
* Generates Proxies automatically during Runtime.

------------------------------------------------------------
Limitations:

* Cannot Proxy final classes.
* Cannot override final methods.
* Cannot Proxy private methods because they cannot be overridden.

------------------------------------------------------------
JDK Dynamic Proxy vs CGLIB Proxy:

| JDK Dynamic Proxy                            | CGLIB Proxy                                    |
| -------------------------------------------- | ---------------------------------------------- |
| Requires an Interface                        | Works with Concrete Classes                    |
| Generates a Proxy implementing the Interface | Generates a Subclass of the Target Class       |
| Uses `InvocationHandler`                     | Uses Method Interception by overriding methods |
| Cannot Proxy Classes without Interfaces      | Can Proxy Classes without Interfaces           |
| Part of Java (`java.lang.reflect`)           | External Library (used by Spring)              |


JDK Dynamic Proxy:

Interface -> Generated Proxy -> Target Object


CGLIB Proxy:

Target Class -> Generated Subclass -> Original Methods

=============================================================================================================================================================================
Important Note
==============

Spring AOP does not have its own Proxy mechanism.

Instead, Spring chooses one of the following based on the Target Bean:

* If the Bean implements an Interface → Spring creates a JDK Dynamic Proxy.
* If the Bean does not implement an Interface → Spring creates a CGLIB Proxy.

Both Proxies provide the same Spring features such as:

* @Transactional
* @Async
* @Cacheable
* Spring AOP
* Method Security

The only difference is the technology Spring uses to generate the Proxy.



=============================================================================================================================================================================
How Spring Creates Proxies
==========================

Goal: To understand how Spring automatically creates Proxies for Beans during the Bean Lifecycle.

=============================================================================================================================================================================
The Big Picture
===============

When a Spring Bean is created, Spring does not immediately store it inside the IoC Container.

Instead, the Bean passes through several phases of the Bean Lifecycle.

One of these phases allows Spring to replace the original Bean with a Proxy.

=============================================================================================================================================================================
Bean Lifecycle with Proxy Creation
==================================

```text
Bean Definition Created
        │
        ▼
Bean Instantiated
        │
        ▼
Dependency Injection
        │
        ▼
Aware Callbacks
        │
        ▼
BeanPostProcessor Before Initialization
        │
        ▼
@PostConstruct
        │
        ▼
BeanPostProcessor After Initialization
        │
        ▼
Spring checks whether the Bean requires a Proxy
        │
        ▼
If YES → Create Proxy
If NO  → Keep Original Bean
        │
        ▼
Store the Bean (or Proxy) inside the IoC Container
```

=============================================================================================================================================================================
Production Example
==================

```java
@Service
public class PaymentService {

    @Transactional
    public void processPayment() {

        System.out.println("Processing Payment");

    }

}
```

Notice:

The Bean contains

```java
@Transactional
```

This annotation tells Spring that every call to this method should execute inside a Transaction.

=============================================================================================================================================================================
Step 1 - Spring Creates the Bean
================================

Spring instantiates:

```java
PaymentService paymentService =
        new PaymentService();
```

This is still the original object.

No Proxy exists yet.

=============================================================================================================================================================================
Step 2 - Dependency Injection
=============================

Spring injects all required dependencies.

Example:

```java
@Autowired
private PaymentRepository repository;
```

The Bean is now fully initialized.

=============================================================================================================================================================================
Step 3 - BeanPostProcessor After Initialization
===============================================

During the After Initialization phase, Spring executes several internal BeanPostProcessors.

One of them checks:

* Does this Bean have @Transactional?
* Does this Bean have @Async?
* Does this Bean have @Cacheable?
* Does this Bean match any AOP Pointcuts?

If none of these are present,

Spring stores the original Bean.

If any are present,

Spring creates a Proxy.

=============================================================================================================================================================================
Step 4 - Spring Chooses the Proxy Technology
============================================

If the Bean implements an Interface,

Spring creates a JDK Dynamic Proxy.

```text
PaymentServiceImpl

↓

JDK Dynamic Proxy
```

---

If the Bean does not implement an Interface,

Spring creates a CGLIB Proxy.

```text
PaymentService

↓

PaymentService$$EnhancerBySpringCGLIB
```

=============================================================================================================================================================================
Step 5 - Spring Stores the Proxy
================================

The Proxy replaces the original Bean inside the IoC Container.

Conceptually:

```text
Before Proxy Creation

IoC Container

↓

PaymentService
```

After Proxy Creation

```text
IoC Container

↓

PaymentService Proxy
```

The original PaymentService object still exists, but it is wrapped by the Proxy.

The Container now exposes only the Proxy.

=============================================================================================================================================================================
Step 6 - Bean Injection
=======================

Suppose another Bean depends on PaymentService.

```java
@Service
public class OrderService {

    @Autowired
    private PaymentService paymentService;

}
```

Spring injects:

NOT

```text
PaymentService
```

Instead it injects

```text
PaymentService Proxy
```

The OrderService is unaware that it is interacting with a Proxy.

=============================================================================================================================================================================
Step 7 - Runtime Method Invocation
==================================

OrderService

↓

PaymentService Proxy

↓

Transaction Begins

↓

PaymentService.processPayment()

↓

Transaction Commits

↓

Return

Every method call passes through the Proxy before reaching the actual Business Method.

=============================================================================================================================================================================
Why does Spring create Proxies After Initialization?
====================================================

Spring must first create and initialize the actual Bean.

Only then can it inspect the fully constructed Bean and decide whether it requires additional behavior such as:

* Transactions
* Security
* Caching
* Asynchronous Execution
* Logging (AOP)

After making that decision, Spring either keeps the original Bean or wraps it inside a Proxy.

=============================================================================================================================================================================
Key Points
==========

* Spring creates Proxies during the BeanPostProcessor After Initialization phase.
* The original Bean is never modified.
* The Proxy wraps the original Bean.
* The IoC Container stores the Proxy instead of the original Bean.
* Other Beans receive the Proxy during Dependency Injection.
* Every method invocation first reaches the Proxy and then the actual Business Bean.
* Spring automatically chooses JDK Dynamic Proxy or CGLIB based on the target Bean.
