=============================================================================================================================================================================
=============================================================================================================================================================================
										Proxies
=============================================================================================================================================================================
=============================================================================================================================================================================

Goal:

- To separate Cross-Cutting Concerns (Logging, Transactions, Security, Caching, etc.) from the Business Logic without modifying the Business Class.

=============================================================================================================================================================================
Why Proxies:
=============================================================================================================================================================================

- Imagine we are building an Online Payment System.


public class PaymentService {

    public void processPayment() {
        // Business Logic
	repository.savePayment();
    }
}


- Initially, the class contains only the business logic.
- As the application grows, new requirements are introduced.

For example:

- Logging
- Transaction Management
- Security Checks
- Performance Monitoring
- Caching
- Retry Mechanism
- Exception Handling
- Audit Logging

- Without Proxies, all these concerns are added directly into the business method.


Example:

public class PaymentService {

    public void processPayment() {

        logStart();
        securityCheck();
        startTransaction();
        repository.savePayment();
        commitTransaction();
        logEnd();
    }
}


- Cross-Cutting Concerns are functionalities that are required by multiple classes but are NOT part of the actual business logic.
- Every Service require same concerns.

------------------------------------------------------------
Without Proxy: 
------------------------------------------------------------

Client -> PaymentService


Problems:

- Business Logic becomes difficult to read.
- Same code is duplicated across multiple services.
- Maintenance becomes difficult.
- Violates the Single Responsibility Principle (SRP).

------------------------------------------------------------
With Proxies:
------------------------------------------------------------

 Client -> Proxy -> PaymentService


- A Proxy is an object that stands between the Client and the Real Object.
- Instead of directly calling the actual object, the client communicates with the Proxy.
- The Proxy can perform additional work before and after invoking the actual business method.


Advantages:

- Separates Cross-Cutting Concerns from Business Logic.
- Keeps Business Classes clean and maintainable.
- Eliminates duplicate code.
- Follows the Single Responsibility Principle (SRP).
- Allows Spring to add framework features without modifying the Business Class.
- The Proxy decides what should happen before & after Business logic:


Before Business Method: Logging, Security, Start Transaction
	↓
Business Method
	↓
After Business Method: Commit Transaction, Logging, Performance Monitoring


Important Note:

- The Proxy intercepts only external method calls that pass through the IoC Container.
- If one method inside the bean directly calls another method of the same bean (Self Invocation), the call bypasses the Proxy and the additional framework logic is not executed.

------------------------------------------------------------
BeanPostProcessors vs Proxies:
------------------------------------------------------------

- BeanPostProcessors create the Proxy during the Bean Lifecycle.
- The Proxy is then stored inside the IoC Container instead of the original bean.
- During Runtime, every external method invocation reaches the Proxy first, which then delegates the call to the actual bean.


Application Startup:


Instantiate Bean
↓
Dependency Injection
↓
Aware Callbacks
↓
BeanPostProcessor (Before Initialization)
↓
@PostConstruct
↓
BeanPostProcessor (After Initialization)
↓
Proxy Created (If Required)
↓
Bean Ready (Original Bean or Proxy)


=============================================================================================================================================================================
Static Proxy:
=============================================================================================================================================================================

- Consider the following PaymentService:


public class PaymentService {

    public void processPayment() {
        System.out.println("Processing Payment...");
    }
}


- Now suppose a new requirement is introduced "We need to log every payment request."


Business Interface:

public interface PaymentService {
    void processPayment();
}



Business Class:

public class PaymentServiceImpl implements PaymentService {

    @Override
    public void processPayment() {
        System.out.println("Processing Payment...");
    }
}



Proxy Class:

public class PaymentServiceProxy implements PaymentService {

    private PaymentServiceImpl service;
    
    public PaymentServiceProxy(PaymentServiceImpl service) {
        this.service = service;
    }

    @Override
    public void processPayment() {

        System.out.println("Payment Started");
        service.processPayment();
        System.out.println("Payment Completed");
    }
}



Client:

public class Main {

    public static void main(String[] args) {

        PaymentService proxy = new PaymentServiceProxy(new PaymentServiceImpl);
        proxy.processPayment();
    }
}


Client
↓
PaymentServiceProxy.processPayment()
↓
Logging Before
↓
PaymentService.processPayment()
↓
Logging After
↓
Return


- Notice that the Client never directly communicates with the PaymentService. It always communicates with the Proxy.
- This way Business Logic remains clean and Cross-Cutting Concerns are separated.
- It follows the Single Responsibility Principle (SRP).
- This is called a static proxy. Because, the proxy class is manually written by the developer at compile time and before the application even runs, the compiler already knows about it.
- Now, suppose we have the following services:

* PaymentService
* OrderService
* RefundService
* NotificationService

- Each service now requires its own Proxy.


PaymentService
↓
PaymentServiceProxy

--------------------------------

OrderService
↓
OrderServiceProxy

--------------------------------

RefundService
↓
RefundServiceProxy

--------------------------------

NotificationService
↓
NotificationServiceProxy
```

Problems:

* Large amount of duplicate code.
* Every new service requires writing another Proxy manually.

- This problem led to the introduction of Dynamic Proxies.

=============================================================================================================================================================================
JDK Dynamic Proxy:
=============================================================================================================================================================================

- With Static Proxies, every Business Class requires its own Proxy.
- Instead of manually creating Proxy class for every business class, Java can generate the Proxy automatically during Runtime.
- The developer only provides:

* The Target Object.
* The additional logic to execute before and after every method invocation.

- Java generates the Proxy class automatically.


Client
↓
Dynamic Proxy (Generated at Runtime)
↓
Target Object


- Java introduces an interface called: InvocationHandler
- Instead of writing a complete Proxy class, we implement only one method:


public Object invoke(Object proxy, Method method, Object[] args);


- This method is executed whenever any method on the Proxy is called.
- Inside this method, we can write:

	* Logging
	* Security
	* Transaction Handling
	* Performance Monitoring

- Then invoke the actual business method.



Business Interface:

public interface PaymentService {
    void processPayment();
}


Business Class:

public class PaymentServiceImpl implements PaymentService {

    @Override
    public void processPayment() {

        System.out.println("Processing Payment...");
    }
}


Invocation Handler:

public class LoggingHandler implements InvocationHandler {

    private Object target;

    public LoggingHandler(Object target) {
        this.target = target;
    }

    @Override
    public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {

        System.out.println("Payment Started");

        Object result = method.invoke(target, args);

        System.out.println("Payment Completed");

        return result;
    }
}


Client:

PaymentService service = new PaymentServiceImpl();

PaymentService proxy =
        (PaymentService) Proxy.newProxyInstance(
                service.getClass().getClassLoader(),	// To tell Java which class loader to be loaded
                service.getClass().getInterfaces(),	// To tell Java which interface should be implementing
                new LoggingHandler(service)             // For the method body
        );		

proxy.processPayment();


- Notice we never created PaymentServiceProxy. Java generated it automatically.


Client
↓
Generated Proxy
↓
invoke()
↓
Logging Before
↓
method.invoke(target)
↓
PaymentServiceImpl.processPayment()
↓
Logging After
↓
Return


- Now, this proxy can be used with any service class PaymentService, OrderService, RefundService,...


Problems:

* JDK Dynamic Proxies can create Proxies only for Interfaces.
* If the Business Class does not implement an Interface, Java cannot generate a JDK Dynamic Proxy.

- This limitation led to the introduction of CGLIB Proxies, which can create Proxies for concrete classes.

=============================================================================================================================================================================
CGLIB Dynamic Proxy:
=============================================================================================================================================================================

- JDK Dynamic Proxies can create Proxies only for Interfaces.
- Now consider the following class:


public class PaymentService {

    public void processPayment() {

        System.out.println("Processing Payment...");

    }

}


- Since there is no Interface, JDK Dynamic Proxy cannot create a Proxy.
- Instead of implementing an Interface, CGLIB generates a Subclass of the Target Class during Runtime.

Example:

PaymentService
↓
PaymentService$$EnhancerByCGLIB


- The generated subclass overrides the methods of the original class.
- It executes additional logic before and after calling the original method.



Business Class:

public class PaymentService {

    public void processPayment() {
        System.out.println("Processing Payment...");
    }
}


Method Interceptor:

public class LoggingInterceptor implements MethodInterceptor {

    @Override
    public Object intercept(Object obj, Method method, Object[] args, MethodProxy proxy) throws Throwable {

        System.out.println("Payment Started");

        Object result = proxy.invokeSuper(obj, args);

        System.out.println("Payment Completed");

        return result;
    }
}


Client:

Enhancer enhancer = new Enhancer();

enhancer.setSuperclass(PaymentService.class);

enhancer.setCallback(new LoggingInterceptor());

PaymentService proxy = (PaymentService) enhancer.create();

proxy.processPayment();



Execution Flow:


Client
↓
CGLIB Generated Subclass
↓
Logging Before
↓
super.processPayment()
↓
Logging After
↓
Return


- Instead of calling another object, the generated subclass invokes the original implementation using super.processPayment();


Advantages:

* Works with Concrete Classes.
* No Interface is required.
* Eliminates the need for manually writing Proxy classes.
* Generates Proxies automatically during Runtime.


Limitations:

* Cannot Proxy final classes.
* Cannot override final methods.
* Cannot Proxy private methods because they cannot be overridden.

------------------------------------------------------------
JDK Dynamic Proxy vs CGLIB Proxy:

| JDK Dynamic Proxy                            | CGLIB Proxy                                    |
| -------------------------------------------- | ---------------------------------------------- |
| Requires an Interface                        | Works with Concrete Classes                    |
| Generates a Proxy implementing the Interface | Generates a Subclass of the Target Class       |
| Uses `InvocationHandler`                     | Uses Method Interception by overriding methods |
| Cannot Proxy Classes without Interfaces      | Can Proxy Classes without Interfaces           |
| Part of Java (`java.lang.reflect`)           | External Library (used by Spring)              |


JDK Dynamic Proxy:

Interface -> Generated Proxy -> Target Object


CGLIB Proxy:

Target Class -> Generated Subclass -> Original Methods


=============================================================================================================================================================================
How Spring Creates Proxies
=============================================================================================================================================================================

- When a Spring Bean is created, Spring does not immediately store it inside the IoC Container.
- Instead, the Bean passes through several phases of the Bean Lifecycle.
- One of these phases allows Spring to replace the original Bean with a Proxy.

------------------------------------------------------------

Bean Lifecycle with Proxy Creation:


Bean Definition Created
        │
        ▼
Bean Instantiated
        │
        ▼
Dependency Injection
        │
        ▼
Aware Callbacks
        │
        ▼
BeanPostProcessor Before Initialization
        │
        ▼
@PostConstruct
        │
        ▼
BeanPostProcessor After Initialization
        │
        ▼
Spring checks whether the Bean requires a Proxy
        │
        ▼
If YES → Create Proxy
If NO  → Keep Original Bean
        │
        ▼
Store the Bean (or Proxy) inside the IoC Container


Note: 

- Spring creates Proxies during the BeanPostProcessor After Initialization phase.


Example:


@Repository
public class PaymentRepository {

    public void savePayment() {

        System.out.println("Saving Payment");
    }
}


@Service
public class PaymentService {

    @Autowired
    private PaymentRepository repository;

    @Transactional
    public void processPayment() {

        repository.savePayment();
        System.out.println("Payment Processed");
    }
}


@Service
public class OrderService {

    @Autowired
    private PaymentService paymentService;

    public void placeOrder() {

        paymentService.processPayment();
    }
}


Notice:

- The Bean contains @Transactional
- This annotation tells Spring that every call to this method should execute inside a Transaction.

------------------------------------------------------------
Step 1 - Spring Creates the Bean


- Spring instantiates:

PaymentService paymentService = new PaymentService();

- This is still the original object. No Proxy exists yet.

------------------------------------------------------------
Step 2 - Dependency Injection


- Spring injects all required dependencies:


@Autowired
private PaymentRepository repository;


- The Bean is now fully initialized.

------------------------------------------------------------
Step 3 - BeanPostProcessor After Initialization


- During the After Initialization phase, Spring executes several internal BeanPostProcessors.
- One of them checks:

* Does this Bean have @Transactional?
* Does this Bean have @Async?
* Does this Bean have @Cacheable?
* Does this Bean match any AOP Pointcuts?

- If none of these are present, Spring stores the original Bean.
- If any are present, Spring creates a Proxy.
- In our example, we have @Transactional, so it will create a proxy for the bean

------------------------------------------------------------
Step 4 - Spring Chooses the Proxy Technology


- If the Bean implements an Interface, Spring creates a JDK Dynamic Proxy.
- If the Bean does not implement an Interface, Spring creates a CGLIB Proxy.

------------------------------------------------------------
Step 5 - Spring Stores the Proxy


- The Proxy replaces the original Bean inside the IoC Container.

Conceptually:

Before Proxy Creation

IoC Container
↓
PaymentService


After Proxy Creation

IoC Container
↓
PaymentService Proxy


- The original PaymentService object still exists, but it is wrapped by the Proxy.
- The Container now exposes only the Proxy.

------------------------------------------------------------
Step 6 - Bean Injection


- Now, another Bean OrderService depends on PaymentService.


@Service
public class OrderService {

    @Autowired
    private PaymentService paymentService;

}


- Spring does not inject PaymentService, instead it injects PaymentService Proxy
- The OrderService is unaware that it is interacting with a Proxy.

------------------------------------------------------------
Step 7 - Runtime Method Invocation


OrderService
↓
PaymentService Proxy
↓
Transaction Begins
↓
PaymentService.processPayment()
↓
Transaction Commits
↓
Return

- Every method call passes through the Proxy before reaching the actual Business Method.

------------------------------------------------------------
Why does Spring create Proxies After Initialization?


- Spring must first create and initialize the actual Bean.
- Only then can it inspect the fully constructed Bean and decide whether it requires additional behavior such as:

* Transactions
* Security
* Caching
* Asynchronous Execution
* Logging (AOP)

- After making that decision, Spring either keeps the original Bean or wraps it inside a Proxy.




=============================================================================================================================================================================
=============================================================================================================================================================================
									Spring AOP (Aspect-Oriented Programming)
=============================================================================================================================================================================
=============================================================================================================================================================================

Goal: To separate Cross-Cutting Concerns from Business Logic using Proxies.

------------------------------------------------------------
What is Spring AOP?


- Spring AOP is a framework feature that applies Cross-Cutting Concerns to Spring Beans using Proxies.
- It allows developers to execute additional logic:

* Before a Business Method
* After a Business Method
* Around a Business Method
* After an Exception is thrown

- without modifying the Business Class.

------------------------------------------------------------
Important Terminologies:


Aspect

- An Aspect is a module that contains Cross-Cutting Logic.
- It consists of one or more Advices and the Pointcuts that determine where those Advices should execute.

Example:

TransactionAspect
LoggingAspect
SecurityAspect


---

Advice

- Advice is the actual code that should execute at a particular point during a method invocation.

Types of Advice:

* Before
* After Returning
* After Throwing
* After (Finally)
* Around

Example:

Before
↓
Validate User

----------------------------

After Returning
↓
Commit Transaction

----------------------------

After Throwing
↓
Rollback Transaction

---

Join Point

- A Join Point represents a method execution where Spring AOP can apply additional logic.
- In Spring AOP, every intercepted method execution is a Join Point.

Example:

processPayment()
refund()
placeOrder()


- Each method execution is a Join Point.

---

Pointcut

- A Pointcut determines which Join Points should execute a particular Advice.

Example:

- Instead of applying Logging to every method, apply it only to:

PaymentService.*
OrderService.*


Only these methods become eligible for the Logging Advice.

---

Weaving

* Weaving is the process of connecting an Aspect with the Target Bean.
* In Spring, Weaving happens by creating a Proxy during Bean creation.

------------------------------------------------------------

Runtime
↓
Client
↓
PaymentService Proxy
↓
Before Advice
↓
Business Method
↓
After Returning / After Throwing
↓
Return

------------------------------------------------------------
Relationship Between AOP and Proxies:


- Spring AOP does not modify the original Business Bean, instead:

* Spring creates a Proxy.
* The Proxy executes the configured Advice.
* The Proxy then invokes the actual Business Method.
* The result is returned to the Client.

- Without a Proxy, Spring AOP cannot intercept method calls.

@Transactional:
=============================================================================================================================================================================

- It manages database transactions declaratively, allowing Spring to handle transaction boundaries, commit, rollback, and transaction propagation.


------------------------------------------------------------
Implementation:
------------------------------------------------------------


@Service
public class OrderService {

    @Autowired
    private OrderRepository orderRepository;

    @Autowired
    private InventoryRepository inventoryRepository;

    @Autowired
    private PaymentRepository paymentRepository;

    @Transactional
    public void placeOrder(Order order) {

        orderRepository.save(order);

        inventoryRepository.reduceStock(
            order.getProductId(),
            order.getQuantity()
        );

        paymentRepository.save(
            createPayment(order)
        );
    }
}


- If the method placeOrder() completes successfully, Spring commits the transaction.
- If an applicable exception occurs, Spring rolls back the transaction.


------------------------------------------------------------
How does @Transactional work internally?
------------------------------------------------------------

- Spring uses AOP (Aspect-Oriented Programming) and proxies to implement declarative transaction management.


Controller
- Calls OrderService.placeOrder()
      |
      V
Spring AOP Proxy
Transaction Interceptor
- Checks transaction attributes.
- Checks propagation settings.
- Starts or joins a transaction.
      |
      V
Actual OrderService method
- Executes business logic and repository calls    
      |
      V
Transaction completion
- Commit if successful
- Rollback if applicable failure



- Some important internal components:

Component			Responsibility
------------------------------------------------------------------
@Transactional			Declares transaction configuration
TransactionInterceptor		Intercepts method invocation
TransactionAttributeSource	Reads transaction metadata
PlatformTransactionManager	Manages transaction lifecycle
DataSourceTransactionManager	Manages JDBC transactions
JpaTransactionManager		Manages JPA transactions


------------------------------------------------------------
Rollback rules
------------------------------------------------------------

- By default, Spring rolls back for: RuntimeException, Error
- Spring does NOT roll back by default for checked exceptions.


Example:

@Transactional
public void createOrder() throws IOException {

    orderRepository.save(new Order());
    throw new IOException("File processing failed");
}


- The transaction is committed by default, despite the IOException.
- To change this:


@Transactional(rollbackFor = Exception.class)


- can also specify:


@Transactional(
    rollbackFor = IOException.class,
    noRollbackFor = IllegalArgumentException.class
)

@Async:
=============================================================================================================================================================================

- Used to execute a method asynchronously in a separate thread, allowing the calling thread to continue without waiting for that method to complete.
- It is Spring's abstraction over Java's concurrency mechanisms, such as Executor and thread pools.

------------------------------------------------------------
Use Case:
------------------------------------------------------------

- When a customer places an order, application needs to:

1. Save the order in the database (100 ms).
2. Send an email confirmation (1,000 ms).
3. Generate an invoice (800 ms).
4. Send a notification (500 ms).

- Without @Async, the request-processing thread is occupied until all four operations finish and takes approximately 2,400 ms.
- With @Async, we can execute some of these operations asynchronously.

------------------------------------------------------------
Implementation:
------------------------------------------------------------
 
- First, enable asynchronous execution in Spring.

@SpringBootApplication
@EnableAsync
public class Application {

    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}

- Now create a service

@Service
public class NotificationService {

    @Async
    public void sendEmail() {

        System.out.println(
            "Email thread: " +
            Thread.currentThread().getName()
        );

        // Simulate email processing
        try {
            Thread.sleep(1000);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }

        System.out.println("Email sent");
    }
}

- Call it from another service:

@Service
public class OrderService {

    private final NotificationService notificationService;

    public OrderService(NotificationService notificationService) {
        this.notificationService = notificationService;
    }

    public void placeOrder() {

        System.out.println(
            "Order thread: " +
            Thread.currentThread().getName()
        );

        // Save order
        System.out.println("Order saved");

        // Asynchronous execution
        notificationService.sendEmail();

        System.out.println("Order processing completed");
    }
}


Possible output:

Order thread: http-nio-8080-exec-1
Order saved
Order processing completed
Email thread: task-1
Email sent

------------------------------------------------------------
How does @Async work internally?:
------------------------------------------------------------

- Spring does not create a new thread every time it encounters @Async
- Spring generally uses a TaskExecutor (thread-pool-based executor) to manage asynchronous tasks

1. Spring AOP proxy:

- When Spring detects @Async, it creates an asynchronous interceptor around the bean (proxy).

2. TaskExecutor:

- The executor manages a pool of threads.

Thread Pool
 ├── Worker-1
 ├── Worker-2
 ├── Worker-3
 ├── Worker-4
 └── Worker-5

- If more tasks arrive than the number of worker threads, they may be queued

3. Worker thread:

- The worker thread picks up the submitted task and executes the actual method body.


------------------------------------------------------------
Configuring a custom thread pool
------------------------------------------------------------

@Configuration
@EnableAsync
public class AsyncConfig {

    @Bean(name = "taskExecutor")
    public Executor taskExecutor() {

        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();

        executor.setCorePoolSize(5);
        executor.setMaxPoolSize(10);
        executor.setQueueCapacity(100);

        executor.setThreadNamePrefix("async-");

        executor.initialize();

        return executor;
    }
}


Configuration		Meaning
---------------------------------------------------------
Core pool size = 5	Maintains five core worker threads
Max pool size = 10	Can grow to ten worker threads
Queue capacity = 100	Can hold 100 waiting tasks

-If all ten workers are busy and the queue is full, the task is rejected according to the configured rejection policy.


Using a named executor:

@Async("taskExecutor")
public void sendEmail() {
    // Email processing
}


------------------------------------------------------------
Return a result:
------------------------------------------------------------

- Spring supports Future and CompletableFuture.

@Service
public class ReportService {

    @Async("taskExecutor")
    public CompletableFuture<String> generateReport() {

        System.out.println(
            Thread.currentThread().getName()
        );

        // Simulate report generation
        try {
            Thread.sleep(3000);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new RuntimeException(e);
        }

        return CompletableFuture.completedFuture(
            "Report generated successfully"
        );
    }
}


- Calling service:

@Service
public class OrderService {

    private final ReportService reportService;

    public OrderService(ReportService reportService) {
        this.reportService = reportService;
    }

    public void process() {

        CompletableFuture<String> future =
                reportService.generateReport();

        System.out.println("Continuing other work");

        future.thenAccept(result ->
            System.out.println(result)
        );
    }
}
