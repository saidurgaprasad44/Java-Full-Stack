=============================================================================================================================================================================
=============================================================================================================================================================================
										Bean Lifecycle
=============================================================================================================================================================================
=============================================================================================================================================================================

Goal:

To understand how the Spring IoC Container creates, initializes, manages and destroys every bean.

=============================================================================================================================================================================
Why Bean Lifecycle is important?
=============================================================================================================================================================================

Creating an object is only one part of its life; Most objects require additional work before they are ready to be used.

For example:

- A Database bean may need to establish a database connection.
- A MailService may need to load SMTP configurations.
- A CacheManager may need to load cache entries.
- A REST Client may need to initialize HTTP connections.

Similarly, before the application shuts down, these resources must be released properly.

Without lifecycle management, developers would need to manually initialize and destroy every object.

Spring automates this entire process.

Every Spring Bean goes through the following phases:

1. Create BeanDefinition
2. Instantiate Bean
3. Inject Dependencies
4. Aware Callbacks
5. BeanPostProcessor (Before Initialization)
6. @PostConstruct
7. BeanPostProcessor (After Initialization)
8. Bean Ready
9. Bean Used
10. @PreDestroy
11. Destroy Bean

Spring automatically manages all these phases.

=============================================================================================================================================================================
1. Create BeanDefinition
=============================================================================================================================================================================

The first step is NOT creating the object.

Spring first creates a BeanDefinition.

A BeanDefinition is simply metadata (instructions) describing how to create the bean, not actual object

It contains information like:

- Bean Name
- Bean Class
- Scope (Singleton, Prototype, etc.)
- Constructor Information
- Property Information
- Initialization Method
- Destroy Method
- Lazy/Eager Initialization
- Other Bean Metadata

Example:

Bean Name      : userService
Class          : com.demo.UserService
Scope          : singleton
Dependencies   : UserRepository

At this stage, No object exists yet. Spring is only collecting information about every bean.

=============================================================================================================================================================================
2. Instantiate Bean
=============================================================================================================================================================================

Using the BeanDefinition, Spring now creates the actual Java object from the class.

Example:

UserService service = new UserService();

- During instantiation, Java allocates memory for the object in the JVM Heap and executes the constructor. 
- At this stage, the object exists in memory, but it may not yet be fully usable.

=============================================================================================================================================================================
3. Inject Dependencies
=============================================================================================================================================================================

After creating the object, Spring injects all required dependencies.

Example:

public class UserService {

    private UserRepository repository;
    public UserService(UserRepository repository){
        this.repository = repository;
    }

}


Spring creates:

UserRepository
↓
Injects it into
↓
UserService


Now the bean has everything it needs.

=============================================================================================================================================================================
4. Aware Callbacks
=============================================================================================================================================================================

If the bean implements one of Spring's *Aware interfaces, Spring provides information about itself.

Examples:

BeanNameAware
BeanFactoryAware
ApplicationContextAware
EnvironmentAware
ResourceLoaderAware

These callbacks allow a bean to know about the Spring container.

Example:

public class UserService implements BeanNameAware {

    @Override
    public void setBeanName(String beanName){
        System.out.println(beanName);
    }

}

Output: userService

=============================================================================================================================================================================
5. BeanPostProcessor (Before Initialization)
=============================================================================================================================================================================

Spring now gives every BeanPostProcessor a chance to modify the bean before initialization.

Method executed:

postProcessBeforeInitialization()

Typical uses:

- Validate bean configuration
- Inject additional values
- Modify bean properties
- Custom framework logic

Normally, application developers rarely implement BeanPostProcessor. Spring uses it internally.

=============================================================================================================================================================================
6. @PostConstruct
=============================================================================================================================================================================

Now Spring executes the bean's initialization logic.

Example:

@PostConstruct
public void init(){

    database.connect();

}

Typical uses:

- Open Database Connections
- Load Configuration
- Initialize Cache
- Read Files
- Create Thread Pools

After this step, the bean has completed its own initialization.

=============================================================================================================================================================================
7. BeanPostProcessor (After Initialization)
=============================================================================================================================================================================

Spring again gives every BeanPostProcessor a chance to modify the bean.

Method executed:

postProcessAfterInitialization()

This is where Spring usually creates proxies.

Examples:

- @Transactional
- @Async
- Spring Security
- AOP
- Caching

The original bean may now be wrapped inside a proxy object.

=============================================================================================================================================================================
8. Bean Ready
=============================================================================================================================================================================

The bean is now fully initialized.

It is stored inside the IoC Container.

The application can now use it.

Singleton beans remain inside the container until the application shuts down.

=============================================================================================================================================================================
9. Bean Used
=============================================================================================================================================================================

Whenever the application needs the bean, Spring returns it from the IoC Container.

Example:

@RestController
↓
UserService
↓
UserRepository
↓
Database

The same Singleton bean is reused for every request.

=============================================================================================================================================================================
10. @PreDestroy
=============================================================================================================================================================================

When the application is shutting down, Spring executes methods annotated with @PreDestroy.

Example:

@PreDestroy
public void cleanup(){

    database.close();

}


Typical uses:

- Close Database Connections
- Stop Threads
- Close Files
- Flush Logs
- Release Resources

=============================================================================================================================================================================
11. Destroy Bean
=============================================================================================================================================================================

After @PreDestroy,

Spring removes the bean from the IoC Container.

The bean becomes eligible for Garbage Collection.

Its memory will eventually be reclaimed by the JVM Garbage Collector.

=============================================================================================================================================================================
Complete Internal Flow
=============================================================================================================================================================================

Configuration (XML / Annotation / Java Config)
↓
Create BeanDefinitions
↓
Instantiate Bean
↓
Inject Dependencies
↓
Aware Callbacks
↓
BeanPostProcessor (Before Initialization)
↓
@PostConstruct
↓
BeanPostProcessor (After Initialization)
↓
Bean Ready
↓
Bean Used Throughout Application
↓
@PreDestroy
↓
Destroy Bean
↓
Garbage Collection (JVM)



Note - Proxies are usually created during postProcessAfterInitialization().

=============================================================================================================================================================================
Example bean to understand the complete lifecycle in one go:
=============================================================================================================================================================================

@Repository
public class PaymentRepository {

    public void savePayment() {
        System.out.println("Payment saved successfully.");
    }

}



@Service
public class PaymentService implements BeanNameAware {

    @Autowired
    private PaymentRepository repository;

    private BankApi bankApi = new BankApi();

    @Override
    public void setBeanName(String beanName) {
        System.out.println("Bean Name : " + beanName);
    }

    @PostConstruct
    public void initialize() {

        // One-time Initialization

        bankApi.authenticate();

        System.out.println("Connected to Bank Server.");

    }

    @Transactional
    public void processPayment() {

        repository.savePayment();

    }

}

------------------------------------------------------------
Step 1 - Scan the Package


Spring scans the configured package.
It discovers the following Spring Beans:

- PaymentRepository
- PaymentService

At this stage, Spring has only identified the bean classes. No objects are created yet.

------------------------------------------------------------
Step 2 - Create BeanDefinitions


For every discovered bean, Spring creates a BeanDefinition.
At this stage:

PaymentRepository  → BeanDefinition
PaymentService     → BeanDefinition


The actual objects still do not exist.

------------------------------------------------------------
Step 3 - Instantiate PaymentRepository


Spring starts creating beans.
Since PaymentRepository has no dependencies (no @Autowired), Spring simply creates it.


Equivalent to:

PaymentRepository repository = new PaymentRepository();


The object is now created in the JVM Heap. but it is not yet ready to be used.

------------------------------------------------------------
Step 4 - Process the PaymentRepository Bean


Now imagine Spring has a list of Processors.


Processor A -> Value Processor
	↓
Processor B -> PostConstruct Processor
	↓
Processor C -> Transaction Proxy Processor
	↓
Processor D -> AOP Proxy Processor


Each one has one responsibility. 

Who registered them? 
Spring did. During startup.

What all processors are registered?
Spring is smart. Spring only registers the processors required for the features you're using. 


Now Spring says:


Repository Bean Created
↓
Let's ask every processor
if it wants to do something.


PaymentRepository contains none of these features.
Therefore, every stage simply passes the bean without making any changes.
Spring stores the fully prepared PaymentRepository bean inside the IoC Container.

------------------------------------------------------------
Step 5 - Instantiate PaymentService


Spring now creates the PaymentService object.


Equivalent to:

PaymentService service = new PaymentService();


The object exists, but it is not yet ready to perform business operations.
Now the same processors run again.

------------------------------------------------------------
Step 6 - Perform Dependency Injection

For dependencies Spring runs a special processor InstantiationAwareBeanPostProcessor that checks for @Autowired

Spring detects:

@Autowired
private PaymentRepository repository;


Spring searches the IoC Container for a PaymentRepository bean.
Since it already exists, Spring injects it.


Equivalent to:

service.repository = repository;

------------------------------------------------------------
Step 7 - Execute Aware Callbacks


PaymentService implements:

BeanNameAware


Spring therefore calls:

setBeanName("paymentService");


The bean now knows its own Spring bean name.

------------------------------------------------------------
Step 8 - Execute BeanPostProcessor (Before Initialization)


Spring now sends the bean through every registered BeanPostProcessor.

Each BeanPostProcessor checks whether it has any responsibility for the current bean.

If not, it simply passes the bean to the next processor.

------------------------------------------------------------
Step 9 - Execute @PostConstruct


Spring detects:


@PostConstruct
public void initialize() {

    bankApi.authenticate();
}


Spring invokes this method once.
This method is used for one-time initialization after dependency injection has completed.
Typical production work includes:

* Authenticating with external systems.
* Loading lookup data.
* Building caches.
* Validating configuration.
* Initializing expensive resources.

In this example, the application authenticates with the Bank API before processing any payment requests.

Notice:
@PostConstruct prepares the bean.
It is NOT the bean's business logic.

------------------------------------------------------------
Step 10 - Execute BeanPostProcessor (After Initialization)


Spring again sends the bean through every registered BeanPostProcessor.
One of Spring's internal BeanPostProcessors detects:


@Transactional


Instead of returning the original PaymentService object, Spring creates a Proxy.


PaymentService Proxy
↓
PaymentService


The Proxy is returned to the IoC Container.
(The complete Proxy mechanism will be explained in the next chapter.)

------------------------------------------------------------
Step 11 - Bean Ready


The fully prepared bean (or Proxy) is stored inside the IoC Container.
Whenever another bean requests like:

@Autowired
private PaymentService paymentService;

Spring returns the Proxy.
The application is now fully started.
The PaymentService bean waits until another component invokes:

paymentService.processPayment();

Only then does the actual business logic execute.

=============================================================================================================================================================================
=============================================================================================================================================================================
										Bean Scopes
=============================================================================================================================================================================
=============================================================================================================================================================================

Goal: To understand who owns each scope and when each scope should be used in a real production application.

=============================================================================================================================================================================
Why Bean Scopes are important?
=============================================================================================================================================================================

Should Spring create only one object for the entire application?
		or
Should it create a new object every time it is requested?
		or
Should each HTTP request get its own object?



This behavior is controlled using Bean Scopes.

=============================================================================================================================================================================
What is a Bean Scope?
=============================================================================================================================================================================

A Bean Scope defines:

- How many objects Spring should create for a bean.
- How long those objects should live.
- When they should be destroyed.

Different applications require different lifecycles.

For example:

Database Connection Pool - Only one object is enough.
Shopping Cart - Each user should have a different object.
Request Information - Each HTTP request should have a different object.

=============================================================================================================================================================================
Types of Bean Scopes
=============================================================================================================================================================================

Spring provides six bean scopes:

1. Singleton (Default)
2. Prototype
3. Request
4. Session
5. Application
6. WebSocket

The first two are available in every Spring application.

The remaining scopes are available only in Web Applications.

=============================================================================================================================================================================
1. Singleton Scope (Default)
=============================================================================================================================================================================

Spring creates only ONE object of the bean for the entire IoC Container.

Every request for that bean receives the same object.

Example:

@Service
@Scope("singleton")
public class UserService {
}

Since Singleton is the default scope, the above is equivalent to simply writing:

@Service
public class UserService {
}


Flow:

Application Starts
↓
Spring creates one UserService object
↓
Stores it inside the IoC Container
↓
Controller A requests UserService
↓
Same object returned
↓
Controller B requests UserService
↓
Same object returned
↓
Application Shutdown
↓
Bean Destroyed


Example:


@RestController
public class UserController {

    @Autowired
    private UserService service;

}

@RestController
public class AdminController {

    @Autowired
    private UserService service;

}


Both controllers receive the same UserService object.

------------------------------------------------------------

Advantages:

- Low Memory Usage
- Better Performance
- Thread safe
- Faster Object Retrieval
- Suitable for Services and Repositories

Disadvantages:

- Since all users share the same object, Singleton beans should NOT store user-specific data. 
- They should be Stateless 

------------------------------------------------------------

Why Singleton Beans Should Be Stateless?

Saying a singleton bean should be stateless means that the bean must not store changeable, client-specific data in its class-level variables. Because Spring Framework creates only one single instance of a singleton bean for the entire application, that exact same instance is shared and executed by multiple users (threads) at the same time.

Good Example:

@Service
public class CalculatorService {

    public int add(int a, int b) { 	// Business logic only
        return a + b;
    }
}

Every request provides its own data. Nothing is stored inside the object.

Use Singleton for Controllers, Services and Repositories. Because, these classes only contain business logic. 

Nothing those classes belongs to a specific user. Therefore, one object is enough for the entire application.

------------------------------------------------------------

Bad Example:

@Service
public class LoginService {

    private String currentUser;

    public void login(String username){
        currentUser = username;
    }
}

Suppose:

User A logs in, currentUser = "Sai", before User A finishes,
User B logs in, currentUser = "John", now User B and A both see currentUser = "John"
Both users are sharing the same object. This is called a Stateful Singleton.

It is unsafe. Instead, Store user-specific data in:

- Database
- Session
- JWT
- Redis
- Request Object

NOT inside Singleton Beans.

=============================================================================================================================================================================
2. Prototype Scope
=============================================================================================================================================================================

Spring creates a NEW object every time the bean is requested.


Example:

@Component
@Scope("prototype")
public class ReportGenerator {
}


Flow:

getBean()
↓
Create New Object
↓
Return Object
↓
getBean()
↓
Create Another Object
↓
Return Another Object


Every request receives a different object.


Important Note: Spring manages only the creation of Prototype beans. After returning the bean, Spring no longer manages it.

Specifically:

- @PreDestroy is NOT called.
- Spring does NOT destroy Prototype beans.

The developer is responsible for cleanup.

------------------------------------------------------------
Singleton vs Prototype


Singleton

Objects Created		: 1
Lifecycle		: Entire Application
Stored in Container	: Yes
Destroyed by Spring	: Yes
Shared			: Yes
Typical Usage		: Services, Repositories, Configuration, Utilities



Prototype

Objects Created		: Unlimited
Lifecycle		: Per Request to getBean()
Stored in Container	: No
Destroyed by Spring	: No
Shared			: No
Typical Usage		: Temporary Objects, File Processing, Report Generation, PDF Creation

=============================================================================================================================================================================
3. Request Scope
=============================================================================================================================================================================

Available only in Web Applications.

Spring creates one bean per HTTP Request.


Flow:

HTTP Request
↓
Create Bean
↓
Use Bean
↓
HTTP Response
↓
Destroy Bean


Example:

@Component
@RequestScope
public class RequestData {

}

Every HTTP request receives its own object

Each object can store request-specific information such as:

- Request Id
- Client IP Address
- Authenticated User / JWT Claims
- Request Start Time
- Correlation ID
- Request-specific Data

This information is available only while processing the current HTTP request.

Once the request is completed and the response is sent, Spring destroys the Request-scoped bean.

The next HTTP request receives a completely new bean instance.

=============================================================================================================================================================================
4. Session Scope
=============================================================================================================================================================================

Available only in Web Applications.

One bean is created for each HTTP Session.


Flow:

User Login
↓
Create Bean
↓
Multiple Requests
↓
Same Bean Used
↓
Logout / Session Timeout
↓
Destroy Bean


Example:

@Component
@SessionScope
public class ShoppingCart {

}

Each user gets their own ShoppingCart.

=============================================================================================================================================================================
5. Application Scope
=============================================================================================================================================================================

Available only in Web Applications.

One bean is created for the entire ServletContext. All users share the same object.

Example:

@Component
@ApplicationScope
public class ApplicationStatistics {

}

Typically used for:

- Global Configuration
- Application Statistics
- Shared Cache

=============================================================================================================================================================================
6. WebSocket Scope
=============================================================================================================================================================================

- Available only in WebSocket Applications.
- One bean is created for each WebSocket session.
- Destroyed when the WebSocket connection closes.

=============================================================================================================================================================================
Choosing the Right Scope
=============================================================================================================================================================================

Singleton

Use when:

- Bean contains business logic
- Bean is stateless
- Bean can be shared

Examples:

- Services
- Repositories
- Controllers

------------------------------------------------------------

Prototype

Use when:

- Each operation requires a new object
- Object contains temporary state

Examples:

- PDF Generator
- Excel Generator
- File Processor

------------------------------------------------------------

Request

Use when:

- Data belongs to one HTTP request

Examples:

- RequestInfo
- AuditRequest
- RequestContext

------------------------------------------------------------

Session

Use when:

- Data belongs to one logged-in user

Examples:

- Shopping Cart
- User Preferences

------------------------------------------------------------

Application

Use when:

- Data should be shared by the entire application.

Examples:

- Application Statistics
- Global Configuration

=============================================================================================================================================================================
Before Spring:
=============================================================================================================================================================================

Java never had the concept of Bean Scopes. Developers themselves decided:

- When an object should be created.
- How long it should live.
- Who should own it.
- When it should be destroyed.

Everything depended on where the developer wrote the "new" keyword.

------------------------------------------------------------

Singleton-like Objects (Before Spring):

If the object is created once during application startup and reused everywhere, it behaves like a Singleton.


Example:

public class Main {
    public static void main(String[] args) {

        Calculator calculator = new Calculator();
        // Entire application uses the same object
    }
}

One object is created.
↓
Entire application uses the same object.

------------------------------------------------------------

Prototype-like Objects (Before Spring):

If the object is created every time a request is processed, each request receives a new object.


Example:

public void processRequest() {

    Calculator calculator = new Calculator();
    calculator.add(10,20);
}


Request 1
↓
new Calculator()
↓
Object Used
↓
Eligible for Garbage Collection


Request 2
↓
new Calculator()
↓
New Object Created

------------------------------------------------------------

Request Scope (Before Spring):


Servlet developers manually stored objects inside the HttpServletRequest.


Example: 

request.setAttribute("user", user);

The object lived only for that HTTP request.

------------------------------------------------------------

Session Scope (Before Spring)


Developers manually stored objects inside HttpSession.


Example:

session.setAttribute("shoppingCart", cart);

The object remained alive until the user logged out or the session expired.

------------------------------------------------------------

Application Scope (Before Spring)


Developers manually stored objects inside ServletContext.


Example:

getServletContext().setAttribute("configuration", configuration);

The object was shared by the entire application.
