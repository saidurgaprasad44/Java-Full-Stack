EntityManager and Persistence operations 

EntityManagerFactory emf = Persistence.createEntityManagerFactory("employeeCRUD");
EntityManager em = emf.createEntityManager();

EntityManager is an interface used to manage the entities and its lifecyle in the persistence context

- em.persist(employee) - CREATE: creates new entity in persistence context to manage/track it and schedule it to be inserted in the db
- em.find() - READ: JPA first checks the persistence context, return it if it is present in persistence context, or query database, create entity in persistence context, & make it managed 
- em.remove(employee) - DELETE: mark it for deletion and during flush, hibernate removes it 
- em.merge(): copies the detached/transient entity's state and applies it the newly created/managed entity, if a managed entity with same identity is already present in the persistence context, it will not create a new entity in the persistence context
- em.flush():
- em.detach():

- em.close(): closes the entitymanager/persistence context

Lazy/Eager loading & proxies

when to load/fetch the dependent entities

eager loading - fetches the related data while the entities themselves are loaded
lazy loading - keeps the hibernate proxies in place of related data while loading the entities and retrieves the related data from the data only when requested.

@ManyToOne(fetch = FetchType.LAZY)

by default:

@ManyToOne, @OneToOne are Eagerly loaded
@ManyToMany, @OneToMany are Lazily loaded

LazyInitializationException

=======================================================================================================================================================================

Cascade & orphan removal

cascade: while performing a lifecycle operation like em.find(), em.remove(), em.detach(), etc, hibernate decides whether to propagate the operation to its related entities or not based on the cascade configuration

orphan removal: the child entity becomes an orphan in the relationship when it is removed from the relationship. hibernate decides whether to delete such entities or not based on the configuration

@OneToMany(mappedBy = "department", cascade = CascadeType.ALL, orphanRemoval = true)

N+1 problem ⭐

JOIN FETCH: while loading/fetching the employee table, fetch the department entities as well

Entity Graph: 
defining an entity graph:
@Entity
@NamedEntityGraph(
    name = "Employee.withDepartment",
    attributeNodes = {
        @NamedAttributeNode("department")
    }
)
class Employee {
    @Id
    Long id;

    String name;

    @ManyToOne(fetch = FetchType.LAZY)
    Department department;
}

using the graph:

EntityGraph<Employee> graph =
    em.createEntityGraph("Employee.withDepartment");

Map<String, Object> properties = new HashMap<>();

properties.put(
    "jakarta.persistence.fetchgraph",
    graph
);

Employee employee =
    em.find(
        Employee.class,
        1L,
        properties
    );



JOIN FETCH = fetching is specified inside the query.
Entity Graph = fetching is specified separately as a fetch plan.

Optimistic/pessimistic locking

optimistic locking: hibernate and database maintain the version column to control the locks - @Version
pessimistic locking: LockModeType.PESSIMISTIC_WRITE,

Account account = em.find(Account.class, id, LockModeType.PESSIMISTIC_WRITE);

Account account = em.createQuery("SELECT a FROM Account a WHERE a.id = :id", Account.class)
    .setParameter("id", id)
    .setLockMode(LockModeType.PESSIMISTIC_WRITE) // Syntax flag
    .getSingleResult();

Caching

l1 cache - persistence context (enabled by default) - reference to the actual java objects - not another copy of entities - no need of invalidation/updates
l2 cache - hibernate's sessionfactory (not enabled by default) - keeps another copy/cache of entities - needs data invalidation/update - not equivalent to distributed cache like redis
query cache - caches the identifiers of entities instead of the entire entities while using typedqueries
